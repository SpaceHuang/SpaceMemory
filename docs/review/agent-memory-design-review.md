**但存在 2 个阻断项**——均为"两条决策记录互相矛盾 / 强制机制错位"，不是架构错误，修复只需要改写规格文本：

两项解决前不应进入 §8 第 4 步（核心库）与第 5 步（brief / 台账闭环）；第 1–3 步（格式规范）可并行推进。

## 一、阻断项（必须先解决）

### B1. "brief 纯读"（D12）与"首次 brief 创建台账 / trail 机械追加"（D13/D14）互相矛盾

**位置**：D12（"brief 纯读、索引支撑，多 Agent 并发冷启动互不干扰"）；D13 第 1 条（会话建立触发器含"首次 brief"）与 trail 定义；D14 工具响应 footer。

**问题**：

1. D13 明确把"首次 brief"列为会话台账记录的创建触发器——brief 至少每会话写一次；trail"机械追加（本会话经接口触碰过的记录）"进一步使每次 show/find/trace 都是一次对 sessions/ 的写。D12 的"纯读"在按文实现下不成立。
2. "纯读"是 D12 论证"多 Agent 并发冷启动互不干扰"的全部依据；改为写之后，该性质必须靠 D3 锁协议重新论证。各会话建各自的台账文件、冲突面确实小，但"互不干扰"不再是纯读的免费推论，论证链条断了。
3. 留下一个无法回答的验收问题：只读存储（只读挂载、只读权限）上 `mem brief` 是否可用？按 D12 答"是"，按 D13 答"否"。R1.1 验收演示（B 接手 A）与所有 brief 测试用例都依赖这个答案。
4. 连带未定义：trail 追加是否逐次 git 提交。开放问题 14 只覆盖"sessions/ 入不入 git"，没覆盖"每次触碰一次提交？"——若逐次提交则是提交噪音，若不提交则 trail 的 git 可审计性为空。

**为什么是阻断**：冷启动链（§8 第 5 步的核心）是全系统最高频路径，两条决策记录对它的读写性质给出相反答案；按文实现必然由实现者随机选边，测试无法先行定义。

**修复建议**（a 必做，b/c 一并做掉成本更低）：

- a) 显式定义 brief 的写集：每会话首次调用创建台账记录（幂等，以会话 ID 为键），此后纯读；trail 追加定义在 show/find/trace 侧而非 brief 侧（或明确 brief 也追加，但"纯读"字样全文废除，改为"除会话建立外不改任何记录"）；
- b) 定义降级：只读存储上 brief 跳过台账建立、输出显式标注（R8.9 式文档化降级路径）；
- c) trail 的 git 策略与提交粒度写死（建议：追加不逐次提交，随 end-hook flush 或定期对账合并提交，与开放问题 14 合并定稿）。

### B2. 唯一键强制机制写成"唯一索引"，与红线 8 / D5 嵌入模式只读矛盾——嵌入模式下 R3.3 无机制

**位置**：D11.2（"基础设施如唯一索引强制"）；红线 8（"索引永不 gate 正确性，只 gate 速度"）；D5（"嵌入模式对索引只读"）；§4 R3.3 行（"规范路径 O_EXCL/mkdir"）。

**问题**：R3.3 要求唯一性"由基础设施强制，不依赖写入者'先查后建'"，且验收场景就是多进程竞态。而按 v0.3 现文：

1. SQLite 唯一索引是派生缓存——按红线 8 不得 gate 正确性，崩溃/漂移即重建，不能作为拒收依据；
2. 嵌入模式（sidecar 不在场）对索引**只读**——索引连写入都做不了，遑论强制；而嵌入模式恰是多进程竞态的高发场景（D2/D3 存在的全部理由）；
3. 若按 D11.2 字面把强制点建在索引上，R3.3 的保证就依赖一个可丢弃、可漂移、嵌入模式下只读的缓存——直接违反红线 8，并复活前代评审 B1 的失败模式（check-then-act 竞态击穿唯一性，且事后两个文件都合法、无修复路径）。

§4 映射行里的"规范路径 O_EXCL/mkdir"表明作者脑中有正确的机制（路径级原子独占创建），但它没有进入决策记录；目前两处表述互相打架，实现者会按 D11.2（更详细的那处）把强制点建错位置。

**为什么是阻断**：R3.3 对应整体成功判据 3（"无重复创建"）；核心库（§8 第 4 步）会按错误位置实现强制点，事后迁移成本远大于现在改一段文本。

**修复建议**：

- a) 把 (a) 类强制点定在文件系统原子原语上，二选一写入 D11.2：
  - **记录路径即自然键**：`records/task/<scope>/<slug>` 规范路径，O_EXCL 创建，输者读赢者 ID 返回既有记录——与 D11.2 已有的"mkdir EEXIST 语义"一句自洽，无需额外文件；
  - 或 **键指针文件**：`.keys/<type>/<key 哈希>` → 记录 ID，O_EXCL 创建（存储多一层机器文件，牺牲部分 R2.2 人读性）；
- b) 显式降级 SQLite 唯一索引的角色为"缓存与对账诊断"，永不作为拒收依据，写进红线 8 的注释或 D5；
- c) 键的字符集 / 大小写规则随此一并定稿（见 M1——Windows 大小写不敏感与中文 slug 是前代 B2 的直接残留面）。

## 二、高优先级（实现对应组件前必须决策）

### H1. 红线 11 与 D12 第 1 步（cwd 缺省视图指针）字面冲突

红线 11："禁止从 cwd、目录名或宿主环境推断（身份、主题、项目、视图）"；D12 冷启动第 1 步恰是从 cwd 读指针文件选视图。设计意图自洽——指针是对**已声明视图的显式选择**，不是从环境推断视图内容——但红线作为合规判据没有这个但书，按红线字面，冷启动链第一天就违规。建议红线 11 补 carve-out："cwd 指针仅选择已声明的视图，视图内容全部来自声明数据，不构成推断"。

### H2. 多记录事务（merge / `mem apply`）没有并发协议

D3 只定义了单记录锁协议。D11.3 的 merge 要重定向 N 条引用记录并"单次 git 提交"，D6 的 `mem apply` 执行多记录计划。按现文实现会撞上：多锁获取顺序未定义（两个 merge 的引用集相交且方向相反 → 死锁）；中途崩溃的半成品状态未定义（部分引用已重定向、部分未动）；"单次提交"与逐记录"路径圈定提交"（D3 第 4 步）如何拼合成一个事务未说明。建议：维护类多记录操作走**全局维护锁**（低频、经人工确认，简单可靠，无需锁排序），并把 merge 的操作顺序写死（先重定向引用、别名落位，被合并者 tombstone 最后）与崩溃恢复语义（别名先于删除生效，使中断态仍可解析）。

### H3. D3 第 4 步（git 提交）的并发语义未定义

每记录锁不解决 git 自身的 `.git/index.lock` 全局串行：两进程各改各的记录、同时进入提交步骤，必有一方 commit 失败。D3 第 6 步的"重试耗尽"只覆盖记录 CAS，未覆盖提交步骤。需要写明：git 提交是**可重试资源**（index.lock 冲突退避重试）；"已落盘但未提交"的状态按 R2.4 处理（合法、下次提交顺带入库）。这与"冲突一等结果"的既有承诺一致，但必须写出来，不能留给实现者现场发明。

### H4. 台账接续的选择规则缺失（R1.1 验收路径）

D13 说"B 的 brief 读到 A 的台账，增量接续"、"自你上次读取以来的变更"；但多 Agent 场景下 active 台账天然有多条（zcode、codex、DSH 各自会话并行）：brief 读**谁的**台账？水位挂在会话上，而接续语义需要跨会话解析，选择/合并规则未定义。建议：同 principal + view 的最近 active 会话优先接续，其余 principal 的活动以 peers 摘要呈现；无任何台账时水位回退为全库最近事件。

### H5. 红线 3 与 D6"进阶档"（预授权自动合并）字面冲突

红线 3："永不无确认改写记录内容；机械注记除外"。D6 进阶档允许按版本化策略**自动合并**重复项——merge 是内容改写（重定向引用、写别名），无逐次确认。判断 5 的论证（可审计 + 授权有界）本身成立，但红线文本没有为预授权留例外。该档默认关闭不影响当下实现，但红线是文档的宪法，建议补"经版本化预授权策略、每次运行留 plan+diff 者除外"。
