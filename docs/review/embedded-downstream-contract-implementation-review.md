# 嵌入式下游契约候选实现复核

- 日期：2026-11-22
- 复核对象：当前 `codex/safer-agent-memory-setup` 工作树中的嵌入式下游契约候选、`event.restore_body/v1` 特性接入及迁移补标。
- 复核方式：本机静态复核与已记录的自动化证据；本机复核本身不构成发布批准，也不是 Windows/SpaceTeam/正式历史发行物验收。维护者已于 2026-11-22 单独接受当前 `1.0.0` 候选。

## 结论

本轮复核范围内**未发现阻断实现候选的问题**。特性登记、依赖写入、格式迁移和候选机读声明的顺序相符；缺失第二个真实特性的跨特性并发测试及所有 T09 外部验收仍然限制完成状态。本记录可供维护者审定，不替代其裁决。

## 范围与核查

### 正确性

- `Store::register_required_features` 取得独占门闩后，调用要求 `ExclusiveBarrierGuard` 的内部登记入口；它在锁内重读最新磁盘配置，求并集并原子写回。空集合无副作用；不支持或非法标识在配置变化前拒绝。
- `ops::restore_body` 获取独占门闩，复核当前兼容状态，在同一门闩内先登记 `event.restore_body/v1`，再发布正文记录与事件。没有共享锁升级，也没有离开许可后继续写入的窗口。
- 格式 1 迁移先验证事件日志、链和店状态，再用同一份已校验事件快照提取 `restore_body` 依赖；原子切换时写入排序特性清单。已存在的恢复事件不会因迁移丢标记，没有使用该能力的店仍为空清单。
- 自动化回归覆盖成功登记、迁移补标、旧功能拒绝、多进程同特性幂等登记，以及登记后、记录发布后、事件追加后三个真实进程终止点。终止后允许的状态分别为保守标记、可回填记录、完整事件状态。
- 新增跨进程许可交错回归：A 在 `add` 原子发布记录但尚未追加事件时持有共享许可暂停，B 的正文恢复调用已进入但不能登记特性或写入，直至 A 完成并释放许可；最终 Create 与 RestoreBody 事件有序，配置和正文一致。

### 可读性与架构

- 特性语义留在 `ops::restore_body`，店能力集合和格式迁移由 `Store` 管理。内部组合登记入口要求独占门闩凭证，减少调用者误用。
- 正文恢复本身使用独占门闩，可能降低它与其他普通写之间的并行度；这是该整店特性登记必须等待所有在途写完成的直接成本。普通记录写路径仍使用共享门闩。
- 迁移依赖扫描复用迁移预检读取的事件快照，没有增加第二次全量日志解析。

### 安全与数据边界

- 特性标识继续经过格式校验和本构建支持集合校验；迁移只从已解析事件枚举中识别受支持的 `restore_body` 操作，不信任任意配置输入。
- 特性先登记、后写数据。进程在登记后中断会留下保守标记，不会出现新数据已发布但缺少必需特性的状态。
- 本复核未覆盖任意外部程序绕开 SpaceMemory 受管 API 直接编辑店目录；这仍由部署责任和协议边界管理。

### 契约与验证一致性

- API 候选列出正文恢复签名、来源类型和结果；编译示例锁定 `restore_body`、支持特性查询、`AddArgs`、`OpenMode`、错误与迁移状态的调用形状。
- 能力 JSON 声明产品候选版本 `1.0.0`、基础格式及 `event.restore_body/v1`。测试逐项比较该 JSON 与运行时 manifest，并显式固定此特性，避免两边同时误变为空。
- MCP 工具名称通过对照测试与运行时工具表比较；候选共店列表保持空，不声明无证据的组合。
- 变更记录注明该特性是按需能力、迁移如何补标，以及候选仍未发布。

## T04 方案 2 裁决附记（2026-11-22）

维护者选择保持当前 `1.0.0` 特性范围，并把“两个不同真实特性的并发并集”限定为至少存在两项真实支持特性时的验收。当前仅有 `event.restore_body/v1`，因此此不同特性子矩阵对本候选为 N/A；已有同一真实特性的跨进程并发登记幂等测试及依赖写等待共享写许可交错测试仍为当前验收证据。此项范围裁决允许按当前真实能力关闭 T04，不声称 F/G 不同特性矩阵已经运行或通过。

未来新增第二项真实特性时，F/G 并发登记与依赖写、最终排序并集、两类数据/事件可解释性及重试幂等立即成为必需验收；不得以测试专用的虚构特性替代。理由是测试应反映实际产品语义，且当前 1.0.0 不应为缺少第二能力而扩大公开能力面。护栏：第二项能力合入前补齐真实多进程测试，并复核能力 manifest、迁移补标、兼容性声明及全工作区测试。该裁决不改变 T09 外部验收或发布授权状态。

## T09 SpaceTeam 发布后验收裁决附记（2026-11-22）

维护者确认下游 SpaceTeam 的 POC、升级和回退验收以前提“已有可安装/可集成的正式版本”开展；将它列为首发前置条件会让下游针对未发布候选做产品级验收，不符合真实发布流程。因此它从首发硬门槛移至发布后：SpaceTeam 应固定下游 revision，针对正式 `1.0.0` 资产记录编译、适用入口调用、升级/回退结果与店快照摘要。下游验收未完成时不得声明 SpaceTeam 已通过或将其共店组合记入 `validated_coexistence`。Windows 等平台证据仅在对应平台被声明支持时成为该平台发布门槛。此调整仅移动 SpaceTeam 验收时点，不降低候选的本地正确性或兼容声明标准。

## T09 真实部署店发布后验收裁决附记（2026-11-22）

维护者指出当前是开发环境，并无可提供的真实部署店；要求先拿生产店数据才能发布，既与任务环境不符，也会把不可能的输入伪装成开发门槛。故首发前的迁移安全证据采用本机隔离合成店、历史源码程序、可控故障注入、完整备份恢复与进程中断测试；这些证明可复现机制行为，但明确不宣称完成真实部署验收。真实店迁移/回退移至发布后运维阶段，在实际部署环境存在、数据责任人授权样本后，以正式版本演练并记录输入/输出摘要、迁移及恢复结果。该项不阻止首发。此裁决只调整验收时点，不放宽对迁移行为、备份恢复机制或证据真实性的要求。

## T08 扩展性复核附记（2026-11-22）

对 API 签名清单逐类型复核时发现，变更记录承诺的“可扩展结果结构”未完整落到 `RestoredBody`，而公开输入枚举 `RestoreSource` 允许下游穷尽匹配。补充消费者探针后，基线确认直接构造/穷尽匹配可编译；将 `RestoredBody` 与 `RestoreSource` 标为 `non_exhaustive` 后，探针按预期失败（E0639/E0004）；调整为读取字段并用 `..` 解构、匹配时留通配分支后恢复通过。候选 API 文档和变更记录现已说明这些扩展边界。修复后重新运行全工作区测试、all-targets 开发检查及 release 库/二进制/示例检查均通过，未发现本机候选新增阻断。维护者已接受当前 `1.0.0` 候选；全部外部验收限制仍然有效。
