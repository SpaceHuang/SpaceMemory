# 二进制内容承载技术方案评审报告

- 评审对象：`docs/develop/binary-content-design.md` v0.1（2026-11-09，待评审）
- 评审日期：2026-11-09
- 评审标尺：`agent-memory-requirements.md` v1.4（R10.2、R11.1–R11.6、验收 1–7）、`agent-memory-design.md` v1.2 红线、`envelope-format.md` v1
- 评审方式：文档读审＋对现有写路径、事件回填、索引 schema/查询和 git 提交批次的定点代码核验；未改实现，未运行写入型端到端场景

## 评审结论（TL;DR）

**不予通过：3 项阻断。** 两前端字节取回、非文本预览降级、检索正文域门槛和独立内容恢复命令的方向均可成立，但以下三处使方案按现文无法兑现验收：

1. **B1**：非文本正文素材置 `NULL` 与现有索引的非空 schema、行结构和读取代码直接冲突，所写迁移不能消除冲突；
2. **B2**：`history` 以“最后登记摘要”为可信锚，损坏经回填后该锚会变为损坏字节，恢复可静默地把损坏内容再次当作可信来源；
3. **B3**：`.gitattributes` 未纳入既定的按路径提交批次，且冲突配置只告警不阻断，跨机克隆的字节直通承诺没有闭合。

三项分别阻断 R11.4/R10.3、R11.6、R11.1/R11.2 的对应实施与验收；修复前不建议批准 BD2–BD5 所涉实施面。

## 阻断项

### B1 `NULL` 素材语义与索引 schema/读取契约冲突，迁移步骤无效

**位置**：设计 §3.4“非文本正文的粗筛素材列置 NULL”、§5 新增面第 8 条、§7“索引”行。

**代码事实**：

- `crates/mem-index/src/sqlite.rs:154-158` 将 `body_text`、`body_folded` 都声明为 `TEXT NOT NULL DEFAULT ''`；
- `crates/mem-index/src/sqlite.rs:31` 的 `IndexRow.body_folded` 是 `String`，`sqlite.rs:501` 与 `crates/mem-index/src/fts.rs:74` 均按非空 `String` 读取该列；
- 现有迁移只在建表时保留上述定义，并执行 `ALTER TABLE ... ADD COLUMN ... NOT NULL`（`sqlite.rs:140-183`）。`CREATE TABLE IF NOT EXISTS` 不会修改旧表，补列也不会解除既有列的 `NOT NULL`；即使删除索引，按当前 schema 重建仍会得到同一非空约束。

**反例与影响**：

1. 按设计把任一非文本记录的 `body_folded` 写成 `NULL`，`INSERT`/`UPDATE` 立即违反 `NOT NULL`，索引物化失败，验收 5 的快路径用例无法完成；
2. 若只改 schema 而不同步修改行结构与所有查询，任何返回该行的 `list`/`brief`/`find` 都可能因 NULL→String 解码失败，反而破坏 R11.6 的“读取不崩溃”；
3. §7 所写“首次写例程重建索引＋物化代际递增”既不是 schema 迁移算法，也不能作为 NULL 契约已经一致的完成标记。

**为什么是阻断**：同一新增面在 SQL 层、Rust 行类型层和迁移层有三种互不兼容的隐含实现，按现文落地会直接使物化或读取失败，不是测试阶段再补细节即可消化的问题。

**修复门槛**：

- 二选一并写全契约：
  - 保持 `NOT NULL`，非文本正文用空字符串表示“无正文检索素材”（LIKE 不参与命中，且无需可空迁移）；或
  - 正式改为可空列：给出 SQLite 表重建迁移、`Option<String>` 行契约、全部查询适配和旧索引识别/重建规则；
- 验收 5 除直读/快路径命中集合外，还须断言含非文本记录时索引物化成功，且 `brief`/`list`/`find` 快路径读取不报错；迁移完成标记须能区分旧 schema 与新 schema，而非只看 epoch 递增。

### B2 `history` 的最后事件锚会被回填推进到损坏字节，可能静默“恢复为损坏”

**位置**：设计 §3.6 的 `history` 来源定义、BD4 的“机制内校验来源”、§8 验收 6、§13“history 锚点”。

**机制事实**：状态覆盖回填会把当前文件摘要登记为新事件的 `new_digest`。`crates/mem-core/src/event.rs:508-520` 对现存漂移记录追加 `Op::Backfill`，其 `new_digest = cur.digest`；深档审计则始终比较磁盘与该记录最后事件的摘要（`crates/mem-core/src/ops.rs:1126-1145`）。因此，“最后登记摘要”不恒等于“损坏前可信摘要”。

**反例**：

1. 记录原全文为 A，外部翻转正文一个字节后为 B；
2. 在任何一次 `reconcile` 或其他触发回填的写例程后，最后事件变为 `backfill(A→B)`，若同批提交成功，git 历史也存在 B；
3. 按现文执行 `restore-body history`：锚取 B 的摘要，自新至旧首先命中 B，取回的“来源正文”仍是损坏正文；
4. 恢复把 B 写成 B 的新版本，随后“正文摘要＝来源摘要”和“深档不再漂移”都为真，但内容并未治愈。若 B 未提交，则扫描不到锚，已知良好的 A 也不会被选择。

同样地，损坏后若用户以当前令牌做过一次合法载荷更新，正文按既有更新纪律保持不变，最后普通事件也会登记 B；仅跳过 `kind=backfill` 仍不能修复该问题。

**验收缺口**：§8 只覆盖“翻转 → 立即 deep → history 恢复”的理想顺序，没有覆盖合法且常见的“翻转 → reconcile/后续写入 → 恢复”。后一路径下，现有断言会被“恢复为 B”伪通过。

**为什么是阻断**：BD4 用独立命令消除静默二次损坏，但当前 `history` 又引入“来源被错认、接口却报告成功”的静默恢复失败，直接落空 R11.6 的“可治愈”。

**修复门槛**：

- 不得把任意时刻的“最后事件摘要”直接定义为可信来源；明确可信摘要的来源、确认方式及其在回填后的可用性；
- 至少规定：当前摘要已与最后事件一致（漂移已收敛）时，自动 `history` 不得声称能推出损坏前版本，应响亮拒绝并要求调用方显式选择可信 git 版本或备份；若保留自动锚定，应使用漂移发现时保存并展示的“磁盘摘要≠登记摘要”证据，而非恢复执行时重新取已推进的最后事件；
- 明确“机制校验字节完整复制”与“调用方确认来源可信”两件事，不能把后者由前者替代；
- 验收 6 增加“损坏→回填→尝试 history”的反例：不得把损坏来源静默报告为治愈；同时保留立即恢复、显式 git 版本和备份来源三条正向路径。

### B3 `.gitattributes` 只落工作区、不进提交批次，跨机字节直通不成立

**位置**：设计 §3.1 末、BD5、§5 新增面第 10 条、§7 `.gitattributes` 行。

**代码事实**：既有写路径的提交批次由 `commit_same_batch` 统一构造，只包含调用方给出的记录路径和 `events.jsonl`（`crates/mem-core/src/ops.rs:723-727`）；commit-pending 也保存同一批次（`ops.rs:740-743`）。设计只规定 init/写例程创建 `.gitattributes`，没有把该文件加入提交批次、pending 重试或完成标记。`mem init` 当前的 `git add -A`（`crates/mem/src/commands/mod.rs:390-395`）也只暂存，不等同于把文件收入提交；后续 path-scoped commit 不会顺带提交未列出的 `.gitattributes`。

**反例与影响**：

1. 源机 init 或首次写例程在本地创建 `.gitattributes`，随后记录与事件按既有批次提交，`.gitattributes` 仍是未提交/仅暂存文件；
2. 用户同步该 git 仓库并在另一台启用 `core.autocrlf=true` 的机器克隆，克隆结果中没有该规则，检出仍可转换记录字节；
3. 目标机随后才由写例程补种规则，无法撤销克隆时已经发生的字节变化。深档漂移、修订令牌跨机失效正是 BD5 要消除的结果。

此外，BD5 对“已存在且内容不同”的规则仅“响亮告警不覆盖”。若现有内容启用了 text 转换，机制仍继续写入，等于在明知字节直通未建立时照常提交，与“全店禁行尾转换”的强承诺冲突。

**为什么是阻断**：验收 1 的直接目录复制不经过 git，无法覆盖该失败；而设计明确把 git 克隆列为必须保真的多机通道。规则未进入历史，跨机承诺在最基本的同步路径上即失效。

**修复门槛**：

- 规定 `.gitattributes` 的创建/变更与记录、事件进入同一提交及 commit-pending 批次；完成标记至少包括“规则已存在于供同步的提交树中”，不能只看本机文件存在；
- 对冲突规则明确二选一：建立并核验有效 `-text` 后才允许受管写入，或把承诺降级并重新取得需求裁决；只告警后继续写不满足当前强承诺；
- 增加真实 git 子进程端到端用例：源机提交非法 UTF-8＋含 CRLF 的正文，确认 `.gitattributes` 已在提交树中；在强制 `core.autocrlf=true` 的新克隆中逐字节核对记录，并核对事件最后摘要与磁盘一致。另补既有冲突 `.gitattributes` 的行为测试。

## 非阻断修正（定稿时一处措辞）

BD4“依据强度”仍写“机制写入的字节随写路径同批提交进 git，锚摘要**必可**在历史中找到”。这比既有契约多走了一步：同批提交可能进入 commit-pending，且 `.git` 可合法缺席，因此机制写入登记不保证当时已有可读取的 git 版本。建议改为“若对应提交已存在，锚摘要可在历史中匹配；无 `.git`、提交仍 pending 或扫描无匹配时响亮失败，并引导显式 `git:<版本>`／`file:` 来源”。§3.6 可补同一句无匹配处置。

该项只影响失败分支的表述完备性，不会恢复静默错选来源：扫描无匹配天然不能返回伪来源，故不重新构成阻断。
