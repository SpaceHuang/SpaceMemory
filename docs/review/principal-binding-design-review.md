# 写路径归属绑定技术方案评审报告

- 评审对象：`docs/develop/principal-binding-design.md` v0.1（2026-11-19，待评审）
- 评审日期：2026-11-19
- 评审标尺：`agent-memory-requirements.md` v1.4（R2.4、R3.4、R6、R7）、`agent-memory-design.md` v1.3（红线 12/15）、`envelope-format.md` 公开规范
- 评审方式：文档读审＋对 `ops::add`、会话台账、principal 删除与 `.gitattributes` 写前核验的定点源码核验；未改设计或实现，未运行测试

## 评审结论（TL;DR）

**不予通过：3 项阻断。** “显式参数 > 会话台账 > 响亮拒绝”、核心库单源、显式胜出并告警及 principal 类型豁免的方向均可成立，但现文尚不能作为唯一、完整的实施契约：

1. **B1**：把非 principal 记录的 `principal=null` 定为非法，却声明“无数据格式变更”且未安排公开信封规范修订；受管创建、外部写入和既有记录因此没有一致语义；
2. **B2**：现有 `add` 会在归属校验前补写 `.gitattributes`，而方案的“磁盘零变化”验收只数记录与事件，无法发现该反例；
3. **B3**：台账继承只援引建台账时的存在性校验，未明确要求创建当次复核；principal 在建台账后被删除时，可按现文写出悬空归属。

三项关闭前，不批准决策①–⑤及方案整体进入实施。

## 阻断项

### B1 `null` 合法域已经改变，公开规范与外部写入语义却未收口

**位置**：方案 §0.1 决策④、§2.1 豁免、§2.5 信封注释同步、§5“零新增……无数据格式变更”、§7 收编清单。

**规范与代码事实**：

- `docs/specs/envelope-format.md:5` 声明该文件是存储格式的单一事实源；其 §2.2（85 行）目前允许所有类型的 `principal` 为 `string | null`，只限制非 null 值必须指向现存 principal；
- 当前解析器同样不区分类型地接受 null（`crates/mem-core/src/envelope.rs:63-66`）；
- 方案把规则表述为“空 = **仅 principal 类型合法**”，这不只是创建入口的默认值变化，而是字段合法取值域的变化。字段集合不变不等于数据格式语义不变；
- 方案 §7 只安排主设计文档收编，没有安排上述公开规范同步，也没有定义外部直写或既有非 principal 空归属记录的读取、审计和修复语义。

**反例与影响**：用户按 R2.4 直接放入一条 `type=memory, principal=null` 的记录。按新方案的“仅 principal 类型合法”，它是坏记录，应被识别并存在接口修复路径；按现行公开规范和解析器，它仍是合法记录。若实施只改 `ops::add`，受管创建会拒绝、外部记录却照常无告警读取，且方案 F8 又说明更新/恢复不能补归属。两种行为都能声称符合现文，公开格式与机制不再同源。

**修复门槛**：

- 二选一并写全边界：
  - 若只收紧**受管创建**，把“仅 principal 类型合法”改为“仅 principal 类型可在受管创建时省略”；明确外部/存量非 principal 空归属仍按原规范可读，不再宣称其全局非法；或
  - 若确要改变全库合法域，将 `envelope-format.md` 修订纳入 §5/§7，并定义外部与存量记录的读取告警、verify 判定及经接口补归属的修复路径；
- 增加对应验收：手工放入非 principal 空归属记录后，read/verify/fix 的行为与所选契约一致；principal 空归属仍合法；
- 删除或修正“无数据格式变更”，使新增面清单与实际裁决一致。

### B2 “拒绝后磁盘零变化”与现有写前补种冲突，验收断言覆盖不足

**位置**：方案 §2.1（95 行）强断言、§4.1 第一行机制与验证点、§4.2 核心层拒绝测试。

**代码事实**：`ops::add` 当前先执行 `check_writable`，随后在任何载荷/归属校验之前调用 `gitattrs::ensure_for_write`（`crates/mem-core/src/ops.rs:315-322`）。对有 `.git` 而缺 `.gitattributes` 的店，该调用会直接写入默认规则文件（`crates/mem-core/src/gitattrs.rs:46-59`）。

**反例**：在有 `.git`、尚无 `.gitattributes` 的店中，以非 principal 类型调用 add，且既不给显式归属也不给台账。若按现有顺序接入解析链，调用最终因缺归属失败，但 `.gitattributes` 已被创建。方案 §4.1 所列“记录数与事件日志行数均不增”仍会通过，因而不能以该测试声称“磁盘零变化”。

**为什么是阻断**：这是方案自设的强承诺，且现有写路径存在确定可达的反例；不是实现自由度或措辞瑕疵。验证点若只覆盖记录与事件，会把明确违反承诺的实现判为合格。

**修复门槛**：

- 明确归属解析及“无归属拒绝”发生在 `ensure_for_write`、任何锁文件创建和其他写盘之前；保留合法写入时既有的 `.gitattributes` 核验与同批提交纪律；
- 将验收改为店级文件树前后一致，至少必须覆盖“有 `.git`、缺 `.gitattributes`”反例并断言该文件未被创建；只比较记录数和事件行数不满足通过条件；
- CLI/MCP 拒绝用例也应断言该前置反例下无文件变化，而不只检查错误文案。

### B3 台账身份只凭建账时校验，可继承到已删除的 principal

**位置**：方案 §1.2 F6、§2.1 解析链第 1/2 步、§4.1“台账身份被正确继承”、§4.2 验收面。

**问题与证据**：第 1 步明确要求显式归属“按现状校验存在性后使用”；第 2 步对台账归属只说“建立台账时已校验过存在性”，没有要求 add 当次复核。两者不能互换：台账可长期存活，而 principal 记录可在此期间被删除。

该反例在现有机制中可达。principal 是独立信封字段，不在 `envelope.refs` 中；删除路径的依赖检查只调用 `reverse_refs` 检查引用集合（`crates/mem-core/src/ops.rs:665-684`），不会因为台账仍保存该 principal 而阻止删除。因此“先建台账 X → 删除 X → 不带显式归属 add”是合法的操作序列。

**影响**：若实现按第 2 步直接使用台账中的旧 ID，新记录的归属会指向 attic 中或已不存在的身份，违反红线 12 的“存在性强制”及方案自身的归属可信目标。另一个实现若在继承后调用现有 `validate_payload_and_refs` 则会拒绝；现文因此允许两种结果相反的实现。

**修复门槛**：

- 规定显式与台账两种来源在解析后走**同一个 add 当次存在性校验**，目标必须是当前 `records/` 中 `type=principal` 的记录；建台账时的校验不能替代创建时校验；
- 在 §4.1/§4.2 增加“建台账 X → 删除 X → 继承创建”的反例：必须响亮拒绝且磁盘零变化；恢复 X 后再创建可成功；
- 同步明确缺失或损坏台账不得被当成合法身份来源；若显式归属存在时仍允许创建，应保持显式优先规则，但不能借台账旧值绕过上述校验。

## 非阻断修正

1. **F5 的“零新增读取”不准确**：前端 `make_ctx`/`write_ctx` 虽已读台账，但 `WriteContext` 只携带 `session_id` 和格式化后的 `by` 字符串（`crates/mem-core/src/ops.rs:47-55`），核心库要取得结构化 principal 仍需再次 `session::get`，或新增上下文字段。方案 §2.2 已允许核心读台账，删除“零新增读取”即可，不影响单源方向。
2. **决策⑤的“调用方零破坏”应改为“签名零变化”**：无显式归属且无台账的既有调用会从成功变为拒绝，方案 §0.3 已如实承认该行为破坏；决策条目不应再称零破坏。

**本轮请求批准**：无。三项阻断修复前，不批准方案整体进入实施。

## 本轮阻断

### B4 锁外一次性校验无法防御并发删除，和“悬空归属被防御”承诺冲突

**位置**：v0.2 §2.1“统一当次校验”与“执行位置”（96–102 行）、§4.1“悬空归属被防御”（250 行）、§4.2 悬空反例（260 行）。

**代码与协议事实**：

- 当前 `add` 的 principal 存在性检查发生在 `validate_payload_and_refs` 中（`crates/mem-core/src/ops.rs:298-310`），之后才开始获取共享门闩与**新记录**的锁（`ops.rs:346-347`）；整个创建过程不持有被引用 principal 的锁；
- v0.2 明确要求把这项校验进一步固定在 `.gitattributes` 核验和**任何锁文件创建之前**，但没有规定后续复核；
- 删除 principal 走的是该 principal 自身的记录锁（`ops.rs:685-695`）。共享门闩不会互斥两个普通写，而新记录锁也不能与 principal 删除锁建立串行关系；
- 主设计对 x-ref/DAG 的既有裁决已经承认“锁外尽力 + 锁内复核”的必要性（主设计 v1.2 修订行 M3）。v0.2 对 principal 只保留前一半，且给出了全称防御断言。

**并发反例**：

1. 台账登记身份 X，add 不带显式归属，从台账解析出 X；
2. add 在锁外扫描确认 X 当前位于 `records/`，随后暂停；
3. 另一进程删除 X，将其移入 attic 并完成事件登记；
4. add 恢复，获取新记录锁并创建记录，信封仍写 `principal=X`。

最终记录创建成功但归属已悬空。§4.2 的“建账 X → 删除 X → 继承创建”只在第一次扫描之前完成删除，因此会响亮拒绝，无法发现上述交错。

**为什么是阻断**：方案新增的是跨记录归属引用，并把“悬空归属被防御”列为强断言；现定执行顺序却结构性允许并发删除穿透，触及 R3.4 的并发引用完整性。不能用串行测试把该断言判为已验证，也不能把它留成实现者自行决定是否补锁内复核的自由度。

**修复门槛**：

- 采用两阶段或等价协议：锁外预检仍可用于确定性的无归属/已失效归属拒绝，以满足零写盘；预检成功后、新记录可见之前，必须与 principal 删除建立同步（例如按全库统一锁序持有 principal 记录锁），并在锁内重新确认其仍位于 `records/`。不能只重复一次无锁扫描；
- 写清新增锁与既有门闩/新记录锁/序列锁的先后顺序，以及锁内复核失败时如何满足或调整“全店文件树零变化”承诺；两项承诺若需重新取舍，必须作为裁决项显式提交，不能静默缩小；
- 增加可控暂停的并发验收：add 完成锁外预检后暂停 → 删除 X 完成 → 恢复 add；不得创建带悬空归属的记录。保留现有串行删除/恢复测试，并验证合法创建与 principal 删除不会因新锁序死锁。

## 非阻断措辞

§2.5 已将外部空归属记录定义为“合法、可读、无告警、校验不报坏”，同句末尾却又说其治理由“坏写入的识别隔离机制”承载，二者语义不一致。建议删除后一表述，直接说明这类记录是合法但未归属、按 principal 过滤自然不命中即可；不影响当前接口契约的唯一性。

## 本轮阻断

### B5 创建先完成后，正常删除流程并不检查归属依赖，仍会留下悬空 principal

**位置**：v0.3 §2.1 锁序段（105 行）、§4.1“悬空归属被防御”（280 行）、§4.2 并发反例与死锁守护（291–292 行）。

**问题与代码事实**：§2.1 称两种写串行后“要么删除先完成……要么创建先完成（删除面对的是带归属的新记录，按其正常流程决策）”。这隐含假设删除的正常流程会识别并处置新记录的归属依赖，但当前机制没有这一步：

- 删除的依赖集合只来自 `reverse_refs`（`crates/mem-core/src/ops.rs:665-684`）；
- `reverse_refs` 只遍历 `envelope.refs`，不检查 `envelope.principal`（`ops.rs:785-795`）；
- 因而一条记录的 `principal=X` 不会阻止或警示删除 X。

此外，删除目前在获取 X 的记录锁**之前**计算依赖（665–668 行），686 行才锁 X。即使只把 principal 纳入锁外 `reverse_refs`，也仍有“删除预检后、add 创建归属记录、删除再取锁”的同类窗口；必须在 principal 锁内复核依赖。

**反例**：add 持有新记录锁与 X 的 principal 锁，完成记录创建后释放；delete X 随后取得 X 的锁。按现有正常流程，依赖清单为空，X 被移入 attic，新记录保留 `principal=X`。这正是 §2.1 所说“创建先完成”的合法分支，却不是“按其正常流程决策”即可安全处理的分支。

**为什么是阻断**：B4 的目标是受管并发下结构性排除悬空归属，而 v0.3 只排除了删除先获胜的一半；创建先获胜仍确定产生同一终态。当前死锁守护只要求操作在超时内完成，没有断言该分支的引用完整性。

**修复门槛**：

- 明确 principal 删除对归属依赖的处置：至少把记录的 `envelope.principal` 纳入依赖集合，并按既有删除语义选择阻止，或 force 时显式告警；台账引用是否也阻止删除可另行裁决，但不能影响记录归属的完整性；
- 将归属依赖检查置于被删 principal 的记录锁内，或在锁内重新复核，确保与 add 的锁内创建顺序形成闭环；
- 并发验收同时覆盖两个胜负分支：删除先完成→add 拒绝；add 先完成→delete 按选定语义阻止或显式告警，不得无声留下悬空归属。串行“创建记录→删除其 principal”也须有独立回归。

### B6 “锁内拒绝终态逐字节一致”未承接记录锁的持有者重写与清理竞态

**位置**：v0.3 §2.1 第二阶段与分层强断言（101、111–116 行）、决策⑥、§4.1 净零验证点（278–280 行）、§5 新增面清单。

**代码事实**：

- 当前 `RecordLockGuard::drop` 只释放平台锁和进程内槽位，不删除锁文件（`crates/mem-core/src/lock.rs:188-195`）；
- 每次成功取得记录锁都会调用 `write_owner`，把含当前时间戳的持有者 JSON 覆盖写入锁文件（`lock.rs:219-222、269-274`），无论文件是否由本次操作新建；
- 锁文件是独立的协调原语，既有协议允许记录消失后锁文件继续存在。跨进程等待者不受本进程“是否自建”的知识约束，简单在释放时删除锁文件还需要额外的安全清理协议。

**反例**：B4 测试先创建 principal X，因此 X 的规范记录锁文件可以已经存在。并发删除和 add 复核随后先后取得该锁，持有者时间戳被重写。即使 add 最后复核失败、没有记录或事件，且把本次新建的新记录锁文件删除，预先存在的 `X.lock` 内容也已改变；它不属于“自建锁文件随释放清理”的范围，全店前后逐字节快照仍不一致。

若改为释放时删除所有本次触及的锁文件，则会破坏既有锁文件存续语义，并引入“等待者仍持有旧文件句柄、另一进程经新路径创建新文件”的互斥裂口；方案没有给出可证明安全的清理协议。

**为什么是阻断**：决策⑥把“终态净零＝前后快照逐字节一致”作为批准项和强制验收，但其指定机制只处理自建文件，没有处理既有锁文件的内容变化。按现文实施会出现测试必败，或为通过测试而引入不安全的锁删除行为。

**修复门槛**：

- 重新界定净零的对象：建议区分**真相层净零**（无新记录、无事件、无 `.gitattributes`/会话等状态变化）与运行时锁文件；锁文件内容及存在性按公开规范本就无真相语义，可显式排除在逐字节快照之外；
- 若仍坚持全店逐字节一致，则必须给出与跨进程等待者、陈旧锁判定兼容的完整锁清理/内容恢复协议，并证明不会制造两个锁实体；不能以 Drop 时直接删除代替设计；
- 同步修改 §2.1、决策⑥、§4.1/§4.2 与 §5，并用“principal 锁文件预先存在”的并发反例验证最终所选承诺。

### B7 `force` 删除后的 principal 断链未进入 verify 审计，新增验收无实现来源

**位置**：v0.4 决策⑦后果与依据（287、292 行）、§4.1“删除侧归属依赖处置”（307 行）、§4.2 删除侧回归（319 行）、§5 新增面清单（329–343 行）。

**代码事实**：

- 当前删除告警声称断链由 verify/agenda 报告，但其依赖来源 `reverse_refs` 只遍历 `envelope.refs`（`crates/mem-core/src/ops.rs:785-795`）；

**为什么是阻断**：方案用“verify 报断链注记”承接 force 后的显式可发现性，并将其列为强制验收；但新增面清单没有对应交付面，现有审计也不能自然覆盖该字段。这不是文案问题，而是批准范围内的验收缺少实现路径。

**修复门槛**：

- 在 §5 和决策⑦明确新增 principal 完整性审计：verify 对非空 `envelope.principal` 检查目标是否仍为 `records/` 中现存的 principal 记录；指向 attic/缺失目标时报告来源记录、目标身份及修复入口。若决策保留 agenda 报告，也须同步登记其扫描面；

## 全量连带核验

1. **创建与删除双分支闭合**：删除先完成时 add 锁内复核拒绝；创建先完成时 delete 在 principal 锁内看到归属依赖并默认阻止，force 越过显式告警且由 verify 承接。
2. **净零断言可执行**：锁外拒绝保持全店逐字节一致；锁内拒绝只承诺真相层净零，运行时锁文件豁免，不再要求危险的锁文件删除。
3. **空归属语义未回退**：受管创建仅 principal 可省略；外部/存量非 principal 空归属仍合法，verify 基线明确不得误报。
4. **格式承诺未破坏**：归属审计直接读取既有 `envelope.principal`，不向 refs 镜像，不新增信封字段、schema 或公开规范变更。
5. **验收来源完整**：§4 的继承、拒绝、显式告警、豁免、串行/并发悬空、force 删除、verify 三组回归与死锁守护均能在 §5 找到对应交付面。
