## B1 库并未提供所述原子批次，C3 的缺口归因因此错误

**位置**：需求第 15 行“进程内事务能力／事务性批量写”、第 38 行“经库 API 落为一个原子提交”，第 59 行 C3.2，以及第 51 行 C1.5 的“已提交”。

**核验事实**：

- `commit_batch` 接收已经写出的记录路径和 `CommitSink`，把这些路径与事件日志交给 Git；不接收待执行的记录操作，也不负责把这些操作一起生效。未配置提交汇时直接成功返回。Git 失败时登记待重试批次，**不回滚真相层**。下钻：`crates/mem-core/src/ops.rs:1209–1254`。
- `add` 在调用该函数前，已创建记录并追加事件；记录并非等到批次提交才可见。下钻：`crates/mem-core/src/ops.rs:549–580`。
- 既有设计明确：Git 只提供历史，不提供工作目录的跨记录原子可见性；多记录维护中途崩溃采用可检出的执行状态与显式续跑／回滚。下钻：主设计 D4、D17；`crates/mem-git/src/lib.rs:3–11`。
- 已有测试刻意检查“Git 提交失败后记录与事件仍存在，并登记待重试文件”，不是事务回滚。下钻：`crates/mem-core/tests/ops.rs:1617–1648`（本轮只读测试源码，未执行）。

**反例与影响**：下游先写事件记录、再写边和投影，即使最后把相关路径收进一个 Git 提交，其他进程仍可在中途读到部分成果；最后一次写失败或进程退出，也不能由 `commit_batch` 撤销先前成果。因此不能以该 API 证明“库形态已具备原子批次、只有 MCP 缺等价入口”。按现文只增加一层工具包装，会通过“工具已新增”的验收，却仍不满足“多条记录与边原子落盘”的承诺。

**修复门槛**：

1. 将现状改为“单记录受管写与可汇总的 Git 历史提交”；若下游另有恢复链，应明确其提供者和保证边界，不能归因于 mem-core 的 `commit_batch`。若主张另有库事务入口，须提供具体公开签名及失败／并发读证据。
2. C3 显式区分至少两个选项：保持当前逐笔写、仅支持历史提交汇总；或新增跨记录事务能力。前者仍允许读到部分批次，后者是库机制与两个前端共同新增的能力，不能只登记为 MCP 缺口。
3. 若选择跨记录事务，需求至少明确：一个成员 CAS／校验失败时其他成员是否全部不生效；进程在批次中途退出后可观察什么；其他进程能否读到部分批次。具体机制留给设计，不在需求中指定锁或日志形态。
4. C1.5 定义“已提交”的可观察边界，区分受管写成功与 Git 入史；覆盖无 Git、提交滞后及失败路径。§5 的 C3 验收须检查所选行为，不能只查工具是否存在。

**建议**：先如实收口现状，再把是否新增事务能力交维护者裁决；裁决前不把原子批次列作已具备能力。

## B2 C1.1 的整库串行等价并非既有保证，引用与全局序边界也未收口

**位置**：第 47 行 C1.1“经公开 API 并发读写……结果等价于某种串行执行／不产生断链”、第 49 行 C1.3“事件号与记录版本链（CAS 令牌）……全局唯一”，以及 §3 将这些性质作为既有实现事实的表述。

**核验事实**：

- 既有需求保证受管单次写的原子性、同记录更新冲突可见、创建唯一性；引用完整性允许阻止、级联清理或**显式报告**。这不等于所有公开读写操作具有整库串行等价。下钻：需求基线 R3.1–R3.4。
- 多记录维护的屏障只约束写者，读路径不受屏障影响；公开的 `scan_all` 逐文件读取，没有为整次扫描取得共同快照。下钻：主设计 D17；`crates/mem-core/src/ops.rs:86–106`。
- 公开 `delete_record(..., force=true)` 可以成功产生悬空引用／归属并返回警告；它仍是经公开 API 的受管操作。下钻：`crates/mem-core/src/ops.rs:1008–1041`；MCP 同样公开 `force`（`crates/mem-mcp/src/tools.rs:73–75`）。
- 记录版本从 1 开始、每次机制写递增；CAS 令牌表示该记录的版本与完整文件摘要。全库序号则由事件日志独立分配。令牌没有跨记录先后比较语义。下钻：`docs/specs/envelope-format.md:84,119,170`；`crates/mem-core/src/token.rs:18–28,62–76`。

**交错反例**：一次公开扫描先读到 A 的旧值；另一进程依次成功更新 A、B；扫描随后读到 B 的新值。扫描返回“A 旧、B 新”，但真实状态只经历过“A 旧／B 旧 → A 新／B 旧 → A 新／B 新”。若把整个扫描当作一次操作，就找不到与它等价的串行位置。这个例子说明“每条记录读取有效”和“整次查询来自同一快照”是两种不同承诺，不是证明当前实现违反既有需求。

此外，即使完全没有并发，显式强制删除也能留下已报告的断链。因而 C1.1 的无例外“不产生断链”已经与既有合法行为冲突。把记录令牌一并称为“全局序”，还会让消费者把单记录版本误用为跨记录水位。

**修复门槛**：

1. 决策并明示 C1 的操作边界：单记录写、多记录维护、一次扫描／查询、调用方连续多次调用，哪些具有何种一致性。不能仅以“并发安全”包住全部公开 API。
2. 若本期只契约化既有能力，去掉整库串行等价的全称表述；按受管写原子性、CAS 冲突、创建唯一性、引用的阻止／清理／显式报告分别声明，并保留 `force` 等例外。若确要新增整库串行等价或查询快照，应标为新增需求并单独裁决其范围，不能作为现状追认通过。
3. C1.3 分开写清：事件号在同店事件流中唯一、有序；记录版本链及令牌用于同一记录的跨进程冲突检测，不充当跨记录全局时钟。若确有更强要求，须另列可观察定义与验收。
4. 增加“扫描与写入交错”“显式强制删除”“不同记录版本相同但事件序号不同”的边界验收，使实现者与消费者得到同一种解释。

**建议**：本期优先发布既有保证的明确契约；更强的查询隔离或事务能力作为独立决策。维持当前读语义能保持成本与兼容性，但消费者必须自行处理跨记录观察的不同时点；新增快照能力则需要新的设计与验证，不能靠文字升级现有保证。

## B3 C1.6 允许替代式验收，无法证明核心的跨进程与崩溃承诺

**位置**：第 52 行 C1.6 允许回归形态为“双进程或同进程双句柄交错、崩溃注入均可”；第 87 行仅要求各条有公开 API 级回归并随发布点通过。

**核验事实**：当前互斥有进程内注册表和平台跨进程锁两个部分。只保留进程内互斥、破坏平台锁的实现，仍可能通过全部同进程双句柄测试，却允许两个真实进程同时写入。进程死亡后的资源释放也不同于正常返回错误、正常释放 guard。下钻：`crates/mem-core/src/lock.rs:12–15,39–44`。

仓库已有“父进程持锁、子进程探测、释放后子进程成功”的跨进程回归先例，但它不替代本次所需的公开 API 写入与进程死亡验收。下钻：`crates/mem-core/tests/locks.rs:153–186`。

**为什么阻断**：跨进程并发和崩溃接管正是本提案的核心消费前提；若只用同进程替代测试即可验收，“C1.1–C1.5 有回归”无法机械检出最关键的退化。实现形态自由不意味着可以用观测不到目标故障的测试证明承诺。

**修复门槛**：

1. 将真实独立进程与同进程多 Store 句柄列为两个验收维度，不能二选一。锁内策略、测试框架与具体编排仍由实现方选择。
2. 跨进程场景经公开 API 验证至少包括：同令牌竞争的成功／冲突结果、不同记录事件序号不冲突、成功写后另一进程读取新值。
3. 对崩溃接管设置受控同步点，使真实写者在未走正常清理的情况下退出，再由存活进程经公开 API 完成后续操作。写清测试的完成界限与允许的恢复／告警结果，避免“永不返回的测试也无法判失败”。不必覆盖断电，但须说明进程崩溃与存储故障的边界。
4. 按支持平台登记证据；本机不能执行的平台列外部验收项，不能用本机同进程测试宣称全部平台已通过，也不应将外部验收误设为本机开发前置门禁。

**建议**：保留同进程回归作为补充，真实进程测试承担跨进程与死亡接管承诺。该调整只限定验收的观测能力，不限定锁机制。

## B4 批量工具不是当前 serve 变成唯一写者的完整前置条件

**位置**：第 18 行将 MCP 工具面用于未来“经 serve 访问”，第 60 行 C3.3，以及第 81 行“经工具协议访问、serve 为唯一写者……前置条件即 C3”。

**核验事实**：

- 当前 `mem mcp` 是 stdio MCP 前端；它对每次工具调用直接打开 Store，并在自身进程调用 `ops::add/update/link`。下钻：`crates/mem-mcp/src/lib.rs:10–13`；`crates/mem-mcp/src/protocol.rs:77–80,349–387`。
- 当前 `mem serve` 是索引／新鲜性 sidecar，IPC 返回版本、订阅状态、事件水位等握手信息；它没有承接 MCP 写请求的集中写入分派。下钻：`crates/mem-core/src/sidecar.rs:1–10,37–47,383–407`；使用指南 `docs/user-guide/README.md` §9。
- 既有设计允许 sidecar 随时退出，其缺席只使读退回嵌入模式。下钻：主设计 D2、D5。

**影响**：即使给现有 MCP 增加原子批量工具，多个宿主仍可各启一个 MCP 进程直接写同一店，写者不会自动集中到 `mem serve`。若真要 serve 成为唯一写者，还需决定集中请求通道、其他受管写入口如何接入，以及服务退出时是否允许回退为直接写；这些会影响可用性和部署形态，不能由 C3 的批量入口默认涵盖。

**修复门槛**：

1. 在本文就地说明现有 MCP 与 sidecar 的职责，修正两者等同的表述。
2. 二选一明确范围：本提案只补工具能力，未来仍允许多 MCP 进程共店；或另列“集中写通道”为未来待裁决能力，其完成是唯一写者形态的另一前置条件。后者不是本轮自动批准的新服务设计。
3. 如果候选终局仅为下游自行维护一个 MCP 进程、独占地把其写入送往该进程，应明确这属于下游部署约束，不能据此声称 SpaceMemory 全部写入口已经被集中到 serve。
4. 调整 C3 时机与 §5 验收，避免把“工具已补齐”当作“唯一写者形态已可用”的充分证据。

**建议**：本期只裁决库契约与工具能力，集中写架构另行保留为候选。这个修正不阻断下游 v1，也不要求现在实施集中服务。

## 随本轮修订补齐的材料

1. **公开行为的裁决材料**：按 `docs/rules/document-writing.md` §0–§1、§4 补待批准清单、作者自曝三处、需要拍板事项的六要素与四列开放决策表。至少将“一致性级别、历史批次或事务、集中写通道范围”显式列项，分别给出维持现状的后果、关闭节点与验收条件。裁决前默认保留草案状态，不能由实现者暗选对外行为。
2. **发布与共店版本范围**：C2 应说明 C1 适用于同一发布版本，还是也支持某些不同版本共店；至少明确混用的支持边界与升级责任。不可变 tag 只能保证源码不变，不能单独证明新旧进程的协作协议兼容。C2.1 的“店目录布局冻结”还应指向公开格式范围，区分真相格式与实现私有运行时文件，避免与开头保留实现自由的立场冲突。这里要求声明支持范围，不预设必须增加运行时版本协商。
3. **现状与外部证据标注**：第 34 行“无远程”与当前本地配置不符，本轮 `git remote -v` 可见 `origin`；本地 `git tag --list` 为空，只能证明本地未见 tag，不能证明远端没有。应标注核验时间与范围。SpaceTeam 的三次断裂、POC-1、120 用例与 RK1 本轮未读取其仓库或复跑，应保持为下游提供的背景证据，不能写作本轮上游实测结论。

## 复审范围与待批准清单

**复审最低范围**：B1–B4 的修复门槛与受影响的 §1、C1/C3、§3、§4、§5 同步核对；检查新增需求与现状追认是否分清，验收是否真正覆盖相应进程形态和失败边界。需求阶段不要求先实现新增能力，要求先把待裁决范围与验收行为写清。

**本轮请求批准**：无；本报告记录阻断与修订门槛，不代替维护者批准需求取舍。

**可保留的方向**：逐版本引用公开行为、发布点不可变、变更记录可追溯、工作区中间态不承诺兼容、机制对具体类型零知识、新增能力遵循前端对等，以及 C3 不阻断下游 v1。

**本轮明确不批**：整库串行等价或跨记录原子批次被当作既有保证；以同进程测试替代全部跨进程／死亡接管证据；因批量工具补齐而默认批准 serve 唯一写者架构；需求编号、基线版本与设计修订行的变更。

## 自曝三处与证据边界

1. **B1 的事务判断来自当前仓库公开入口与设计**：未核验 SpaceTeam 自身是否实现了事务封装或恢复协议。若提供额外公开事务 API 及失败／并发读证据，可重新评估“库已有能力”的事实；若只是下游包装，应修正能力归属，Git 批次本身不提供工作目录原子性的结论不变。
2. **B2 的串行反例是静态交错推演**：本轮未写可控暂停测试。若作者将 C1.1 明确限定到单记录操作并排除整次扫描／多步调用，整库串行等价部分可按新范围关闭；引用显式例外与事件序号／令牌分界仍须写清。
3. **B4 基于当前可见前端与 sidecar 协议**：若已有未在本文声明的集中写实现、或这里的“serve”是未来新服务的泛称，提供接口、职责与状态即可重评；后者应明确为新增待裁决能力，不能继续被当作现有 MCP 的自然结果。

## B2 剩余：消除过强承诺后，核心条目变成“将来再定义契约”的任务

**位置**：第 50 行 C1.1、第 52–54 行 C1.3–C1.5、第 60 行 C2.2，以及第 89–94 行开放决策表。

第 50 行要求“明确……生效边界、CAS 失败结果，以及创建唯一性”；第 53 行要求“明确……观察范围”，写后可见性仅为“可按实际实现证据声明”；第 54 行要求“声明……可继续行为”。这些句子列出了应该回答的问题，却没有给出本期推荐范围内的具体答案。

例如，维护者即使选择“本期只声明现有单记录保证”，仍需追问：过期令牌是否拒绝、是否附当前完整令牌、是否改变目标记录；同一逻辑身份的竞争创建返回什么；成功写后何时允许另一进程读取新值；写者死亡后是否必须无需人工删锁就能继续。这些是原提案的核心消费前提，不能等到契约编写者自行从实现中选取后才知道批准了什么。

**权威事实并不要求新增更强能力**：既有公开写入规范已经规定 CAS 不一致时结构化冲突、含当前令牌、不落盘（`docs/specs/envelope-format.md` §5.3）；主设计 D3 规定同令牌竞争一成一冲突，规范 §3.2 规定竞争创建的输者返回既有记录及令牌。公开事件规范 §4.1 则已将事件号定义为全库唯一分配的行序。把这些必要的最小可观察语义写进提案，不需要复制锁协议，也不需要承诺整库事务。

第 60 行另将发布兼容规则交给“批准的版本策略”，但待批准清单和开放表仅为共店版本组合列了选项；发布点是否不可改指向、对外行为发生破坏时如何另发版本仍没有具体候选政策。一个可追溯的变更记录不能单独保证消费者当初引用的发布点保持原义。

**为什么仍是阻断**：本提案的目的正是让下游获得可引用的确定行为，而非继续反推实现。现文允许契约作者分别写出“冲突只报失败”或“冲突附当前令牌”、保留或不保留写后可见性承诺等不同强度的契约，都可以声称已完成“明确行为”的任务。第 98 行“符合批准的成功／冲突语义”也无法帮助批准者选择，因为本文尚未给出该语义。

**修复门槛**：

1. 为“本期仅契约化现有能力”写出一组最低候选承诺：受管单记录写、CAS 冲突结果、创建唯一性及输者结果、事件号唯一性／有序范围、成功写后可见性、写者死亡后的继续条件。写清适用前提及例外；多记录事务和扫描快照继续排除即可。若某项不准备提供，列为明确不做，并说明下游失去什么。
2. 将关键的既有语义与新增取舍分开：例如完整令牌冲突是已有规范；是否扩到查询快照才是新增取舍。对当前推荐范围，不应把每条既有语义重新包装成实施者可自由决定的空位。
3. 为发布点不变性与破坏性变化的发布方式给出可批准政策，或在开放表独立列项并要求在需求整体批准前关闭。无需本轮决定具体版本号，但不能只留下“按将来批准的策略记录”。
4. 关键决策按写作规则补齐可逆性、各自依据强度、推荐项与未裁决时的处置。现表已有选项、后果和关闭节点；仍缺这些要素。未裁决可以继续保持草案，不能默认实施某个公开行为。

**关闭判据**：维护者选择“仅契约化现有能力”后，仅阅读本文就知道将批准哪些行为；契约编写者可组织措辞和测试实现，但不能再自行决定是否承诺这些核心结果。这里要求补齐候选文本，不要求评审 Agent 替维护者裁决。

## B3 剩余：跨进程验收形态已修正，事件与创建的竞争验收仍缺失

**位置**：第 52 行 C1.3、第 96–105 行验收，尤其第 98 行。

第 98 行增加“不同记录可有相同本地版本号，不应因此被当成事件流序号冲突”，这只说明记录版本和事件号不是同一概念，**没有检查事件流自身的序号是否重复或丢失已成功的事件**。首轮 B3 修复门槛第 2 项明确要求“不同记录事件序号不冲突”；这一部分尚未落实。

**反例**：错误实现若保留记录锁而损坏事件序号分配的跨进程互斥，两个进程更新同一记录仍可一成一冲突，死亡后锁也可以正常释放；不同记录的并发写却可能竞争分配同一个事件号。当前列出的同记录 CAS、写后读、扫描、删除和死亡接管场景均不要求观测这一竞争，不能据此判定事件序保证通过。

此外，C1.1 与待批准清单继续包含创建唯一性，但验收没有真实进程同时创建同一逻辑身份的场景。CAS 更新成功不证明创建入口使用了相同的强制唯一机制。此项属于当前声明需要配对的验收，不要求新增创建语义。

**修复门槛**：

1. 增加不同真实进程同时写不同记录的场景，显式核对最终事件流中序号无冲突、符合所批准的顺序规则，并能对账各成功操作；记录的本地版本号可以相同，事件号不因此共享。
2. 若本期保留创建唯一性承诺，增加同一逻辑身份的真实进程竞争创建：最终仅一份活记录，输者按已声明语义返回既有记录及令牌。若不保留，应在范围决策中明确排除及后果，不能继续列在 C1.1 却没有验收。
3. 将 §5 已采纳的最低验收写为需求批准时一并确认的要求。标题“验收建议”与正文“符合批准的语义”可以用于讨论阶段，但整体批准时必须明确哪些成为强制证据、哪些仍是候选。新增测试的实现可留到实施阶段。

**已关闭的部分不重开**：真实进程不能由同进程双句柄替代、真实非正常退出、存活进程经公开 API 接管、超时判失败、断电不在隐含承诺内，以及外部平台验收的登记方式，v0.3 均已修复。

## B5 基础格式标记不能约束不检查它的历史程序

**位置**：第 67 行“旧基础格式……先显式迁移”、第 68 行“不支持则拒绝打开”，以及第 121 行要求不支持版本被拒绝、已打开旧进程在写前复查。

**代码事实**：

- 当前 `StoreConfig` 将 `format_version` 解析为任意 `u32`，未知配置键进入 `extra`；没有支持集合或版本相等判定。下钻：`crates/mem-core/src/store.rs:70–87`。
- `Store::open` 反序列化配置后直接探测卷可写性并创建句柄，没有拒绝未知基础版本；`check_writable` 只看该句柄的可写布尔值。下钻：`crates/mem-core/src/store.rs:162–179,190–196`。
- 当前代码中没有 `required_features`／`supported_features` 检查；全库 `format_version` 使用点也没有版本门禁。不能把将来的新程序拒绝规则倒推为这些历史程序已经会拒绝。

**反例**：把兼容 JSON 外形的 `mem.json` 从格式 1 改成新基础版本并加入必需特性清单，旧程序仍能反序列化并获得可写句柄；迁移前已经打开的旧句柄还保存着旧配置。新程序先登记特性，不能使这些旧程序突然执行它们没有实现的检查。

第 67 行正确指出旧程序不能被假定会读未知特性字段，但只要求“先显式迁移”仍不充分：旧程序同样不能被假定会拒绝新的基础版本。第 63 行把未声明组合列为不兼容，只规定支持政策，不会自动阻止它实际写入；它与第 68、121 行的机制拒绝承诺需要分层。

**修复门槛**：

1. 明确特性拒写保证从哪个具备基础格式校验与逐写复查能力的协议基线开始适用。对当前这种历史无防护版本，不承诺仅靠标记就能自动拒绝。
2. 为首轮启用防护写清可执行的迁移前提：已有写者退出或被隔离、迁移过程中不能继续写、旧程序再启动的处理。可以通过先统一升级所有受管写入口、目录隔离或其他可证明方案实现；需求不指定锁或部署技术，但必须说明谁负责和失败时允许什么。
3. 区分“已实现防护但不支持某基础版本／特性的程序，会机械拒绝”和“历史无防护程序不在该自动拒绝保证内，必须另行隔离”。不要用一组只由新代码模拟的旧版本测试覆盖全部历史版本。
4. 迁移验收加入真实历史行为的样本及已打开旧句柄场景：要么证明访问被阻止，要么明确其被隔离的前置条件；不能把它仍能写入的结果记录为防护成功。

这是启用新防护协议所需的兼容边界，不要求产品阻止任意外部软件直接编辑文件，也不推翻外部直写的既有合法地位。

## B6 “每次写之前检查”仍存在检查通过后特性集合变化的窗口

**位置**：第 67 行新特性登记的同步保护、第 68 行兼容判断只规定在可能修改目录前执行；第 119 行仅测登记／落数据间崩溃，第 121 行仅要求旧进程后续写前复查。

先登记后使用保证的是元信息与新数据的落盘顺序，逐次检查解决的是句柄永久使用打开时快照。两者仍不能单独保证检查通过后、实际写入之前，目录要求不再变化。

**真实进程交错的静态反例**（A、B 均已实现特性检查协议，不涉及 B5 的历史版本）：

1. A 只支持旧特性，写前读取清单为空，兼容检查通过，随后暂停；
2. B 持有登记同步保护，登记特性 F 并写入依赖 F 的数据，然后完成操作；
3. A 恢复，按此前通过的检查继续受管写，但从不再复核当前清单。

这满足“登记先于新数据”和“A 在本次操作前检查过”，却允许缺少 F 的 A 在整店要求 F 之后继续写，违反 C2.7 的整店拒写承诺。即使本次只写无关记录，整店拒绝规则已经被绕过；若涉及新字段或事件，则还可能破坏新语义。

现有普通写使用共享屏障，两个普通写之间并不互斥；“统一同步保护”不能靠名字自动等同于清单升级与所有写者之间的同步关系。下钻：`crates/mem-core/src/lock.rs:100–115`。此外，`Store::config()` 返回打开时缓存在句柄内的配置快照（`store.rs:199–205`）；逐次调用这个函数也不等于逐次读取另一进程更新的要求。

**修复门槛**：

1. 增加行为不变量：兼容许可必须相对于实际写入时有效的基础格式／必需特性获得。特性升级要么等待已获许可的旧写完成后生效，要么使尚未完成的旧许可失效并在落盘前重新检查；不能允许上面的交错成功。
2. 在同一同步边界内获取最新兼容元信息、验证、执行受其约束的写；或采用等价的代际校验／失效协议。保护需覆盖全部受管变更入口及格式／特性增减，不能只覆盖登记元信息的那一次写。具体锁、代际或数据布局留给设计，不要求全库普通写互相串行。
3. 明确重新检查读取的是最新目录状态而非 Store 缓存；并集增加须在同步边界内基于最新集合合并，不能让并发登记 F/G 相互覆盖。移除特性的核验与后续移除也需避免被并发新增依赖穿透。
4. 增加真实进程受控暂停验收：“A 检查通过后暂停 → B 升级清单并写新数据 → A 恢复”；结果只能是 B 等待 A 完成，或 A 复查后拒绝／按新规则安全完成。另测并发登记两项后清单保留并集。现有串行迁移与崩溃注入不能代替这两类竞争证据。

## B7 只读写盘例外与既有红线及整店拒写冲突

**位置**：第 68 行 C2.9：“只读操作不得写索引、会话或其他派生状态，**除非该能力本身受支持声明覆盖**。”

既有约束是读取路径零写盘，明确包括索引缓存与事件日志；纯读不创建台账，持久化对账只发生在写例程。公开格式也明确读取索引不建库不建表。下钻：主设计红线18／25；`docs/specs/envelope-format.md` §5.5 第 4 项、§7 的 trail 双通道规则。

这里的例外会允许一个缺少某项必需写特性、仅被允许只读打开的程序，因为声称支持索引或会话能力，就在读取期间写派生状态。它既改变红线18，又与同一条前文“特性不满足则拒绝所有受管写”发生冲突。支持某种数据格式说明能正确处理它，不等于允许在只读路径持久化。

**修复门槛**：

1. 删除以能力支持豁免只读写盘的例外，保留既有读取零写盘规则。只读支持范围可另行决定，但允许读不应隐含允许持久化。
2. 若需要索引维护、会话 flush 或其他持久化，明示其属于独立写操作，必须通过全部基础格式／整店必需特性检查；不能由只读请求自动触发，也不能只检查与该操作“看似相关”的部分能力。
3. 新增“不满足写特性但被发布契约允许只读”的验收：读取可返回受支持的内容或显式降级，索引、会话、事件等持久状态不变；显式维护写仍拒绝。沿用既有运行时临时探针的已裁决边界，不借本轮新增例外扩大读写范围。

本轮不建议修改红线。如果确实要改变读取持久化规则，必须作为独立设计变更明确提交，不能从格式支持声明推导出已获批准。
