# Agent 记忆与状态层需求基线评审报告

- 评审对象：`docs/requirement/agent-memory-requirements.md` v1.3（2026-11-07）
- 评审日期：2026-11-09
- 评审方式：需求全文读审，按 `docs/rules/document-writing.md` §0–§1、§4 检查跨条款一致性、验收可判定性与自足性；本轮不评价既有实现是否达标
- 评审环境：仅新增本报告，未修改需求、设计或代码，未执行运行时测试

## 评审结论（TL;DR）

**不予通过：三项阻断。** B1 把原子性、不丢更新和创建唯一性强加到无法由状态层拦截的人手直写，和 R2/R6 所允许的开放写入模型冲突；B2 同时要求“修复不改变正文字节”和“通过恢复历史字节治愈正文损坏”，同一修复操作无法同时满足；B3 要求读路径跳过坏条目，又要求全部存活记录满足条件即进入检索命中集合，对身份可匹配但内容损坏的记录给出相反结果。另有一项高优 H1：整体成功判据 2 未承接二进制例外，最终验收口径不一致。

三项阻断都能通过澄清责任边界解决，不要求推翻统一状态层、关键词检索或二进制承载方向；关闭前不宜把 v1.3 作为无冲突的实现与验收标尺。

## 阻断项

### B1 R3 的强一致保证覆盖人手直写，但状态层无法拦截这类写入

**位置**：R2.2、R2.4；R3 陈述、R3.1–R3.3、R3.5；R7.2；整体成功判据 3。

**问题与反例**：

1. R3 明确把“人直接编辑”列入默认写入者，R2.4 又规定绕过工具接口的人手修改是合法输入；但 R3.1 要求“任何单次写”原子生效。操作系统自带文本编辑器可以原地截断、分段写文件，另一个读取者可能看到中间态，状态层没有可强制该编辑器使用原子替换的介入点。
2. 用户用文本编辑器打开记录后，Agent 经受管接口完成一次更新，用户随后保存旧缓冲区及自己的修改。编辑器没有并发令牌，也不会接收状态层的冲突响应；后写覆盖先写而双方均未感知，直接违反 R3.2。
3. 人手可不经接口复制或新建记录文件。基础设施可以在后续访问时发现重复并隔离，但无法兑现 R3.3 的“不会被并发创建出两份”这一事前保证。
4. R7.2 的“任何写入者无法绕过”进一步扩大了冲突：R6 已把不合规外部写入作为必须识别、隔离和修复的常态输入，说明违规状态可能真实出现；它不能同时声称这类写入在物理上无法绕过机制。

**为什么是阻断**：按强字面实现，需求对不受控的第三方编辑器提出了不可交付的保证；若实现者自行把 R3 限定为接口写入，又会缩小当前基线的明确范围。两种实现无法由同一验收口径判定，且直接影响并发协议、外部修改语义与最终成功判据。

**处置选项**：

- **(a) 划分受管写入与外部输入（推荐）**：R3.1–R3.3 的原子性、冲突报告和唯一性事前强制仅承诺给经受管接口或遵循写入协议的写入者；人手/外部直写由 R3.5 的新鲜可见与 R6 的识别、隔离、修复承接，不承诺拦截其中间态或丢失更新。R7.2 同步改为“受管写入路径无条件强制；外部修改必须可发现、可收敛”。R3 验收分别标明“受管多进程竞态”和“外部修改收敛”。
- **(b) 保留对所有写入者的强保证**：要求人手编辑也使用原子替换、并发前置条件与唯一性协议。这会排除普通操作系统文本编辑器，必须同步收窄 R2.2/R2.4，并放弃当前最低门槛与开放写入模型。

**默认建议**：采用 (a)。它保留“接口写入不静默丢更新”的核心价值，同时如实描述直写文件系统时基础设施的能力边界；只需修订需求文本，无数据迁移成本。

### B2 R11.2 的修复字节不变与 R11.6 的损坏恢复互斥

**位置**：R11.2、R11.6；R11 验收 2、6；术语表“字节保真”。

**问题与反例**：设图记录原始正文字节为 A，人为翻转一个字节后变为 B：

- 按 R11.6 从版本历史或备份回填 A，才能治愈损坏；但“修复”把正文从 B 改为 A，违反 R11.2 的无条件条款“机制的再生成、修复、维护操作不改变记录的正文字节”。
- 若修复严格保持 B 不变，则满足 R11.2，却没有治愈 R11.6 和验收 6 所构造的损坏。

R11 验收 2 只证明“结构头再生成”应保持字节，不能消除 R11.2 中未加限定的“修复”与验收 6 的正文恢复冲突；术语表又把同样的绝对措辞复述为“字节保真”。

**为什么是阻断**：同一个损坏修复用例的两个必过条件互相否定，实现无论选择恢复字节还是保持字节都会失败。

**处置选项**：

- **(a) 区分结构修复与内容恢复（推荐）**：R11.2 改为“结构头再生成、结构修复及不改变内容的维护必须保持正文字节”；R11.6 明确“损坏内容恢复是经确认的内容写操作，允许以历史或备份字节替换当前正文，并产生新版本与审计留痕”。验收 2 继续锁定结构修复哈希不变，验收 6 增加恢复后哈希等于原始 A。
- **(b) 保持所有修复均不得改变字节**：删除 R11.6 的历史/备份回填承诺，只允许替换整条记录或要求用户在系统外修复。这会削弱 R6.3 的“每条坏数据经接口可修复”，并需重新定义记录身份与引用如何保留。

**默认建议**：采用 (a)，以“是否经确认改变内容”区分两类操作，而不是让“修复”一词同时承担相反承诺。

### B3 R6.2 的坏条目跳过与 R10.3 的全存活记录完备召回冲突

**位置**：R6.2；R10 陈述、R10.2、R10.3；R6/R10 验收。

**问题与反例**：在 `records/` 放入一条格式损坏的记录，其身份为 `abs-bad`，载荷或正文结构已无法正常解析。执行查询 `abs`：

- 身份域按 R10.2 的前缀谓词已经命中；该文件属于 R10.3 定义的 `records/` 存活记录，因此必须进入可续读穷尽的命中集合。
- R6.2 又要求“读路径跳过坏条目、附告警”，检索属于读路径，因此该记录应被跳过。

将其作为降级命中返回会违反 R6.2；跳过则违反 R10.3。当前“命中集合与对真相层现存记录逐条执行同一匹配一致”没有为不可判定记录或降级定位项设例外，R6 与 R10 的各自验收也都未覆盖这个交集。

**为什么是阻断**：坏写入是 R6 定义的常态输入，完备检索又是 R10 的硬承诺；二者交集不是罕见边角。实现者必须自行选择牺牲哪条基线要求，测试结果也将随选择不同而相反。

**处置选项**：

- **(a) 将完备召回限定为可判定记录（推荐）**：R10.3 明确坏条目不进入正常命中集合，但必须以独立告警暴露其位置、不可判定原因与修复入口；R10.6 的新鲜承诺仍适用于这些告警。补一条验收：身份看似命中但记录损坏时，正常结果不含该条、告警可见、读取不崩溃且可修复。
- **(b) 允许降级定位命中**：R6.2 为检索增加例外，允许身份/别名可确定的坏记录以“降级命中”返回并附告警；同时 R10.2/R10.3 必须定义无法解析的载荷与正文如何参与谓词，以及“完备”对未知值采用何种三值语义。该方案保留更多定位能力，但显著扩大检索契约。

**默认建议**：采用 (a)，保持正常命中谓词确定性，把不可判定状态显式移到告警面；不要把原始字节猜测匹配当作完备召回。

## 高优项

### H1 整体成功判据 2 未承接 R2.2/R11 的二进制例外

**位置**：R2.2、R2 验收、R11 责任边界、§5 范围划界与整体成功判据 2。

R2.2 已把二进制记录降格为“结构信息可读，内容字节经接口或整文件替换修改”，R2 验收与 §5 也都有例外；但整体成功判据 2 仍无条件要求“用户在不使用任何 Agent 工具的情况下，能读懂并修改自己的全部状态”。对任意图片、音频等字节，“读懂全部状态”不能由文本结构审计替代，最终总验收因此与分项口径不一致。

**处置建议**：整体成功判据 2 末尾补“文本类状态可读懂并修改；二进制记录按 R2.2 的可审计与替换例外处理”。这与 R2 验收现有括注一致，只统一口径，不重开二进制决策。

## 自曝三处（评审方）

1. B1 按 R3“写入者集合开放（含人直接编辑）”的明确字面判断。如果作者本意始终是“R3.1–R3.3 只管受管接口”，那么问题不是机制不可行，而是关键适用范围漏写；推荐处置正是补齐该边界。
2. B2 依据“修复”在 R11.2 未限定为结构修复。如果术语上已约定它与 R11.6 的“内容恢复”是不同操作，仍需在基线正文写出，否则当前自足文本无法让读者得出该区别。
3. B3 只证明正常命中与坏条目跳过存在直接冲突，没有穷举所有可能的降级检索设计；若另有三值匹配契约可满足双方，可作为 B3 的第三种处置，但必须在需求中定义其命中与告警语义。
