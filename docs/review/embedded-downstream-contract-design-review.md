## 3. 源码核验摘要

以下是静态核验事实，用于支撑候选方案的起点；不把它们当作新协议已实现的证明。

1. `StoreConfig::format_version` 当前为 u32；`Store::open` 先反序列化配置，再执行 Auto 可写探测（`crates/mem-core/src/store.rs:70`、`:162`）。字符串候选标记针对的是这条已核实的打开路径，不能外推到所有历史程序或其他自定义访问方式。
2. 当前 `check_writable` 仅查句柄布尔值，`config()` 返回缓存；普通屏障使用共享锁，维护使用独占锁（`store.rs:190`、`:199`；`crates/mem-core/src/lock.rs:100`、`:109`）。方案正确地把锁内重新判定和内部许可列为新增工作，而没有依赖现有布尔检查完成撤权。
3. 当前更新在记录锁内重读并比较完整令牌；随后发布记录、追加事件和汇入历史。`commit_batch` 收集已写路径，失败登记 pending，不回滚记录（`crates/mem-core/src/ops.rs:641`、`:674`、`:1213`）。A1/A7 的行为边界与此相符；公开 `update_locked` 等仍须在实施中封住绕过许可的路径。
4. 索引证明当前核对检查点、订阅、只读 schema 及索引 epoch；没有基础格式／必需特性维度（`crates/mem-index/src/proved.rs:58`）。现有 sidecar 的初始维护、tick 和握手均有持久化调用路径（`crates/mem-core/src/sidecar.rs:148`、`:165`、`:191`）。方案已经要求改造这些路径，不能把“旧代码已有只读连接”当作整体无副作用的完成证据。
5. macOS 平台实现实际使用 `flock`，部分模块注释仍描述 fcntl；现有测试已包含同进程多个共享 guard 分别释放时的跨进程互斥检查（`crates/mem-core/src/platform/macos.rs:57`；`crates/mem-core/tests/locks.rs:172`）。本轮未据过时注释推导锁缺陷；后续平台和死亡接管结论以实现及真实进程结果为准。

## 4. 非阻断整理与实施关注点

- **文档分层整理**：第 134–146 行把执行计划复选框放在技术方案内，与 `docs/rules/document-writing.md` §3 的“方案／规范内无复选框”不一致。建议把 T01–T09 移入独立执行计划，方案保留验收与依赖的指针。当前任务关系可以理解，此项不影响技术机制通过。

- **不要遗漏有界等待及 API 绕过验收**：第 88 行已要求核对阻塞式屏障，T01/T04–T06 已安排低层入口和许可改造。实施证据应覆盖进程内等待与平台等待、路径别名／多句柄，以及原公开低层写入口；仅测记录锁已有超时或单个元数据登记入口不足以关闭这些任务。
- **稳定交付面在发布前具体化**：公开 API 签名、错误判别码、能力文件名称与结构、迁移前端映射仍由 T01/T03/T07/T08 固定。维护入口应按需求基线 R10.1 明确 CLI/MCP 对应或逐项豁免裁决，不能用笼统“管理入口”替代最终清单。现稿已列交付物及冻结节点，本轮不要求实施前先交付这些产物。
