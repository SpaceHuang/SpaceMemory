# 关键词检索与载荷字段过滤技术方案（R10）评审报告

- 评审对象：`docs/develop/keyword-search-design.md` v0.1（2026-11-09）
- 评审日期：2026-11-09
- 评审标尺：`docs/requirement/agent-memory-requirements.md` v1.4，重点为 R10.3、R10.5、R10.6、R10.10，以及主设计红线 8/18/21
- 评审方式：文档读审 + 对现有 CLI/MCP 调用链、证明式新鲜性、索引物化、类型声明加载的定点源码核验
- 评审边界：只读核验设计与现状；未改设计或实现，未运行测试（本轮没有代码变更）

## 评审结论（TL;DR）

**不予通过：三项阻断。** B1 允许 indexed 路径在告警缓存缺失时静默省略强制告警，直接违反 R10.3，并与方案自身的双路径等价承诺冲突；B2 未定义跨类型同名字段声明异形时的校验与命中语义，CLI/MCP、direct/indexed 可据此做出不同结果；B3 拟下沉的 trait 没有承接现有索引代际核对，按草案接线可能绕过红线 21 的新鲜性门禁。

查询文法、正词项粗筛/负词项精筛、严格 UTF-8 正文边界、命中后分页、新增 `mem_find` 与两端同批交付的方向无需重开。修复下列三项后提交复审。

## 阻断项

### B1 `bad_records` 缺失时返回空告警不是合法降级，且现有旧索引可实际到达该分支

**文档位置**：§2.5（198–200 行）、§2.8 红线 8 行（255 行）、§4.1“坏记录不静默”行（350 行）、§7 索引迁移行（398 行）。

**问题与证据**：

1. §2.5 和 §4.1 承诺 direct/indexed 告警同源且集合等价；§2.8 却写明“`bad_records` 表……缺失时 indexed 路径告警为空属降级而非正确性损失（verify 兜底）”。R10.3 要求坏记录**不得静默消失**，并必须在本次读取以独立告警暴露位置、原因与修复入口；要求用户另跑 verify 不能替代本次响应的告警义务。
2. 这不是纯理论分支。当前只读索引校验只检查 `records/refs/meta` 及既有折叠列（`crates/mem-index/src/sqlite.rs:105-137`）；若新增 `bad_records` 时不把该表纳入只读 schema 门禁，旧代索引仍可通过校验。方案 §7 又明确“无迁移例程”，因此“旧索引 + 既有检查点 + 缺新表”是升级后可直接出现的状态。
3. 当前物化只对 `scan.records` 中可解析记录登记同代 stat，并丢弃 `scan.warnings`（`crates/mem-index/src/sqlite.rs:237-320`）。若新增告警表却不调整检查点条目，坏文件会造成实时 stat 与检查点持续失配，indexed 告警路径不可达；若另行枚举或另一次扫描补表，又会破坏“索引内容与检查点来自同一次扫描”的新鲜性依据。

**必须修复**：

- 删除“缓存缺失即告警为空”的规则。`bad_records` 缺表、结构不完整、读取失败或无法证明与检查点同代时，必须转为 direct 全量扫描并透出真实告警；也可显式拒绝 indexed，但不能以空告警继续服务。
- 明确坏记录与正常记录在同一次物化扫描、同一事务中写入，检查点 stat 集覆盖该次扫描看到的全部 `records/` 文件（含不可解析/不可读文件）；若选择“有坏记录即 direct”的保守方案，也须写成唯一规则，不得保留一条不可达的 indexed 告警承诺。
- 为超过 200 条告警规定稳定排序（建议 `rel` 升序）后再截断，避免 direct/indexed 因枚举或 SQL 无序而返回不同的告警子集。
- 补回归：新鲜 indexed 下的坏记录三要素；缺表/坏表回退 direct；坏记录增改删后的告警新鲜性；201 条以上告警的双路径同序同子集及 `warnings_truncated`。

### B2 跨类型同名字段的声明冲突未裁决，过滤请求没有唯一行为

**文档位置**：§2.4“声明检查”“取值转换”“两路径执行”（182–192 行）、§2.7 错误表（242–249 行）、决策④（296–304 行）、验收 8（365 行）。

**问题与反例**：方案只区分“候选集中无类型声明”和“部分类型声明”，没有覆盖“多个类型都声明同一字段，但取值形态不同”。例如：

- 类型 A：`status: {"type":"string","x-filter":true}`；
- 类型 B：`status: {"type":"number","x-filter":true}`；
- 未限定类型的 MCP 查询：`filters={"status":"todo"}`。

按“值形态不符声明 → `invalid_filter_value`”可读作整个请求因 B 被拒；按“部分声明类型生效、其他类型不命中”的精神又可读作仅 A 参与过滤并正常返回。两种实现的响应一个是错误、一个是命中清单，且都能从现文本找到依据。CLI 还没有唯一转换目标：`status=1` 可按 A 的字符串、B 的数字或二者同时解释，命中集不同。`candidates(..., Some(声明类型的清单))` 只负责收窄类型，并不能裁定上述参数合法性或逐类型等值语义。

这正属于决策④声称要消除的“同一查询两种都合规的实现”；现有验收 8 只覆盖“声明/未声明”，覆盖不到“声明但异形”。

**必须修复**：

1. 在决策④补充同名字段多声明的唯一规则：可选择“候选集内声明必须同形，否则 `invalid_filter_value`”，或“值至少兼容一个声明即合法，不兼容类型不命中；全不兼容才报错”，但不能继续留白。
2. 明确 CLI 在所选规则下按哪个声明转换；多个过滤条件共同出现时，明确各字段兼容类型集如何参与候选收窄，精筛仍以每条记录自身类型的声明裁定。
3. 增加 string/number 同名冲突、CLI `1` 的双形态、两个过滤条件分别由不同类型声明、direct/indexed 与 CLI/MCP 对账测试。

### B3 `FindPrefilter` 未承接索引代际核对，下沉后的新鲜性门禁不完整

**文档位置**：§2.1 执行流程与 trait（87–129 行）、§2.8 红线 21 行（258 行）、决策②（276–284 行）。

**问题与证据**：现有快路径不是只有“检查点 + sidecar + 只读打开”：CLI 还比较 `checkpoint.index_epoch == index.epoch()`，防止索引被删除重建或物化未完成时把旧检查点配到新/空索引（`crates/mem/src/commands/mod.rs:281-315`，其中代际核对在 301–305 行）。

方案把 fastpath 判定下沉到 mem-core，但注入的核心接口只有：

- `candidates(...)`；
- `bad_records(...)`。

trait 没有暴露 epoch，也没有定义“只构造已经通过同代校验的对象”或其他等价契约。按所给接口直接在 mem-core 做判定，核心无法完成现有代际比较；若让 CLI/MCP 各自在注入前补做，则关键新鲜性逻辑又留在两个前端，与单源目标相违，并允许某一前端漏做。该缺口会影响命中集合与告警新鲜性，不是可自由调整的内部模块归属。

**必须修复**：

- 把完整快路径契约收进单源：检查点、订阅、只读打开、schema 完整性（含 B1 的 `bad_records`）、epoch 同代比较均须有唯一执行点。可给索引读取 trait 增加受约束的 `epoch()`/校验方法，或改成仅由共同组装函数在全部证明通过后构造 indexed 执行器；文档须选定一种形状。
- 任一证明或索引调用失败均回退 direct，并更新 `read_mode.reason`；不得把失败转换为空命中或空告警。
- 保留并迁移现有“删除/重建索引但检查点仍指旧代”的回归，同时分别经 CLI 与 MCP 验证不会走 indexed。

## 本轮阻断

### B4 CLI 的兼容集双解释在 MCP 中无可等价表达，违反前端功能对等

**文档位置**：§2.4“取值转换”（204 行）、“两路径执行”（208 行）；§4.1“跨类型异形过滤唯一行为”（371 行）；验收 9（385 行）。

**反例**：候选类型 A 声明 `status: string`，类型 B 声明 `status: number`，两者均有 `x-filter: true`；库中各有一条记录，值分别为字符串 `"1"` 与数值 `1`，其余检索条件相同。

按 v0.2 §2.4：

- CLI `mem find x --filter status=1`：字符串声明和数值声明都转换成功，因此同时命中 A、B 两条记录；
- MCP `mem_find {"query":"x","filters":{"status":"1"}}`：仅字符串声明兼容，只命中 A；
- MCP `mem_find {"query":"x","filters":{"status":1}}`：仅数值声明兼容，只命中 B。

因此，CLI 这一次调用的 A∪B 命中集没有任何单个 MCP `filters.status` 值可以表达；反向地，CLI 也无法只表达 MCP 字符串输入的 A 子集或数值输入的 B 子集。`find` 又没有 type 参数，不能借类型限定消除差异。§204 末尾“两端……命中集一致”及 §371“四面对账”由此没有可执行的输入映射。

这不是“CLI 输入是字符串、MCP 输入是 JSON”的必然差异，而是 v0.2 新选择的兼容规则造成的能力差：同一语义过滤条件不能跨前端表达，直接触及 R10.1 的功能对等和提案范围第 5 条的结果一致性。

**必须修复**：

1. 重新裁决兼容类型集的跨前端输入语义，使每个合法过滤语义在两端都可表达。可选择：两端都对输入逐声明尝试转换；或为 CLI/MCP 同批增加等价的显式类型表达；或改采“候选集内同名声明必须同形”等不产生双解释的规则。不能只补测试来掩盖当前输入域差异。
2. 明确 string/number/boolean 及标量数组在所选规则下的两端映射，并保证 direct/indexed 共用同一 canonical 过滤条件。
3. 将上述 A/B 反例加入验收：至少固定 CLI 的 A∪B 调用及其 MCP 等价调用；另测 MCP 两种原生形态在 CLI 的对应表达。修复前 §4.1 的“四面对账”不可视为有效验证点。

## 高优项

### H1 “检查点同批写入”措辞可能绕过既有收敛发布协议

**文档位置**：§2.5（214 行）。

该句在“同一次物化扫描、同一事务”之后写“`bad_records` 表与 records 行、**检查点同批写入**”，容易读成检查点也纳入物化事务。现有正确协议是：物化完成后再做新鲜订阅查询，收敛才发布检查点（`crates/mem-core/src/freshness.rs:201-235`）；若检查点随物化事务提前发布，维护期间的二次写入可能被旧检查点提前确认，重新引入既有 `maintenance_race` 所防的新鲜性漏洞。

v0.2 修订行已把“bad_records/records 同事务”与“检查点 stat 覆盖”分开，§2.5 应保持同一分界：**只有 bad_records 与 records 同扫描、同事务；检查点复用该扫描的 stat 集，但仍在既有收敛查询成功后发布**。建议按此改写，并明确继续调用 `publish_converged_checkpoint`，不新增第二条检查点发布路径。
