## 阻断项

### B1 验收 5 与决策④(b) 的排除范围矛盾

- **现象**：验收 5 断言"命中清单**不含任何图记录**……与移除全部图记录后的等价库命中集合一致"——这是**全域**排除。而决策④(b) 只排除正文域："正文区不是合法 UTF-8 的记录，其正文区不参与关键词检索（**身份、别名、结构头字段照常参与**）"。
- **反例**：图记录 `payload.filename = "abs_demo.png"`（或别名/身份含 "abs"）→ 按决策④(b) 是合法命中，按验收 5 是验收失败。按④(b) 实现的**正确**系统无法通过验收 5；反之，为通过验收 5 而按记录类型全域排除，又违反④(b) 与 R8.2（基础设施对类型零知识，机械上也不可得"图记录"这一分类）。待批准清单第 1、2 条同时请求批准二者，批准即固化矛盾。
- **附带缺陷**：验收 5 未要求构造"正文区确含查询词编码巧合"的前置（伪命中前提），测试可能空转——正文区不含 "abs" 的图记录天然不命中，验不出排除逻辑。
- **处置建议**：改写为边界锁定式验收——(i) 构造正文区含 "abs" 编码巧合、其余三域不含的图记录：不进命中清单，与移除后等价库命中集合一致；(ii) 构造载荷/别名含 "abs" 的图记录：**仍**命中（锁定"仅正文区排除"）；(iii) 可加一句：正文区为合法 UTF-8 的图记录（如 SVG）照常参与——恰是"非合法 UTF-8"判定标准的正确行为。与 L4 一并收口。

### B2 现状盘点① CLI 格与 §1.2 第 1 条的事实错误

- **文档声称**：§1.1 表①命令行前端"✗ 仅文本通道"；§1.2-1"命令行导入路径无字节通道"；缺口定性"**写一半**、读为零"。
- **代码事实**：CLI 写通道已是字节保真——
  - `crates/mem/src/cli.rs:101-102`：`mem add --body`（"正文文件路径；'-' = stdin"）；`cli.rs:116`：`mem update --body-file`；
  - `crates/mem/src/commands/mod.rs:337-350`：`read_body` 以 `Vec<u8>` 原始读入（文件/`read_to_end`），无 UTF-8 强制；
  - `crates/mem-core/src/ops.rs:132`（`AddArgs.body: Vec<u8>`）→ `record.rs:26-39`（`serialize_new` 将 body **原样** extend 落盘，注释明言"字节领土，红线27"）。
- **影响**：(a) 问题定义的证据基础失真——真实缺口是"**写已通（两前端皆可保真写）、读为零**"，写入侧无缺口；(b) §1.2-1 与 R11.5 的动机叙述（导入"仅限完整工具协议档"）随之失真；(c) 决策③依据强度只提 MCP 写通道为现状——CLI 同样是 (a) 的现状，追认范围应覆盖两前端；(d) 文档自称"2026-11-07 代码核验"，错误断言以"已验证"身份进入决策依据，正是评审友善度规则要防的失效形态。
- **处置建议**：更正 §1.1 表① CLI 格为 ✓（`--body` 文件/stdin 原始字节）、§1.2-1 相应改写；缺口定性改为"读为零、写已通"；决策③依据补 CLI 现状。修正不翻转任何决策，反而加强③(a)。

## 高优项

### H1 R11.5 只约束完整工具协议档，CLI 字节读回义务无任何承载

- CLI `mem show` 正文输出有损（`crates/mem-core/src/budget.rs:63` body_slice lossy 截断；R14 报告亦登记"body_slice lossy"语义注记）——但 R11 全部六个分项中，取回义务只落在 R11.5（完整工具协议档）；CLI 前端读回字节既无分项要求，也不在"明确不做"清单登记后果。按 document-writing.md §4 判定句：补与不补 CLI 字节读回通道的两种实现都合规 = 需求没写完。B2 修正后此问题从"隐藏"变"显眼"（既然两前端都能保真写，为何只有一前端须能保真读）。
- **处置建议**：二选一显式化——R11.5 扩为各前端自足，或范围三清单"明确不做"加一条：命令行字节读回不做（后果：CLI 侧取回字节须经文件系统直接读记录文件，命令行宿主通常具备该能力）。

### H2 现状⑤"无脱离 git 历史的对账路径"不准确

- **代码事实**：`mem verify --deep` 的对照物是**事件日志**（`crates/mem-core/src/ops.rs:1121-1151` `deep_digest_audit`：磁盘全文件 sha256 vs `events.jsonl` 最后 new_digest；注释明言"真实对照物是事件日志"）。`events.jsonl` 是店目录内普通文件，与 git 无关——这正是"脱离 git 历史的对账路径"。R14 已复验 deep 真被读取。
- **影响**：翻转正文区字节今天即可经 `--deep` 发现（字节内容无关、天然覆盖二进制记录）——R11.6 的"发现"半边现状已基本具备，需求的真实增量在"治愈路径＋读路径不崩溃＋发现能力作为承诺而非偶然"。现状表失真会误导设计侧工作量评估。
- **处置建议**：更正现状⑤为"已具备（--deep 磁盘 vs 事件日志对账；非 deep 校验不做摘要对照）"；R11.6 可注明发现半边是对既有审计面的追认。

### H3 验收 3 后半在 link 边路径上现状不成立，与 R11.3"不新造语义"表述冲突

- **代码事实**：默认删除阻止覆盖一切 `envelope.refs`（`ops.rs:708-719` `reverse_refs` 全量扫描，含 `mem_link` 建的边）✓；但 verify 的断链审计只覆盖**类型声明 x-ref 镜像**（`ops.rs:1154-1211` `mirror_consistency_audit`：仅按类型声明核对 payload x-ref 两方向），`mem_link` 直接加进 `envelope.refs` 的边悬空后**无任何可见载体**（show/brief 不做悬空标注）。
- **影响**：题目→图引用若经 `mem_link` 建立（"类型化引用"的自然路径之一），越权删图后"题目侧的依赖警示可见"现状失败——R11.3"只要求该机制对图记录同样生效、不新造语义"的零增量表述失真，设计侧会漏掉一块真实工作量。
- **处置建议**：R11.3/验收 3 指明引用建立路径（题目类型 payload x-ref 字段，则既有审计覆盖；或 link 边），或将"link 边悬空可见性"登记为显式增量/显式不做。

# 第六轮重审（r6，2026-11-09）——字节保真与损坏治愈的边界冲突

- 评审对象：`docs/requirement/binary-content-requirements.md` v0.3（已并入基线）；联动核验 `agent-memory-requirements.md` v1.3 的 R11 平移文本

## 评审结论（TL;DR）

**复审不通过：一项阻断（r6-B1）。** R11.2 无条件禁止修复操作改变正文字节，R11.6 却要求经接口用版本历史或备份治愈已损坏的正文；二者按字面无法同时实现。该冲突已原样进入基线 v1.3，因此不仅要修提案存档，还必须同步修订基线 R11。冲突是局部的，不影响独立受管记录、正文区承载、检索排除边界与版本历史覆盖等既有裁决。

## 阻断项

### r6-B1 “修复不得改正文”与“损坏正文可经接口治愈”互相排斥

- **条款事实**：R11.2 规定“机制的再生成、**修复**、维护操作不改变记录的正文字节”（提案第 56 行；基线第 262 行）；R11.6 规定图字节与历史不符时“存在经接口的修复路径（版本历史或备份回填）”（提案第 60 行；基线第 266 行）。验收 2 只覆盖结构头再生成时保持正文（提案第 67 行），验收 6 则专门构造正文字节损坏并要求存在修复路径（提案第 71 行），说明两处“修复”实际指向不同操作，但分项正文没有划开边界。
- **反例**：图原始正文为字节串 A，外部翻转一个字节后变为 B，`verify --deep` 检出漂移。若按 R11.6 从历史或备份恢复，接口必须把正文由 B 改回 A，直接违反 R11.2；若遵守 R11.2 保持 B 不变，则损坏没有治愈，违反 R11.6。验收 6 只断言“存在路径”，不能消解分项层面的矛盾，反而会放过一个永远保留损坏字节的伪修复实现。
- **影响**：实现者无论选择“结构修复一律保字节”还是“内容恢复允许换字节”，都能找到使自己不合规的另一条已批准需求；按 document-writing.md §4 的唯一行为判据，本轮不能通过。
- **处置建议**：
  1. 将 R11.2 的保真义务限定为“再生成、**结构修复**及不以替换内容为目的的维护操作不得改变正文字节”，并显式登记 R11.6 的损坏内容恢复是唯一例外；
  2. 在 R11.6 明确：内容恢复是调用方显式发起的正文替换，恢复后的正文必须逐字节等于所选历史版本或备份，而不是保持当前损坏字节；
  3. 验收 2 保持结构修复场景；验收 6 增加实际执行恢复后的断言——正文哈希等于所选可信来源，随后深档校验不再报告该记录摘要漂移，避免只验证“有接口”而不验证治愈结果；
  4. 同步修订基线 v1.3 的 R11.2、R11.6 与验收 6；提案作为决策过程记录补注处置，不让两份权威文本继续带同一冲突。

## 阻断项

### r7-B1 “内容只能经受管接口改变”排除了基线允许的人手替换

- **条款事实**：R11.2 规定“内容的改变**只能来自经受管接口的内容写操作**”（第 263 行）。但 R2.2 明确允许二进制内容“经接口或**人手整文件替换**修改”（第 82 行），R2.4 规定绕过工具接口的人手修改是合法输入（第 84 行），R3.5 要求外部修改在下一次访问时如实可见（第 99 行）；R11 责任边界也再次保留人手整文件替换（第 269 行）。
- **反例**：用户停用全部工具，按公开规范以整文件替换修改图记录。该操作按 R2.2/R2.4 合法，系统按 R3.5 必须接受并呈现新字节，却按 R11.2 的“只能”字面违反字节保真需求。机制无法既承认这条合法外部写路径，又保证所有内容改变都来自受管接口。
