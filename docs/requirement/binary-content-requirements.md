## 1. 问题定义

### 1.1 缺口定位

先交代三个本文反复使用的概念：本系统中一条**记录**是一个文件，由结构头（信封：身份、类型、版本、引用等公共字段）加正文区（载荷自由区）构成；记录之间的**引用**是带类型的边，被引用的记录默认不可删除；**完整工具协议档**指宿主仅通过结构化工具调用访问状态层、无命令行与文件系统直接访问的集成形态。按"图从进店到用起来"的动作盘点现状（2026-11-07 代码核验）：

| 能力 | 命令行前端 | 完整工具协议档前端 |
|---|---|---|
| ① 写入图字节（保真落盘） | ✓ `--body`/`--body-file` 接受文件或 stdin，原始字节原样落盘 | ✓ base64 保真通道解码后按原始字节落盘 |
| ② 读回图字节 | ✗ `mem show` 正文按文本有损解码（接口级字节取回通道待补，R11.5） | ✗ 钻取走同一有损读路径（同左待补） |
| ③ 题目↔图的类型化引用 | ✓ 引用机制（含删除保护） | ✓ |
| ④ 检索不因图产生伪命中 | ✗ 有损解码后做子串匹配，编码巧合可入命中 | —（检索能力本身待补，另一提案在途） |
| ⑤ 字节损坏的独立发现路径 | ✓ 已具备（`verify --deep`：磁盘全文件摘要 vs 事件日志最后摘要，与 git 无关；非 deep 校验不做摘要对照） | 同左 |

缺口的性质：**写已通、读为零**。两个前端的写入通道都能把字节保真送进记录正文区（CLI `--body`/`--body-file` 原始字节；MCP base64 仅为传输编码），但全部读取路径把正文当文本解码——非 UTF-8 的字节序列在读回瞬间即被替换字符破坏，且这一损坏是静默的：宿主拿到的字节与写入的字节不一致，没有任何报错。此外，图字节经有损解码后残留的 ASCII 片段会参与子串检索，构成检索噪声。

### 1.2 起源场景中缺口的表现

题库导入需要四件事，件件撞在缺口上：

1. **图随题入库**——①两前端皆可用（CLI `--body` 文件/stdin 原始字节；MCP base64 传输编码），写入侧无缺口；
2. **出题时取回图**——②不可用：两前端接口的正文读回均按文本有损解码，读回即损坏，等于图存了但用不了；
3. **题目与图挂接**——③可用，直接复用既有引用机制；
4. **题库检索不被图污染**——④不可用：图越多，关键词检索的命中清单越不可信。

### 1.3 与既有需求的关系

- **状态主权**（基线 R2：开放格式、迁移等于复制目录、人用文本工具可读可改）：迁移性质对图必须原样成立——"复制目录到另一台机器，图完整可用"不因二进制破例；人类可读性对图记录**降格**为"可审计"（结构头全文可读，内容字节不可文本编辑），这一降格是本文显式请求裁决的实质例外，见责任边界与自曝第 4 处。
- **引用完整性**（基线 R3.4：引用不悬空，删除语义必须确定）：题目→图的引用直接复用既有机制，本文不新造语义，只要求该机制对图记录同样生效。
- **上下文经济**（基线 R4：单次访问规模有机械上限）：图的字节不得推高文本内容的访问成本——预算按记录独立计算，一条题不会因为带图而变贵。
- **坏数据健壮性**（基线 R6：坏写入是常态输入）：损坏的图记录不得使整体读取路径崩溃，且存在经接口的修复路径。
- **声明式类型**（基线 R8：基础设施对记录长什么样零知识，新类型以"结构声明 + 约定文档"两件套引入，零代码）：题库的题目类型与图片类型应以两件套引入，基础设施只补"二进制能被承载"这一通用能力，不认识"题库"或"图片"本身。
- **关键词检索需求（R10，另一在途草案）**：该提案裁定检索域覆盖"全域"；本文对二进制正文的处置与该裁定相抵触，需要协调——两案均未并入基线，措辞随评审同步收口（决策④）。

## 2. 需求陈述（R11 拟）

**陈述**：状态层能以记录形态承载非文本内容（图片等二进制数据）：写入的字节与读回的字节完全一致；图可被其他记录以类型化引用关联，关联与删除语义确定；宿主能按需取回字节；图的存在不推高文本内容的访问成本，也不污染检索；字节损坏可被发现并治愈。

**动机**：知识资产的原始形态不全是文本——题库的配图、签名的扫描件、录屏与音频片段，字节本身就是载荷。承载不了二进制的状态层，把这类资产排除在外，等于宣布"第二记忆只记文字"；而绕开系统把图放旁门外，图的版本、删除、引用、迁移全部脱离机制管辖，正是基线要消除的碎片化形态。

**分项**：

- **R11.1 受管形态**：二进制内容以记录形态入库，完整享有信封机制——身份与并发令牌、写入留痕、删除隔离（删除=移入隔离区而非消失）、引用完整性；跨机器迁移仍等于复制目录。
- **R11.2 字节保真**：写入字节与读回字节完全一致；机制的再生成、修复、维护操作不改变记录的正文字节；保真对两个前端的写与读同样成立——写入按原始字节落盘，取回按原始字节交付（传输环节的 base64 只是保真编码，宿主解码所得与盘上字节一致）。
- **R11.3 关联确定**：题目对图的引用是类型化引用，以题目类型声明的引用字段（x-ref 镜像纪律）建立为主、link 边为通用兜底；两条路径的完整性与删除语义均按既有引用机制（默认阻止删除被引用者、显式越权留痕）；"哪条题用哪张图、删掉一边另一边如何"的答案确定且可见——越权删除后的依赖警示经校验例程（verify 的悬空引用报告，两前端一致，覆盖上述两条建立路径）可见，不做读路径实时标注。
- **R11.4 文本路径不受染**：图的存在不推高摘要、清单、单条钻取文本记录的返回规模（预算按记录独立计，一条题不因带图变贵）；关键词检索不因二进制正文产生伪命中——查询词命中图记录的编码巧合不进入命中清单（本句以决策④(b) 为前提：④若被重新裁决为 (a) 接受伪命中，本句随之失效）。
- **R11.5 取回对等**：图字节取回是两个前端的**同批义务**（前端功能对等原则）——完整工具协议档不经文件系统访问即可完成"定位题目→钻取→取回其图字节"全链路；命令行前端经接口通道取回原始字节（不要求文本形式呈现，如正文落至指定文件一类通道），不依赖人手直接读记录文件或文本解码。
- **R11.6 损坏可治愈**：图字节与历史不符可被校验面发现，且存在经接口的修复路径（版本历史或备份回填）；损坏的图记录不使任何读取路径崩溃。发现半边是对既有审计面的追认（`verify --deep` 的磁盘 vs 事件日志摘要对账天然覆盖二进制记录，按该分档承诺——非 deep 校验不做摘要对照）；本期真实增量在修复路径、读路径不崩溃、以及把发现能力从偶然具备升级为验收承诺。

**责任边界**：状态层保证**字节保真与关联完整**。不承诺：图内容的理解（OCR、图生文——判断型行为，归执行体能力与类型约定）；图的体积优化（压缩、转码、缩略图——存入什么字节就取回什么字节）；"能用文本格式就别用位图"之类的表达劝退（归图片类型约定文档的教学，不铸进机制）。**对基线 R2.2 的显式降格**：人用文本工具对图记录可审计其存在与全部结构信息（结构头可读、大小可查、来源可溯），内容字节的修改经接口或人手整文件替换完成——"文本编辑器直接改图内容"不成立，本文请求将此确立为 R2.2 的唯一明文例外（裁决：允许，2026-11-07）。操作性说明：人手整文件替换需按规范重建结构头并遵守字节确定性（envelope 规范 §2），超出非专业用户的日常操作面——日常修复走接口替换，整文件替换是了解格式的用户的兜底通道；评估降格幅度时以此为准。

**验收**：

1. 带图题库全链路：导入含图题目（题目记录＋图记录＋引用边），将存储目录整体复制到另一台机器，每张图字节与源机逐一哈希一致；
2. 对任一图记录执行结构修复（结构头再生成、正文按字节保持），图字节哈希不变；
3. 删除被题目引用的图：默认被阻止且明确报告依赖方；越权删除后运行校验例程（verify），题目侧的悬空引用报告可见（覆盖类型声明引用字段与 link 边两条建立路径），不静默悬空；
4. 仅具备完整工具协议档的宿主（无命令行、无文件系统访问），完成"定位题目（检索或类型过滤）→钻取→取回图字节"，字节与写入时一致；
5. 检索对二进制正文的排除边界（决策④(b)，仅正文区排除）：(i) 构造正文区含"abs"编码巧合、身份/别名/载荷均不含的记录——不进命中清单，命中集合与移除该记录后的等价库一致（构造须保证编码巧合确在正文区，防测试空转）；(ii) 构造载荷（如文件名含"abs"）或别名含"abs"的记录——仍命中，锁定"仅正文区排除"边界；(iii) 正文区为合法 UTF-8 的图记录（如 SVG 文本）照常参与检索；
6. 人为翻转某图记录正文区一个字节：`verify --deep` 报告该记录磁盘摘要与事件日志不一致（发现半边按既有 --deep 分档承诺；非 deep 校验不做摘要对照），存在经接口的修复路径；全部读取路径不因此崩溃；
7. 前端对等抽验：命令行前端经接口通道取回图字节（不经人手直接读记录文件、不经文本解码），字节与写入时哈希一致（对应 R11.5，形态对齐关键词检索需求的对等抽验条目）。

## 3. 范围划界

**本期做**（按价值排序）：

1. 二进制承载能力的需求确立（R11 本体：受管形态、字节保真、两前端读回通道）；
2. 存放形态与字节承载位置的裁决（决策②③——图的形态是本需求的全部设计前提）；
3. 检索对非文本正文的处置裁定（决策④，与关键词检索需求草案的措辞协调）；
4. 两前端同批的字节取回义务（R11.5，前端功能对等原则的落地——含命令行接口级取回通道）。

**明确不做**（写不做的后果）：

1. **图内容理解**（OCR、图生文、以图检图）——后果：题图里的文字检索不到；宿主除非自身多模态，否则"看不懂"图内容，只能保真搬运。归执行体能力与类型约定，非本系统机制；
2. **图的加工**（压缩、转码、缩略图）——后果：一张 5MB 原图入库就占 5MB，体积优化是导入方的责任，机制不做有损加工（有损加工一旦做错即静默破坏字节保真）；
3. **表达劝退**（"矢量优先/文本优先"策略）——后果：机制不阻止"能用 SVG 却存 PNG"的浪费；劝退规则放图片类型两件套的约定文档，按约定与强制分离的既有划分（可判断的归机制，需要权衡的归教学）；
4. **同字节去重**——后果：同一张图被多题引用时若按多份存储则体积翻倍（经共享引用可避免，但依赖导入方自觉，机制不做自动发现合并）。

**未来再引入**：

- 同字节图的去重例程（显式、有预算、经确认的维护例程）；
- 缩略图等派生记录（走层级与派生需求的既有结构，图记录作为证据、缩略图作为产物）；
- 超大文件的外置存储（若实测证明版本历史全量跟踪不可承受）。

### 决策① 本文与基线的关系

- **背景**：二进制承载要约束后续设计与验收，必须进入"起源与评审标尺"；进入方式影响基线的评审完整性。
- **选项**：(a) 独立文档（本文）评审，通过后并入基线并占用编号 R11、基线升版；(b) 跳过独立评审，直接在基线上增写 R11 并升版。
- **后果**：(a) 破坏了会怎么表现——多一轮评审动作，基线更新晚一步；期间若设计与实现先行，验收标尺暂时悬空。(b) 破坏了会怎么表现——未评审内容直接进入评审标尺，评审发生在标尺内部：基线一旦被质疑，没有"评审前"状态可回退。
- **可逆性**：(a) 随时可改，无沉没成本；(b) 回退需再次修订基线，且历史中永远留下一个未经评审的版本。
- **依据强度**：已验证——本仓库既有惯例是基线修订由评审驱动（基线 v1.2 即由评审回应产生；关键词检索提案同走独立成文路线）；未验证——无。
- **推荐 + 默认**：(a)。人不决定时按 (a) 处理：本文为草案，不改基线。
- **裁决**（2026-11-07）：按默认 (a) 处理（本文即独立草案）；r4 终审通过。
- 下钻：AGENTS.md §4 决策落档纪律；关键词检索提案决策①（同型先例）。

### 决策② 图的存放形态：受管记录 vs 旁挂文件 vs 外部引用

- **背景**：图进了存储目录，但"是不是一条记录"决定它受不受机制管辖——受管记录享有令牌、留痕、删除隔离、引用与校验；目录里信封管辖之外的普通文件则全部脱离。这是本需求最重要的裁决，其余决策都以它为前提。
- **选项**：(a) 独立受管记录——每张图一条记录，字节在记录内，题目以类型化引用指向；(b) 旁挂文件——图存目录内的附件区，不在信封管辖内，题目正文记文件名；(c) 外部引用——记录里只存图的外部路径或网址。
- **后果**：(a) 破坏了会怎么表现——图记录进入清单与摘要等通用视图，万图题库的清单被图记录挤占，"先按类型过滤才能看清题目"成为常态操作；每图一条记录，导入工具的创建开销按图数线性放大。(b) 破坏了会怎么表现——图脱离全部机制：无版本令牌（并发改图互相覆盖不报）、无删除隔离（删了就是没了）、无引用保护（删题后图成孤儿，无任何机制发现）；校验不覆盖旁挂区；"哪些图还活着、哪张图被谁用着"从此无人能答。人手替换文件仍可行，但 R5/R6 的全部承诺对图落空。(c) 破坏了会怎么表现——外链腐烂或路径失效后题目图文断裂且机制不可见；跨机器迁移不再是复制目录，"复制过去图就没了"。
- **可逆性**：(a)→(b)/(c) 是已发布数据的迁出，代价大；(b)→(a) 可脚本化补建记录，可行；(c)→(a) 同 (b)，但已腐烂的外链不可救。
- **依据强度**：已验证——记录形态的全部机制现成可用（令牌、留痕、隔离区、引用、校验），选 (a) 无新增机制面；未验证——万图规模下图记录对清单视图的实际挤占程度（无数据，见自曝第 2 处）。
- **推荐 + 默认**：(a)。默认 (a)；清单挤占若实测成为问题，缓解走"类型过滤默认排除图记录"等视图层手段，不改存放形态。
- **裁决**（2026-11-07）：采 (a)——独立受管记录。
- 下钻：基线 R8.4（跨类型通用操作只依赖信封）、envelope 规范 §2（记录文件构成）。

### 决策③ 字节承载位置：正文区承载原始字节 vs 结构字段承载编码

- **背景**：图字节进了记录，放在哪里——正文区（结构头之后的自由区，机制对其零解释），还是结构头内作为结构化字段（base64 编码字符串）。现状：两个前端的写通道均已按前者落地（CLI `--body`/`--body-file` 原始字节；MCP base64 仅作传输编码，解码后的原始字节写入正文区）。
- **选项**：(a) 正文区承载原始字节，base64 只是线路上的传输编码；(b) 结构头内增设字段承载 base64 字符串。
- **后果**：(a) 破坏了会怎么表现——图记录的正文区不是文本，文本工具打开即乱码；人对图内容的直接修改只剩接口替换与人手整文件替换两条路（责任边界已显式声明此降格）。(b) 破坏了会怎么表现——大字节塞进结构头：体积膨胀约三分之一；结构头从"人类可读的结构摘要"变成混着编码墙的区域，人可读可编辑性的受损面反而更大（受损的是**全部**图记录的结构头，而非正文区）；语义错位——结构头字段应由类型声明解释，字节仓不是结构化字段。
- **可逆性**：二者互斥（同一字节两处可放即两份真相）；切换需全量迁移图记录。
- **依据强度**：已验证——(a) 即现状**两前端**写通道的实际行为（CLI `--body`/`--body-file` 原始字节读入原样落盘；MCP base64 解码后落盘），代码核验无误；(b) 的体积膨胀为 base64 编码率的算术事实；未验证——无。
- **推荐 + 默认**：(a)。本条是对现状的追认。
- **裁决**（2026-11-07）：采 (a)——追认现状；r4 终审通过。
- 下钻：envelope 规范 §1/§2.5（正文区定位与字节确定性）；红线27（正文按字节保持）。

### 决策④ 检索对二进制正文：排除 vs 接受伪命中

- **背景**：关键词检索按"词项在正文中作为连续子串出现"判定命中。图字节经文本解码后，残留的 ASCII 片段参与匹配——base64 及各类编码的字母表都是 ASCII 子集，任意查询词都有概率与随机字节的编码形式巧合命中。现状：读路径按 UTF-8 有损解码后做子串匹配，无任何排除。
- **选项**：(a) 接受伪命中——检索域维持纯"全域"，不做特判；(b) 排除非文本正文——正文区不是合法 UTF-8 的记录，其正文区不参与关键词检索（身份、别名、载荷照常参与；域称法与关键词检索需求四域一致）。
- **后果**：(a) 破坏了会怎么表现——题库越大伪命中越多，命中清单被编码巧合静默稀释；用户无法区分"真命中"与"编码巧合"，检索可信度随图量线性下降。(b) 破坏了会怎么表现——检索域不再是纯粹的全域：题图里画的文字检索不到（本来也检索不到，文字识别属图内容理解、已列为非目标）；与关键词检索需求草案的"全域匹配"裁定字面抵触，两案并入基线时须同步收口措辞；判定标准（正文区是否合法 UTF-8）成为检索行为的一部分，需要测试面对账。
- **可逆性**：互为对外行为变更，任一方向切换都须重新评审检索行为。
- **依据强度**：已验证——现状读路径确为有损解码后匹配（代码核验）；排除标准"正文区非合法 UTF-8"是机械可判定的（属于强制类规则，不依赖写入者自觉，也不需要每个二进制类型记得自我声明——漏声明的类型会让伪命中静默回归）。未验证——真实查询词在图字节编码形式上的伪命中频率（无实测；按字母表覆盖率推演非零且随图量增长）。
- **推荐 + 默认**：(b)，以"正文区非合法 UTF-8"为排除标准。默认 (b)。
- **裁决**（2026-11-07）：采 (b)——以"正文区非合法 UTF-8"为排除标准；R10 提案并入基线时检索域措辞同步收口。
- 下钻：关键词检索提案 R10.2/决策③（全域裁定与键名噪音的既有容忍）；基线 R7（强制与教学的分离）。

### 决策⑤ 版本历史是否覆盖图字节

- **背景**：本库以 git 为版本历史基座。图记录入库后是否纳入跟踪，决定"误改一张图能否回到旧字节"。题库图的典型写入模式是写一次、读多次——历史增长是一次性的。
- **选项**：(a) 默认全量跟踪——图记录与文本记录同权；(b) 默认排除——跟踪范围交由各库按约定裁决；(c) 大文件外置（LFS 式）——历史存指针，字节存旁库。
- **后果**：(a) 破坏了会怎么表现——万图库的版本库体积与常规操作（提交、查状态）耗时上升，低端设备上可感；换来的完整性与回退能力对图字节同样成立。(b) 破坏了会怎么表现——图的历史断档：误改图后无法回到旧字节（删除恢复不依赖版本历史、不受影响，但**修改**的恢复无从谈起）；各库自行裁决导致行为不一致，"这个库的图有没有历史"成为隐性知识。(c) 破坏了会怎么表现——跨机器迁移需要额外环境组件，"复制目录即迁移"破例；旁库与主库的一致性成为新的失效面。
- **可逆性**：(a)→(b) 收缩跟踪范围可增量做，已跟踪的历史仍在；(b)→(a) 补跟踪即可，但排除期间的修改历史已永久缺失；(c)→(a)/(b) 需把旁库字节收回主目录，迁移成本高。
- **依据强度**：已验证——删除隔离与版本历史相互独立（隔离区的恢复不依赖 git）；题库图的写一次特性使 (a) 的膨胀有界（增长一次性，不随读放大）。未验证——万图库的实际体积与操作耗时（无数据，见自曝第 3 处）。
- **推荐 + 默认**：(a)。默认全量跟踪；确有大库负担的，走 (b) 作为该库的显式约定，机制不内置排除。
- **裁决**（2026-11-07）：采 (a)——默认全量跟踪。
- 下钻：设计文档 M2（git 基座现状）；基线 R2.3（迁移等于复制目录——(c) 与之抵触的依据）。

## 6. 自曝三处

1. **排除标准"正文区非合法 UTF-8"可能误伤**：文本记录若因坏写入携带损坏的编码序列，其正文将被排除出检索——为消伪命中引入了漏检风险。*什么证据会推翻*：实际库中出现含损坏编码的文本记录、且其内容确被检索依赖——届时须改用类型声明标记作排除标准，接受"漏声明即伪命中回归"的代价重新权衡。
2. **决策②对清单视图的挤占无实测**：万图题库下图记录是否真会把清单/摘要挤到不可用，纯推演。*什么证据会推翻*：题库实测中"先过滤才能用"的缓解手段仍不敷使用，且视图层手段（默认排除等）被判不可接受——届时旁挂文件形态须重新裁决。
3. **版本历史全量跟踪的膨胀无实测**：万图库的仓库体积与操作耗时无数据。*什么证据会推翻*：实测显示目标规模下版本库操作不可接受，且该库无法接受按库排除（决策⑤(b)）——届时大文件外置须重新裁决，并接受迁移破例的代价。
4. **对基线 R2.2 的降格可能是本文最大的异议点**："文本编辑器可读可改全部状态"是基线的硬承诺，本文请求对图记录降格为"可审计、可经接口替换"。*什么证据会推翻*：用户裁决 R2.2 不允许任何例外——则二进制内容只能外置（决策②(c)），本文主体（受管形态、保真、取回对等）随之重写。——已裁决（2026-11-07）：允许降格，本条异议未触发。

## 8. 术语与锚点

| 术语/锚点 | 含义 |
|---|---|
| 记录 | 状态层中一条可寻址的信息单元，物理上是一个文件：结构头（信封）＋正文区 |
| 信封/正文区 | 信封是基础设施拥有并管理的公共结构（身份、类型、版本、引用）；正文区是其后的载荷自由区，机制对其零解释 |
| 受管记录 | 享有信封全部机制（令牌、留痕、删除隔离、引用、校验）的记录；与"目录中信封管辖外的普通文件"相对 |
| 删除隔离 | 机制的删除＝移入隔离区（同相对路径、字节不变），可恢复；本文化的"attic"即指此区 |
| 字节保真 | 写入字节与读回字节完全一致，且机制的再生成/修复/维护不改变正文字节（R11.2） |
| 伪命中 | 查询词与二进制字节编码形式的巧合子串匹配——非内容语义的命中（R11.4、决策④） |
| 有损解码 | 把字节序列按 UTF-8 强行解释、非法序列替换为占位符的读法——字节从此不可复原（§1.1 缺口成因） |
| 类型两件套 | 一种内容类型的交付物：可执行的结构声明＋约定文档；新增类型零代码（基线 R8.8） |
| 完整工具协议档 | 宿主仅经结构化工具调用访问状态层的集成形态，无命令行与文件系统直接访问 |
| 前端功能对等 | 命令行前端具备的每项工具与功能，工具协议前端均须对应具备；新增能力须同批落两端（关键词检索需求已裁决原则，R11.5 据此立两前端取回义务） |
| 基线 | `agent-memory-requirements.md` v1.2——R1–R9 需求基线，本文通过后并入 |
| 关键词检索提案（R10） | 同目录 `keyword-search-requirements.md`（v0.5 已裁决，待并入基线）；本文决策④与其检索域裁定联动，并入时同步收口（双侧挂账） |
