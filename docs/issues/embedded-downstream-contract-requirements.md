# 下游集成接口契约需求——SpaceTeam 视角提案

- 版本：v0.6（2026-11-21）
- 修订：依 r4 复审补齐防护协议适用基线、历史旧进程切换隔离、兼容检查与整次写入共用同步边界，以及只读路径零写盘要求；增加历史版本、并发登记与检查后暂停交错验收。B1–B4 修复保留。
- 状态：**草案（待评审/裁决，未编号）**。本文提出需求，不代表维护者已批准新增行为、发布政策或实现方案。
- 说明：本文面向下游消费者，描述按发布版本引用的公开行为及缺失能力。它不规定锁、存储布局、日志实现或内部重构方式。
- 起源：SpaceTeam v1.5 以库形态嵌入 mem-core，并与其他进程共用一店。下游报告称工作区中间态曾造成接口断裂；该经历是下游提供的背景，本轮未读取 SpaceTeam 仓库或复跑其 POC、120 用例和 RK1。

## 本轮待批准清单

维护者本轮需裁决以下候选政策；若批准本文整体，C1 的明确行为与 C2 的候选发布政策即成为需求，而非留待实现者补选：

1. C1 本期是否只发布现有单记录写、CAS、创建唯一性与引用处理行为的契约；是否另立查询快照或跨记录串行等价需求。
2. C3 是否保持逐笔受管写、仅汇总 Git 历史；或新增跨记录事务。两者的故障、可见性结果不同，不能将后者视作现状。
3. C2 的数据格式防护：每个发布契约声明支持的数据格式基础版本与机制特性；数据目录记录当前基础格式及已使用的必需特性。用户已同意以整店必需特性清单进行防护；基础格式升级和只读范围仍需明确。
4. 集中写通道是否作为未来独立能力继续研究。当前方向是维持多进程直写，并允许下游自行选择单 MCP 进程；serve 集中写通道的优缺点和未来边界仍待明确。

本轮明确不批：整库串行等价、整次扫描快照、跨记录原子事务已是现状保证；同进程测试可以替代真实进程证据；增加批量 MCP 工具即可使 serve 成为唯一写者；需求编号、需求基线版本或设计修订行变更。

## 1. 问题定义

### 1.1 消费形态与现状边界

SpaceTeam 当前以库形态嵌入 mem-core，经自身服务调用公共 Rust API，并与其他进程共用同一店。受管写是通过 mem-core 操作入口执行的记录变更；事件登记是把操作记入店内事件流；Git 提交是把已发生的变更汇入历史版本。这三者不是同一件事：当前 `commit_batch` 汇总已写出的记录路径与事件日志，不能使多条记录同时生效，也不提供跨记录失败回滚或原子可见性。无 Git 提交汇时，受管写仍可成功；Git 提交失败也不撤销已经生效的记录。

现有公开 Rust 库接口和工具协议是不同入口。`mem mcp` 是 stdio 工具前端，每次工具调用在自身进程打开 Store 并调用库操作；`mem serve` 是索引与新鲜度 sidecar，提供握手、订阅和事件水位等能力，不接收 MCP 写请求，也不集中其他进程的写入。因此，增加 MCP 批量工具本身不会把写者集中到 `mem serve`。

本文关注三类事项：库接口公开行为是否需要逐版本声明；发布点能否让下游锁定；工具协议是否需要新增批量或集中写能力。实现证据可用于核验，但不自动构成已发布契约。

### 1.2 公开行为缺少逐版本声明

下游希望能够引用某个发布版本承诺的行为，并从变更记录判断升级影响。仅从源码注记反推，会让内部重构和对外行为变化难以区分，也无法从契约条目追溯到覆盖它的回归证据。

### 1.3 发布点与证据范围

下游报告称其计划从工作区 path 依赖迁移到固定 revision；本轮未读取下游仓库核实该计划。上游发布 tag、变更记录和下游升级测试各自是不同责任：本文只提出上游发布点需求，不代替下游完成固定版本和升级验证。

本轮核验范围为上游当前工作区源码与文档，日期 2026-11-20。评审报告记录当时本地可见 `origin`、本地 tag 列表为空；这不证明远端没有 tag。本轮未重新查询远端，故发布状态需在裁决或发布准备时复核。下游所述 SpaceTeam 断裂次数、POC-1、120 用例和 RK1 均为下游背景材料，不作本轮上游实测结论。

### 1.4 批量入口的真实缺口

当前工具清单是否存在批量入口，应以目标发布版本的工具协议盘点确认。即使增加一次调用接收多项操作，也必须先裁决该入口承诺的是逐项受管写、Git 历史汇总还是跨记录事务。若只汇总历史，其他进程仍可能在执行中观察到部分记录；失败也不会自动回滚已生效项。下游恢复链如有提供，须由下游明确承担和验证。

## 2. 需求陈述（拟，C 系列）

**陈述**：SpaceMemory 对已发布版本声明公开行为，并保留变更记录与对应回归证据；对缺失的工具能力明确裁决是否新增。所有新增行为须先经维护者批准，不由现状描述或实现者默认决定。

### C1 库接口行为契约（最低候选承诺）

- **C1.1 单记录写与 CAS 冲突**：通过公开受管写入口更新一条记录时，调用方须提供该记录当前的完整修订令牌（版本与整文件摘要）。令牌不匹配时，操作返回结构化冲突及当前令牌，目标记录不落盘、不追加本次操作事件；调用方可读取当前内容后决定是否重试。写成功只承诺该次单记录操作，不扩展为跨记录事务。
- **C1.2 竞争创建与唯一性**：对同一逻辑身份（同一类型声明的唯一键组合）并发创建，最终只存在一份活记录。输者返回既有记录 ID 与其当前修订令牌，作为可继续处理的结果，不报告为含糊的通用失败。不同逻辑身份可各自创建成功。
- **C1.3 引用处理**：普通删除按公开操作规则阻止或清理会受影响的引用；显式强制删除可以留下悬空引用／归属，但必须在操作结果中返回可观察告警。契约不承诺无例外地“不产生断链”。
- **C1.4 事件号与记录令牌**：每次成功登记的事件在同一店的事件流中获得唯一正整数序号；序号按事件行顺序严格递增，不重复、不遗漏已成功登记的事件。它表示店内事件顺序，不表示跨机器归并顺序。记录版本与 CAS 令牌只用于各自记录的冲突检测，不充当跨记录时钟或全库水位。
- **C1.5 写后可见性**：一个公开受管写成功返回后，之后开始的、针对该记录的公开读取必须返回新版本；Git 提交可稍后完成，是否已入 Git 历史不改变此读取结果。读取与写入重叠时，或调用方跨多次操作读取不同记录时，不承诺共同快照或整库串行等价；扫描可观察到不同记录在不同时点的有效状态。
- **C1.6 崩溃与并发边界**：同一店同一发布版本的受管写由多个真实进程并发执行时，须保持 C1.1–C1.5 行为。写者进程非正常退出后，存活进程无需人工删除锁文件或重启机器，即可在公开操作的配置超时内继续通过公开 API 读写；可观察到的记录和事件状态须符合退出前已成功返回的单记录操作。未成功返回的操作可未生效，或已生效并由事件／读取结果检出，但不得造成无法解析的记录或重复事件。承诺不覆盖断电、内核故障或存储设备损坏。
- **C1.7 回归证据**：每项行为须有公开 API 级回归。同进程多 Store 句柄是补充维度，不能替代真实独立进程。真实进程测试须覆盖同记录 CAS 竞争、同身份创建竞争、不同记录并发写的事件序分配、成功写后另一进程读取，以及真实写者非正常退出后的接管。

### C2 版本化发布点（提案）

- **C2.1 发布点**：提供可固定引用的发布提交与 tag，附公开 Rust API、行为契约和其支持的数据格式版本范围。发布 tag 必须指向不可变提交；已发布 tag 不得被移动、重打或用新内容替换。数据格式版本只覆盖 SpaceMemory 拥有的格式和机制规则，边界见 C2.5。
- **C2.2 破坏性变化**：对已发布公开 API、已承诺行为或公开店格式的破坏性变化，必须发布新的版本号与新 tag，并在变更记录中列出受影响承诺、迁移／适配要求；旧 tag 与其契约继续指向原内容。修复实现但不改变承诺可按兼容修订发布，不得改写旧 tag。具体版本号序列规则（例如语义版本主次补丁位）仍由维护者单独批准。
- **C2.3 变更记录**：每次公开接口或行为契约变化均有可追溯记录。下游负责固定版本，并在升级时运行其自身测试。
- **C2.4 共店版本边界**：同一数据目录上的多个进程按各自发布契约中的兼容声明判定是否可共同读写。未声明兼容的版本组合一律视为不兼容；调用者负责选择版本和安排升级，SpaceMemory 不保证未声明组合可用。
- **C2.5 数据格式基础版本**：每个不可变发布契约声明可解释和维护的数据格式基础版本。基础版本定义机制拥有的结构与规则：记录信封、版本／摘要、事件日志、`mem.json` 机制字段、写入／恢复／维护语义，以及派生状态的重建规则。格式基础版本只在这些结构或规则出现不兼容变化时升级；不要求产品发布者预估未来上界。
- **C2.6 调用者数据边界**：调用者自定义类型声明、载荷字段业务含义和正文语义不属于 SpaceMemory 格式版本的兼容承诺。SpaceMemory 仍须声明其执行的通用机制能力，例如支持的 Schema 方言、通用引用关键字及未知字段保留规则。只要内容符合基础格式的通用承载约束，具体类型和载荷可由调用者自行演进；上游不得因格式升级擅自改写其业务含义。
- **C2.7 必需机制特性元信息（用户已同意）**：具备防护协议的基础格式维护整店级 `required_features` 清单；每个不可变发布契约声明 `supported_features`。特性标识必须稳定并显式带语义代号，例如 `event.restore_body/v1`；仅字段名不足以区分语义变化。写入者须满足 `required_features ⊆ supported_features`，否则拒绝该店全部受管写并报告缺少的完整标识。未知可选字段必须保留；若写入路径不能保留，则按缺少必需特性处理并拒绝。
- **C2.8 特性登记、变更与同步不变量**：兼容检查、获取最新格式／特性元数据、受管变更及其事件登记必须处于同一个同步边界内。任何写许可不得在离开该边界后继续生效；写屏障须贯穿实际变更完成，不能只保护检查或元数据更新。新增特性登记与依赖该特性的数据写入在同一同步边界内完成，且先登记后写数据。并集增加必须基于边界内读取的最新集合，不得并发覆盖彼此；移除须在同一边界内证明无数据、事件或维护规则再依赖后才可生效。具体锁或代际实现留给设计。
- **C2.9 只读与持久化维护**：只读读取维持零写盘，不因发布版本声明支持某种格式、索引或会话能力而例外。读取不写索引、不更新会话、不追加事件、不执行持久化对账。索引重建、会话 flush、reconcile 及其他持久化维护均是独立受管写操作，必须经过完整的基础格式与整店必需特性检查，并在同一同步边界内执行；Store 打开时既有运行时临时探针行为不因本条扩大。
- **C2.10 防护协议基线与历史旧程序切换**：自动拒绝保证仅适用于实现并执行基础格式校验、必需特性校验和逐次写同步协议的版本。更早的历史程序不会因目录标记自动拒绝；不得对它们宣称机制性保护。首次启用防护协议前，部署方须停止全部历史写进程、关闭其已打开句柄并隔离其再启动，然后执行显式迁移。迁移后的基础格式标记必须令已界定的历史公开打开路径在任何可写探测或业务写之前失败；无法证明会失败的其他历史程序继续由部署方隔离。迁移期间不得有旧进程访问目录。迁移后已知历史程序重新启动须在解析／打开早期失败；新协议进程再按格式和特性逐次检查。
- **C2.11 打开与逐次检查**：程序打开目录时校验基础格式版本与必需特性；基础格式不支持则拒绝正常打开。特性不满足则拒绝所有受管写。每次可能改变目录的操作必须在持有 C2.8 同步边界后重新读取最新元数据并校验，不得使用 Store 句柄缓存的旧配置许可。对不具备写能力的格式／特性是否允许只读打开，按格式解析能力声明；任何允许的只读操作仍须零写盘。

### C3 工具批量与集中写通道（待裁决；不阻断下游 v1）

- **C3.1 现状盘点**：在批准或发布时对目标版本工具清单和写入路径重新核验，不以本提案中的历史盘点替代版本证据。
- **C3.2 批量语义选项**：维护者须选择保持逐笔受管写、可选地汇总 Git 历史；或新增跨记录事务。前者可能让其他进程看到中间状态，单项失败不回滚前序成功项；后者须作为库机制与所有对等前端共同新增的能力，明确成员失败时整体生效规则、进程中途退出的可观察结果以及其他进程能否读取部分批次。单次工具调用这一接口形状本身不等于原子事务。
- **C3.3 集中写通道**：若未来目标是由 serve 成为唯一写者，须另行设计并裁决请求通道、其他受管写入口如何接入、服务退出时是否允许直接写回退。当前 `mem serve` 不具备这一职责，补批量工具不是其充分前置条件。下游若自行独占一个 MCP 进程并把写请求送往该进程，那是下游部署约束，不代表 SpaceMemory 全部写入口已集中。
- **C3.4 零知识与前端对等**：若新增通用批量能力，不内嵌具体类型字段语义；经裁决后按前端功能对等原则列出需同步的入口。
- **C3.5 时机**：C3 不阻断下游 v1 的库形态集成。是否作为未来工具形态的前置能力，待下游部署目标和上游能力边界分别裁决。

## 3. 与既有行为的关系

| 既有概念 | 本提案中的准确范围 |
|---|---|
| 受管写 | 单次公开操作按其自身保证生效；不能据此推导跨记录原子性。 |
| `commit_batch` | 将已写记录路径及事件日志汇入 Git 历史；Git 失败不回滚真相层。它不提供跨记录事务。 |
| CAS 令牌 | 表示单条记录的版本与摘要，用于该记录的冲突检测；令牌不匹配时返回结构化冲突和当前令牌，且本次不落盘；无跨记录时钟语义。 |
| 竞争创建 | 同一逻辑身份只有一份活记录；输者取得既有 ID 与当前令牌。 |
| 事件号 | 每个成功登记事件在店内事件流中取得唯一、严格递增的正整数序号；不同记录并发写也共享同一序列。 |
| 引用完整性 | 可按公开操作阻止、清理或在显式强制模式下报告断链；“不产生断链”须保留该例外。 |
| `scan_all` | 逐文件读取；不因此构成整次扫描共同快照。 |
| `mem mcp` | 当前 stdio 工具前端，在自身进程调用库操作。 |
| `mem serve` | 当前索引／新鲜度 sidecar；不承接 MCP 写请求，不是当前唯一写者。 |

下钻：需求基线 R3、R8；主设计 D2、D4、D5、D17 与红线 8、18、19、20、22、24；工具、库和 sidecar 的具体实现以对应发布版本源码为核验材料。上表为本文所需的最小语义说明，不替代这些真源。

## 4. 开放决策

本节已记录用户裁决：采纳 C1 最低契约；C3 不新增事务；C2 采用不可变 tag，破坏性变化另发版；产品发布契约声明支持的数据格式版本与机制特性；维持多进程直写，单 MCP 由下游自选。数据格式仅覆盖 SpaceMemory 拥有的信封、事件、机制配置及恢复维护语义，不覆盖调用者自定义类型、载荷业务含义和正文语义；SpaceMemory 执行的通用 schema／引用机制仍属于其格式契约。目录记录确切基础格式版本与整店必需机制特性；缺少任一必需特性的写入者拒绝整店受管写。新增特性先登记后使用，移除须显式核验或迁移。基础格式的版本支持集合、只读行为及迁移规则仍待裁决。

| 决策点（选项） | 现状与派生差异 | 必须在哪个节点前关闭 | 关闭条件 |
|---|---|---|---|

| C2 特性升级：先登记特性再写数据；或先写数据再补登记 | 先登记可能在崩溃后过度阻止旧版，但不会把含新语义的数据暴露给不支持者；后登记可能留下未标记的新数据，使旧版继续写入并丢字段。建议先登记；移除只经显式核验／迁移。 | 首个新增机制特性写入前 | 有崩溃注入证据证明不会出现“新数据已生效但必需特性未登记”；未知可选字段按规则保留。 |

| C2 防护基线：只承诺协议版本自动拒绝；或声称迁移可约束所有历史二进制 | 新协议可强制检查；历史程序没有这些检查，标记不一定能阻止它。首次切换需停掉并隔离旧写者；迁移后若历史解析器仍接受标记，它仍可能写入。依据：现有 Store 打开路径只解析 u32 格式号后探测可写性。建议保证范围仅覆盖已验证会早期失败的历史版本，其他旧程序由部署方隔离；不得宣称所有历史程序都被机制挡住。 | 防护格式首次迁移前 | 列明防护协议基线、迁移停机前提、已验证旧程序失败边界和不可验证旧程序的隔离责任。 |
| C2 兼容许可同步：写前一次检查；或检查与写入共享同步边界 | 一次检查后可暂停，另进程登记新特性，旧检查者仍继续写，破坏整店拒写承诺。同步贯穿检查到变更完成会阻止该交错，但特性升级需等既有写完成。建议共享同步边界；未满足时不声称特性拒写保证成立。 | 特性协议实现设计批准前 | 定义许可生效范围、全写路径参与方式、元数据新鲜读取和并集更新；加入真实进程受控暂停验收。 |
| C2 只读写盘：保持读取零写盘；或允许受支持派生能力自动持久化 | 允许索引／会话能力豁免会使只读请求写盘，违反现有红线，也可能在缺少写特性时绕过整店拒写。将维护作为显式写操作会增加一次调用，但写权限和事件语义可验证。建议维持零写盘；索引重建、flush 等单独走完整写门禁。 | 本需求批准前关闭 | 明确只读无持久副作用；所有维护写有独立公开入口并执行完整兼容检查。 |

## 5. 验收要求（本文批准后即为契约证据要求）

- **C1 单记录写与 CAS**：两个真实独立进程基于同一令牌更新同一记录；恰有一个写成功，另一个收到结构化冲突及成功写后的当前令牌，冲突操作不落盘且不追加自己的事件。
- **C1 竞争创建**：两个真实独立进程以同一逻辑身份并发创建；最终仅一份活记录，成功方得到创建结果，输者得到同一既有 ID 与当前令牌，不收到通用失败。另用不同逻辑身份确认二者均可创建。
- **C1 不同记录事件序**：两个或更多真实独立进程并发成功写入不同记录；从公开事件读取／校验入口核对每个成功操作各有对应事件，所有事件号唯一且按事件行顺序严格递增，无重复、缺口或成功操作漏记。各记录的本地版本号可相同，不影响全库事件序。
- **C1 写后可见性**：进程 A 的单记录受管写成功返回后，进程 B 随后读取该记录，必须观察到新版本，即使相应 Git 提交尚未完成。该测试不推导整次扫描快照。
- **C1 扫描边界**：用受控同步点使扫描在读取记录之间与另一进程的多条写交错；验收记录实际允许的混合观察，不把扫描结果冒称共同快照。若将来批准快照能力，再另验快照边界。
- **C1 引用边界**：分别验证普通删除按契约阻止或清理引用，以及公开强制删除成功时返回可观察的断链告警。
- **C1 死亡接管**：真实子进程在受控写操作阶段持有相关资源时被非正常终止；另一进程无需人工删除锁文件或重启机器，在有界时间内经公开 API 完成后续读写。验证退出前成功返回的操作仍可读且事件可对账；未成功返回的操作按契约给出恢复或待核验状态。超时须判失败。该证据不覆盖断电或存储设备故障。
- **C2 发布点不变性**：发布后记录 tag 所指提交对象；后续版本发布时再次解析旧 tag，必须仍指向同一提交及同一契约内容。破坏性变化必须使用新版本和新 tag，旧发布的 API、行为和格式说明保留可访问。
- **C2 格式与特性检查**：检查发布契约的基础格式版本及 `supported_features` 可机械读取；以目录清单包含已支持、缺失、未知特性三种情况验证接受／拒绝结果，拒绝时报告全部缺项。
- **C2 特性登记顺序**：在新增特性写入的登记与数据写入边界注入进程崩溃，证明不会出现新数据已提交而必需特性未登记；登记先完成后崩溃可以保守阻止旧版写入。
- **C2 格式边界**：提供调用者自定义 schema/payload/body 的跨版本样例，验证上游只按声明的通用承载能力处理，不把业务字段含义纳入迁移；同时验证信封、事件、机制配置及恢复维护语义按基础格式识别。
- **C2 历史程序切换**：记录防护协议基线；迁移前证明部署方已停止并隔离无防护历史写者。使用实际历史二进制样本验证迁移后公开打开路径在可写探测前失败；对未验证的历史程序，验收其隔离步骤，不把“标记存在”当作它会拒写的证据。迁移期间尝试以旧句柄继续写必须由停机前提排除。
- **C2 检查与写入交错**：真实进程 A 获取写许可后在受控点暂停；B 尝试登记新必需特性并写入依赖数据；A 恢复。只允许 B 等 A 的写边界完成后再升级，或 A 的旧许可失效并在落盘前复查后拒绝。禁止 B 已完成升级而 A 仍凭旧许可写入。另让两个进程并发登记 F、G，最终清单必须包含两者。
- **C2 只读零写盘**：让缺少某个写特性的程序按契约只读打开；读取前后比较真相层、事件、索引、会话和持久化派生状态，必须无变化。显式索引维护、session flush、reconcile 等写操作须分别通过完整兼容检查，缺特性时拒绝。既有运行时临时探针按原边界核对，不扩张为读副作用。
- **C2 数据目录迁移**：真实进程依次用支持与不支持相关基础格式／特性的版本访问同一目录，验证不支持者被拒绝；格式标记只在显式迁移成功后推进，失败保留旧标记或可识别的进行中状态；具备防护协议的已打开进程在每次写边界重新检查最新状态。
- **C3**：批量行为须按批准的选项验收失败与中途退出边界；若只汇总 Git 历史，测试不得声称受管写被回滚。集中写通道若另行立项，需独立验证所有受管写入口的集中性及服务退出时行为。
- **外部验收登记**：凡目标平台无法在开发机运行的真实进程测试，列为该平台外部验收证据，不用同进程模拟代替，也不作为当前机器无法执行的开发前置门禁。

## 6. 作者自曝三处

1. **历史版本切换依赖外部隔离**：旧二进制没有新协议检查，格式标记无法让已打开句柄失效。若无法证明部署方停掉并隔离全部无防护写者，就不能宣称首次迁移已防护；需要将此部署前置作为验收失败条件。
2. **同步边界覆盖全部受管写是核心机制承诺**：若任一写入口不参与同一许可边界，C2.8 的拒写保证即不成立。真实交错验收必须覆盖该入口，不能以单独测试元数据登记代替。
3. **只读严格零写盘**：索引重建、session flush 或 reconcile 不能从读取路径暗中触发。若需要这些持久化行为，必须作为显式维护写并经过完整兼容检查；现有临时探针边界不扩大。

## 7. 下游演进路径（背景）

1. **下游 v1**：库形态嵌入；SpaceTeam 自有进程经 mem-core API 写入，与其他进程共店。可依赖的并发与版本范围以最终批准并发布的 C1/C2 为准。
2. **候选方向**：下游可评估经工具协议访问。若目标要求 SpaceMemory 的 serve 成为唯一写者，则需单独补齐集中请求通道及入口收敛能力；这不是增加批量工具即可自然得到的结果，也不是本提案批准的架构。
