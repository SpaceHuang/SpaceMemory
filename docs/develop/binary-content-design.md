## 1. 缺口与现状（代码核验，2026-11-09）

先交代四个本文反复使用的概念：一条**记录**是一个文件，由**结构头**（信封：身份、类型、版本、引用等公共字段，JSON frontmatter）加**正文区**（结构头之后的一切字节，机制对其零解释）构成；**事件日志**是店目录内追加式的变更登记（每行一个事件，携带记录新旧全文摘要——与 git 无关）；**修订令牌**＝版本号＋整个文件字节的 SHA-256 摘要，用于写操作的并发校验。

R11 已定性缺口为"**写已通、读为零**"。读侧的全部有损点位（逐处代码核验，共 4 处——此数可在机层数出）：

| # | 点位 | 现状行为 | 消费方 |
|---|---|---|---|
| 1 | `mem-core/src/budget.rs` 正文分页函数 | 字节切片后按文本**有损解码**（非法字节替换为占位符，不可复原） | CLI `show` / MCP `mem_show` 的正文预览与分页 |
| 2 | `mem-core/src/search.rs` 命中谓词的正文分支 | 有损解码后做子串匹配——二进制字节的编码巧合可入命中（伪命中） | `find` 直读精筛＋快路径精筛（两执行器共用同一函数） |
| 3 | `mem-index/src/sqlite.rs` 物化（粗筛素材列） | 有损解码后折叠入正文素材列 | 快路径 LIKE 粗筛 |
| 4 | `mem-index/src/sqlite.rs` 正文素材同步 | 有损解码入正文素材 | 索引正文素材维护 |

写侧与审计侧已具备（无需增量，本文仅追认并补测试样本）：

- **两前端写字节保真**：CLI `add --body <文件|->`、`update --body-file` 原始字节读入原样落盘；MCP `body_b64` 传输编码解码后按原始字节落盘（既有裁决 M4）；
- **损坏发现**：`verify --deep` 对每条记录做"磁盘全文摘要 vs 事件日志最后登记摘要"对账，天然覆盖二进制记录；
- **关联与删除语义**：删除默认阻止并报告依赖方（全量反查信封引用清单）；越权删除后 verify 的悬空引用报告覆盖**类型载荷引用字段与通用 link 边两条建立路径**（两前端同构）。

**本设计的真实增量**（六件）：① 两前端的正文字节取回通道；② 检索正文域的参与门槛（伪命中收口）；③ 非文本正文预览降级；④ 损坏内容的恢复通道；⑤ git 字节直通补丁（跨机克隆不改字节）；⑥ 信封规范措辞收口（正文区定义）。

## 2. 设计总则（三条不变量）

- **G1 判定单源**："正文区是否合法 UTF-8"这一判定只实现一次（住 mem-core，输入=正文区全体字节），四个消费方（检索参与门槛、正文分页通道选择、文本预览降级、索引物化）只调用不复写。理由：本项目评审史反复复现"两套实现必然漂移"（同一命中谓词曾在两执行器间逐轮漂移，最终收敛为单源函数）。
- **G2 字节不经过文本域**：一切取回通道以原始字节为源。正文区合法 UTF-8 时，文本通道在数学上字节保真（合法 UTF-8 字节 ↔ JSON 字符串往返恒等）；不合法时文本通道**不可能**保真，必须走字节通道（CLI 落文件 / MCP base64 分页）。配套修正：**文本分页的切点对齐码点边界**（现状按任意字节切再有损解码，跨页拼装会丢页边界处的字节——文本正文多页取回同样不保真，属既有缺口，R11.2 收口时一并修复；页实际字节数因此可能少于预算至多 3 字节，续读偏移仍按字节计）。
- **G3 读路径零写盘不破**：取回通道的落点若是文件，写的是**调用方指定的工作区路径**，不是店内任何真相/缓存/锁/事件。读取路径零写盘这条红线约束的是机制自身状态（索引、事件日志、台账、检查点）——`--body-out` 无任何机制副作用（不追加事件、不动索引、不建台账、不留痕），因此**在只读存储上同样可用**（这是它的验证点之一）。

## 3. 分项设计（R11.1–R11.6 逐条）

### 3.1 R11.1 受管形态——零机制增量

信封机制的全部对象是结构头：身份、并发令牌、写入留痕（事件日志）、删除隔离（隔离区同路径字节不变）、引用完整性、校验——与正文字节无关；机制内部正文全链即为字节序列（写入原样落盘、分页按字节偏移）。因此二进制内容以记录形态入库**不需要任何机制改动**，受管形态自成立。跨机器迁移＝复制目录，验收 1 直接成立（复制不经任何解码）。清单/摘要被图记录挤占的缓解维持视图层手段（`list --type` 过滤），不改存放形态（既有裁决）。

唯一相关增量是 git 字节直通（见 BD5）：复制目录不经 git，但既定的多机同步通道（git 克隆）不得改字节，否则"另一台机器上的店"违反字节保真。

### 3.2 R11.2 字节保真——读回通道（→BD1/BD2/BD3）

**承诺**：写入字节与读回字节完全一致（两前端的写与读）。**机制**：取回通道以字节为源（G2）；结构头的机制再生成只重写 frontmatter、正文按字节保持（既有纪律，不变）。**验证点**：验收 1/4/7 的哈希断言，且必测**非法 UTF-8 正文**用例（合法 UTF-8 正文两通道天然一致，测不出通道缺陷）；另补**合法 UTF-8 正文跨多页拼装**的哈希一致用例——锁定切点码点对齐修复（G2）后文本通道的分页拼装恒等。

| 前端 | 文本正文（合法 UTF-8） | 非文本正文（非法 UTF-8） |
|---|---|---|
| CLI `show` | 正文预览分页（现状，切点改码点对齐） | 预览＝占位描述符（≤128 字节，含字节数/摘要前缀/取回指引）；字节经 `--body-out <路径>` 全量落文件 |
| MCP `mem_show` | `body` 文本分页（现状，切点改码点对齐） | `body=null`＋`body_b64` base64 分页（页=brief_bytes 个**原始字节**，`resume.body_offset` 按字节计） |

`--body-out` 的stdout 只回元信息（路径、字节数、正文 SHA-256）——哈希回显让验收 1/7 的对源断言可在管道内完成。约束两条：目标已存在 → 响亮拒绝（读命令不做覆盖写）；目标位于店目录内 → 响亮拒绝（防止经读通道在店内产生信封管辖外的旁挂文件）。

### 3.3 R11.3 关联确定——零机制增量（补测试）

两条引用建立路径均既有且载体明确：**类型载荷引用字段**（类型声明中标注 x-ref 的字段——写入时同步登记进信封引用清单，即"镜像纪律"）为主；**通用 link 命令**（直接往信封引用清单加边）为兜底。删除默认阻止并报告依赖方（全量反查）；越权删除后 verify 的悬空引用报告遍历**全部**信封引用（覆盖两条路径，两前端同构）；类型镜像另有按声明核对的双向审计。本条无机制改动，验收 3 以图记录样本落入既有测试面。

### 3.4 R11.4 文本路径不受染——检索收口（决策④(b) 落地）

**门槛**：正文域（四个检索域——身份前缀/别名/载荷值/正文——之一）的参与前提＝该记录正文区是合法 UTF-8；不合法 → 正文域不参与，其余三域照常。判定即 G1 单源谓词。

- 命中谓词正文分支：合法 → 现状子串匹配；不合法 → 恒不命中（**不经过有损解码**——现状"有损解码后匹配"被本设计废除，基线 R10.2 已注记由 R11 落地时收口）；
- **索引素材契约（保持非空，零 schema 迁移）**：正文素材列（正文文本列与折叠列）对非文本正文写**空字符串**，合法正文照常写折叠文本。契约依据：素材列 schema 为非空（`TEXT NOT NULL DEFAULT ''`）、行类型为 `String`、既有迁移只增列不解除非空——空串方案三者零改动；空串对任何非空查询的 LIKE 恒不命中，"无正文检索素材"语义成立。**"非文本正文"与"合法 UTF-8 空正文"同为空串、不需要区分**：素材列唯一职责是粗筛超集（给候选，不定命中），两态在粗筛层行为恒等（都不产生正文域候选），正文域真值由 G1 单源谓词在精筛层裁定。

**预算对账**（"图不推高文本访问成本"——各响应面正文字段现状，可数）：brief 条目＝{id, type, modified, token}（无正文）；list 条目＝{id, type, rel, token}（无正文）；trace 节点＝{id, rel, depth}（无正文）；show 正文受 brief_bytes 预算（默认 16384 字节，配置项），非文本正文降级为 ≤128 字节描述符——**一条带图记录的任何读响应都不随图体积增长**。

### 3.5 R11.5 取回对等——两前端同批

字节取回是两前端同批义务（对等原则：新增能力须同批落两端）：CLI 通道＝`show --body-out`；MCP 通道＝`mem_show` 的 `body_b64` 分页（宿主无文件系统访问，"定位→钻取→取回"全链在协议内闭合）。恢复命令同理同批（BD4）。对等的验证形态＝验收 4（协议档全链）＋验收 7（CLI 对等抽验），两侧同用例源。

### 3.6 R11.6 损坏可治愈——发现追认＋恢复通道（→BD4）

- **发现**：`verify --deep` 的"磁盘 vs 事件日志"摘要对账已覆盖二进制记录（追认为验收承诺，分档不变——浅档不做摘要对照）；
- **恢复**：新增经确认的内容写操作 `restore-body`（CLI）／`mem_restore_body`（MCP）——正文区替换为**来源字节**，信封（版本、时间戳除外）与载荷原样保留，走既有更新写路径（共享门闩/记录锁/全摘要令牌校验/事件追加/git 同批提交），事件操作名 `restore_body`，事件照常携带恢复前/后全文摘要（审计痕）；
- **来源三形与责任分界**：`git:<版本>`＝指定历史版本的正文区；`file:<店外路径>`＝店外备份的记录格式文件，取其正文区；`history`＝自动锚定，仅在可机械判定的窗口内可用（见下）。**机制保证与调用方确认显式分离**——机制保证：来源字节被完整复制（落盘正文区摘要==来源正文区摘要，不符即响亮失败、不留半成品）、动作留痕、**来源出处回显**（响应携带：来源形态、锚定摘要或版本、复制前后摘要——供调用方复核）；来源可信性：`git:<版本>`/`file:` 由调用方显式选择承担，`history` 是唯一的机械锚定形态，且其可判定性本身是输出的一部分。机制校验字节完整复制**不能**替代调用方对来源可信的确认；
- **`history` 自动锚定的可用窗口**（两条件同时成立才可用）：
  1. **漂移仍在**：磁盘全文摘要 ≠ 该记录最后事件的登记摘要。此刻最后事件登记的恰是"外部改动前机制最后写入的字节"——漂移的成因只有一种（磁盘被外部改动而日志未登记），机械无歧义；
  2. **最后事件是机制写入登记**（受管写操作产生，非回填）：机制写入的字节随写路径同批提交进 git，**常态下**锚摘要可在历史中找到——两形例外：commit-pending 未收敛（blob 尚未进入历史）与无 .git（git 缺席的合法形态）。例外下扫描无匹配 → **响亮失败**（错误信息区分成因：等待 pending 提交收敛后重试，或改用显式来源），**绝不回退到次优匹配**；无 .git 的店 `history` 与 `git:<版本>` 源整体结构化报错（git 缺席即无历史通道，`file:` 源仍可用）。回填事件的登记摘要描述的是**外部字节**（可能是损坏本身，也可能是合法手改——机械不可分辨），不得作可信锚。

  窗口内：锚＝最后事件登记摘要，自新至旧扫 git 历史取全文摘要相符的版本、用其正文区（无匹配如上响亮失败）。**窗口外**（已收敛——损坏经回填登记、或损坏后发生过合法更新使最后登记＝盘上字节；或最后事件为回填）：**响亮拒绝**自动锚定，不得声称能推出损坏前版本，更不得把盘上（可能损坏的）字节写成新版本冒充治愈；响应附可行动指引——该记录最后机制写入登记的摘要，及 git 历史中匹配该摘要的版本（若找到），引导显式 `git:<版本>` 或 `file:`；
- **读不崩溃**：正文全链按字节处理，解码失败只影响展示层（描述符）——损坏记录上五个读命令（brief/list/show/trace/diff）＋verify 全部可用。**验证点**：验收 6 构造翻转字节样本逐命令跑通。

**操作组合**（复合损坏的处置序）：结构头坏 → 先 `fix`（保正文字节的结构修复）；正文坏 → `restore-body`（换正文字节的内容写）；两者皆坏 → 先 fix 后 restore-body。两类操作的字节纪律相反（一保一换），故**不共用命令面**——这正是 r6/r7 评审在基线收口的分界，命令面与其对齐。

## 4. 决策条目（BD1–BD6）

本轮需要人拍板的六项形状裁决。正文用表现语言，锚点只在下钻。

### BD1 CLI 字节取回通道形状

- **背景**：命令行前端需要一个不经文本解码的正文字节出口——字节取回是两前端的同批义务（前端功能对等）；钻取命令 `show` 现有正文输出按文本截断解码。
- **选项**：(a) `show` 增参 `--body-out <路径>`——正文原始字节全量写至调用方指定文件，stdout 只回元信息；(b) 新命令 `cat <id>`——正文字节直接写 stdout；(c) 维持现状（人手直接读记录文件）。
- **后果**：(a) 破坏了会怎么表现——钻取多一个参数、无新命令；写出的文件是普通工作区文件；给店内路径或已存在路径会被拒绝。(b) 破坏了会怎么表现——stdout 变二进制管道，人读与脚本混用同一出口，令牌等结构化回显无处安放，与"钻取返回令牌"的既有约定断裂。(c) 破坏了会怎么表现——命令行宿主取回字节必须直接读记录文件并自行剥结构头，格式一变脚本全坏，等于把义务推给人手。
- **可逆性**：(a) 参数可加可弃，无数据迁移；(b) 脚本依赖形成后移除有成本；(c) 无从谈起。
- **依据强度**：已验证——show 现有分页/预算机制与字节偏移续读；未验证——无（纯接口形状）。
- **推荐＋默认**：(a)。人不决定时按 (a) 实施。
- **下钻**：R11.5、基线验收 7；r4 评审"通道形状留设计阶段"；`crates/mem/src/cli.rs` Show 参数。

### BD2 MCP 字节取回通道形状与分页语义

- **背景**：完整工具协议档宿主无文件系统访问，字节必须经工具响应交付，响应是 JSON 文本。
- **选项**：(a) **响应自适应**——正文区合法 UTF-8 时维持文本分页（现状）；不合法时 `body=null`、正文页以 `body_b64`（base64）交付，另加恒有字段 `body_utf8`；分页偏移按原始字节计，页大小沿用 brief_bytes（单位＝原始字节；JSON 内 base64 膨胀 4/3 属传输编码开销，不改变预算语义——传输编码只是保真通道，与既有写通道 base64 定性一致）。(b) 请求参数强制选模式。(c) 新工具 `mem_show_binary`。
- **后果**：(a) 破坏了会怎么表现——宿主无需声明模式：非文本记录的文本通道本来就不可能保真，自适应不存在"选错"；响应多一个恒有字段、一个条件字段。(b) 破坏了会怎么表现——宿主必须先知道正文形态才能选对模式（先知问题）；两模式两套分页语义要长期对齐。(c) 破坏了会怎么表现——工具面 +1、钻取语义分裂（同一记录两个入口），"定位→钻取→取回"要跨工具。
- **可逆性**：(a) 加字段向前兼容（旧宿主忽略新字段），可随时增补；(b)/(c) 面收窄更难。
- **依据强度**：已验证——写通道已有同构 base64 传输编码先例（既有裁决：写字节保真通道）；"合法 UTF-8 ↔ JSON 字符串往返恒等"是编码性质（故文本通道对合法正文保真成立，见 G2）；未验证——超大正文多页取回的宿主体验（挂开放问题，见自曝第 1 处）。
- **推荐＋默认**：(a)。
- **下钻**：R11.2/R11.5、基线验收 4；写字节保真通道裁决（设计文档 v1.2 修订行 M4）；`crates/mem-mcp/src/tools.rs` body_b64 既有描述；`crates/mem-core/src/budget.rs` 分页单源。

### BD3 非文本正文的预览降级形状

- **背景**：钻取输出的正文预览现状对非文本正文做有损解码——输出乱码、浪费返回预算、把替换字符混进宿主上下文。
- **选项**：(a) 占位描述符——CLI `body` 字段放单行描述符（模板固定：字节数＋正文摘要前缀＋取回指引；总长上界 128 字节），MCP `body` 置 null（字节由 `body_b64` 承载），两前端恒有 `body_utf8` 布尔字段供机判；非文本预览不再分页（描述符后 `resume=null`）。(b) 维持有损预览（现状）。(c) 预览整体省略（body 恒空）。
- **后果**：(a) 破坏了会怎么表现——人读钻取输出看到"这里有一段 N 字节的非文本正文"而非乱码；机判靠 `body_utf8`，不会把描述符误当正文。(b) 破坏了会怎么表现——乱码入上下文；替换字符序列还可能携带巧合子串，污染宿主侧任何拿预览当正文的文本处理。(c) 破坏了会怎么表现——文本记录的人读体验受损（正文预览是钻取价值的半边）。
- **可逆性**：描述符模板可调，机制无迁移。
- **依据强度**：已验证——有损解码点位（§1 表第 1 行）；未验证——无。
- **推荐＋默认**：(a)。
- **下钻**：R11.4；红线9（预算内显式标注）。

### BD4 损坏恢复通道形状

- **背景**：深档审计发现"盘上字节与事件日志登记摘要不符"之后，把可信字节写回的路径现状只能两步走（先取历史字节落文件，再走通用更新命令）——而通用更新命令要求**整份载荷重发**（既有裁决：更新命令的载荷参数必须显式提供，防静默清空），宿主转写载荷走样时并发校验**不报警**（它只对整文件摘要负责）——修复路径自带"坏图修好、载荷坏了没人知道"的静默二次损坏窗口；且"来源是否可信"没有机制内锚定。
- **选项**：(a) 独立恢复命令（CLI `restore-body`／MCP `mem_restore_body`）：一步完成"取来源字节 → 机制内校验复制保真 → 以既有更新写路径落盘（载荷与信封原样保留、正文替换、版本＋1、事件留痕 `op=restore_body`）"；来源三形、`history` 可用窗口与责任分界见 §3.6。(b) 两步通用件（取历史字节的只读命令＋通用更新命令）。(c) 修改通用更新命令的载荷语义（缺省＝保留现载荷）。
- **后果**：(a) 破坏了会怎么表现——命令面 +1（CLI 子命令 21→22、MCP 工具 14→15）；恢复动作在事件流有专属操作名，事后可辨识；事件流新增操作值带来一次读取侧前向兼容断点（处置见迁移节）。(b) 破坏了会怎么表现——载荷转写窗口如背景所述；来源无机制内锚定，恢复错版本无从拦截。(c) 破坏了会怎么表现——与"载荷缺省必须显式"的既有裁决正面冲突，重开波及全部写路径。
- **可逆性**：(a) 命令可移除；历史事件中的操作值由读取侧兜底容忍（迁移节）。(b) 无表面变化。(c) 语义回退需再修。
- **依据强度**：已验证——更新命令载荷必填语义及其裁决原因（载荷缺省＝静默清空，既有裁决拒收）；漂移成因唯一（磁盘外部改动而日志未登记），故窗口内"最后事件登记摘要＝外部改动前机制写入的字节"，且该字节随写路径同批提交（批次构造核验：记录路径与事件日志同批）——**常态下**在 git 历史中；commit-pending 未收敛与无 .git 两形下可能缺席，此时无匹配即响亮失败并引导显式来源（§3.6，不构成静默路径）；回填事件登记摘要描述外部字节（事件行结构核验）。未验证——深历史的扫描耗时（自曝第 3 处）。
- **推荐＋默认**：(a)。`history` 仅在 §3.6 窗口内自动锚定，窗口外响亮拒绝并附指引——不做静默选择。`restore-body`／`mem_restore_body` 为占位名，最终命名随工具面定稿收口（§9 第 3 条；本轮批准的是形状与语义，不是名字）。
- **下钻**：R11.6、基线验收 6；r6/r7/r8"恢复接口参数形状留设计阶段"；M4 裁决（设计文档 v1.2 修订行）。

### BD5 git 策略落地与字节直通

- **背景**：版本历史对图字节默认全量跟踪已裁决（无机制内排除）。但 git 的行尾自动转换（core.autocrlf / text=auto）会把"提交时的字节"与"检出时的字节"改得不一致——行尾配置激进的用户克隆后，盘上字节即与事件日志登记摘要永久不符（深档审计永久报漂移、修订令牌跨机失效）。这不是图独有问题——机制写文件统一 `\n` 且正文按字节保持，文本记录同样受害；图的字节保真把它变成必须收口的口径。
- **选项**：(a) 店级 `.gitattributes` 固定一行 `* -text`（全店禁行尾转换——提交什么字节、检出什么字节），**闭合四件套**：① init 写入并随首次提交入树；② 写例程核验——工作区缺失则补种并把该文件**纳入当批按路径提交**（commit-pending 批次同样携带，直至核验入树）；③ 工作区已存在且内容不同 → **结构化拒绝受管写入**，附修复指引（恢复默认内容即解锁；读路径不受影响）；④ verify 增审计项——有 .git 的店，`.gitattributes` 已在**提交树**中且内容相符。无 .git 的店不适用（git 缺席即无行尾转换问题）。(b) 依赖用户自行配置（文档教学）。(c) 机制内置按类型/大小的排除语法。
- **后果**：(a) 破坏了会怎么表现——用户在店内的行尾习惯被统一（店内文件字节以写入时为准）；店外仓库不受影响；自带自定义 `.gitattributes` 的店在恢复默认内容前**一切写命令被拒**（读路径不受影响——仍可审计与导出），这是"建立并核验后才允许受管写入"的直接代价；既有跨机已同步店铺中，若历史同步已改过字节，加 `-text` 不改已检出文件，但深档审计会**如实**报出既有分叉（暴露旧伤，非引入新伤，见自曝第 2 处）；存量店升级后**首次受管写入之前**克隆仍拿不到规则（规则随当批提交入树），该窗口内的克隆仍可被转换（见迁移节注记）。(b) 破坏了会怎么表现——教学拦不住机制外行为：任一台机器配置不当，同步后该机永久漂移且难定位成因。(c) 已被裁决排除（默认全量跟踪；确有大库负担的走各库自管排除约定，机制不内置、不读取、不维护——按库排除的后果（修改历史断档）由需求阶段已裁决的后果条款承担）。
- **可逆性**：(a) 删文件并提交即回默认行为。
- **依据强度**：已验证——行尾转换改字节是 git 文档化行为；机制写文件的 `\n` 统一与字节保持纪律；既有提交批次构造只含调用方给出的记录路径与事件日志（批次代码核验）——"规则文件落在工作区"≠"进入同步历史"，必须显式入批，这是闭合四件套的直接依据。未验证——既有店铺中该问题的实际发生率。
- **推荐＋默认**：(a)。
- **下钻**：需求决策⑤（裁决 a）；R11.1/R11.2；envelope 规范 §2.5（字节确定性）。

### BD6 信封规范修订（正文区定义）

- **背景**：信封格式规范现文两条按字面把非文本正文区判为不合规——"文件编码 UTF-8"（整文件口径）与"正文＝载荷自由**文本**"。实现早已按字节处理正文，规范措辞需收口到与已裁决形态一致；规范与实现冲突处以规范评审结论为准是本仓库纪律，悬置不修即纪律失效。
- **选项**：(a) 小版本修订三处：① 正文区＝首个闭合分隔符行之后的**任意字节序列**（文本是常见形态，非唯一合法形态；空正文合法不变）；② "UTF-8、无 BOM"约束收窄到结构头区（文件头判定维持）；③ 事件操作枚举补 `restore_body`（随 BD4）。(b) 大版本重定义物理格式。(c) 不修（留给将来）。
- **后果**：(a) 破坏了会怎么表现——规范读者需看小版本修订行；旧读者按旧文理解不产生错误行为（旧文描述的是常见形态）。(b) 无必要——三段式、分隔符、确定性序列化一字未动。(c) 破坏了会怎么表现——规范权威名存实亡，后续一切"以规范为准"的裁决失去地基。
- **可逆性**：(a) 修订行回退即可（版本与修订行由用户主导）。
- **依据强度**：已验证——规范现文两条字面（§2.1 构成第 3 条、§2.5 编码条）；实现正文全链字节（写入原样、分页按字节偏移）。
- **推荐＋默认**：(a)，批准后按规范修订流程落。
- **下钻**：AGENTS.md §2 规范权威关系；`docs/specs/envelope-format.md` §2.1/§2.5/§4.1。

## 6. 排除方案（选了什么、为什么排除另一个）

1. **stdout 原始字节模式**（BD1-b 落选）——与结构化回显/令牌约定冲突；
2. **请求参数强制模式 / 独立二进制钻取工具**（BD2-b/c 落选）——先知问题与工具面分裂；
3. **有损预览保留 / 预览全省**（BD3-b/c 落选）——乱码入上下文 / 文本体验受损；
4. **两步恢复 / 改更新载荷语义**（BD4-b/c 落选）——转写静默窗口 / 重开既有裁决；
5. **类型声明级二进制标记作排除标准**——需求决策④已裁决机械可判定标准（漏声明类型会让伪命中静默回归），本设计不重开；
6. **LFS／外置旁库**——需求决策⑤(c) 已否决（迁移＝复制目录破例）；
7. **按扩展名的 .gitattributes 规则**（如 `*.png binary`）——机制对类型零知识，不可枚举全部二进制类型；`* -text` 全店字节直通一并覆盖文本记录。

**设计自有验证点**（本设计承诺的机制验证——承诺配对落点，非基线验收的重定义）：

1. **git 克隆字节直通端到端**（真实 git 子进程，随 mem-git 测试面）：源机提交含非法 UTF-8 正文与含 CRLF 正文的记录 → 断言 `.gitattributes` 已在提交树（HEAD 中内容恰为 `* -text`）→ 在强制 `core.autocrlf=true` 的环境新克隆 → 逐字节核对记录文件 == 源机版本，且事件最后登记摘要 == 克隆机磁盘摘要（BD5 承诺：克隆通道不改字节）；
2. **冲突 .gitattributes 行为**：工作区内容 ≠ 默认 → 受管写入结构化拒绝（错误含修复指引）；五个读命令与 verify 仍可用；恢复默认内容后写路径解锁（BD5 闭合四件套之 ③）；
3. **索引素材契约**：非文本记录物化成功（无 NOT NULL 违规）、快路径 brief/list/find 读取不报错（并入验收 5 断言，此处单列机制归属）。

## 9. 开放问题（本设计新增/触及，建议随批准登记）

## 11. 自曝三处

1. **base64 分页的宿主成本未实测**：64 页/MB 的拼装在真实宿主（工具响应截断、上下文预算）下的表现纯推演。*什么证据会推翻*：实测宿主多页拼装出错或上下文超限 → 需调大单页预算、或补一次性全量导出的宿主导引（加请求参数），BD2 的自适应形状不变。
2. **`* -text` 可能揭开既有跨机库的旧伤，且存量店存在升级窗口**：历史同步若已被行尾转换改过字节，规则入树后深档审计开始如实报漂移，用户可能归因于新版本；存量店在升级后首次受管写入之前克隆，规则尚未入树，该窗口内的克隆仍可被转换。*什么证据会推翻*：升级后出现集中于是前已多机同步店铺的大面积"新发"漂移报告且既有回填无法收敛 → 需一次性对账收敛例程或迁移指引（含升级即补种而非随首次写入补种），BD5 的落地顺序重排。
3. **history 源的深历史扫描成本未实测**：自新至旧逐版本取文件、算摘要，典型库首数个版本即命中锚点，深历史才退化（O(历史长度)）。*什么证据会推翻*：大库实测恢复命令分钟级 → 限制扫描窗口（事件日志可给出候选提交的时间下界）或缓存按路径的历史摘要。

## 13. 术语与锚点

| 术语/锚点 | 含义 |
|---|---|
| 正文区／结构头 | 记录文件中首个闭合分隔符行之后的一切字节（机制零解释）／其前的 JSON frontmatter（信封＋载荷两块，机制拥有信封） |
| 有损解码 | 把字节按 UTF-8 强行解释、非法序列替换为占位符的读法——字节从此不可复原（本设计废除其在读路径的全部 4 个点位） |
| 事件日志 | 店内追加式变更登记（一行一事件，含记录新旧全文摘要与路径；序号＝行序；与 git 无关） |
| 修订令牌 | 版本号＋整个文件字节的 SHA-256；写操作必带并在锁内比对（并发校验） |
| 预算（brief_bytes） | 单次响应的正文字节预算，mem.json 配置，默认 16384；截断必须显式标注并给续读 |
| 深档审计 | verify --deep 的磁盘摘要 vs 事件日志摘要对账（浅档不做摘要对照） |
| x-ref 镜像 | 类型载荷引用字段写入时同步登记进信封引用清单的纪律；verify 按类型声明双向核对 |
| link 边 | 通用引用命令直接写入信封引用清单的边（不经类型载荷） |
| 占位描述符 | 非文本正文在文本预览位的单行替身（字节数＋摘要前缀＋取回指引，≤128 字节） |
| history 锚点 | restore-body 自动锚定的**可用窗口**＝漂移仍在（磁盘全文摘要≠最后事件登记摘要）∧ 最后事件为机制写入登记（非回填）；窗口内锚＝最后事件登记摘要（对应 git 历史中随写路径提交的版本）；窗口外响亮拒绝，附最后机制写入登记摘要与匹配的历史版本指引；锚在历史中无匹配（commit-pending 未收敛／无 .git）→ 响亮失败引导显式来源，不回退次优匹配 |
