# macOS 文件变化订阅实施方案（FSEvents）

## 评审摘要

**本轮建议批准范围：** 接入 FSEvents 作为索引后台维护的变化提示，并在无法确认监视根仍有效时停止订阅。FSEvents 的刷新返回和当前回调计数为零，**不作为查询可使用索引的证明**。因此本轮 macOS sidecar 仍报告 `backend="none"`，macOS 查询仍直接读取记录文件；不得新增 `fsevents` 快路径或把它写成受支持的 freshness 后端。

原因是 FSEvents 能帮助发现并处理目录变化，但目前证据不足以证明某次刷新已交付所有此前完成的写入。Watchman 官方文档记录了较早文件修改通知晚于 cookie 通知及同步刷新返回的情况。对同尺寸且保留 mtime 的改写，stat 检查点也无法识别差异。因此本方案不以重复刷新、等待、cookie 或压测未复现来补足同步保证。若未来提出独立的查询同步机制，须另立方案，给出其保证来源、边界和可控延迟通知验收，并先完成设计裁决；未完成前索引快路径保持关闭。

本轮不改变记录、事件日志或索引格式，不改变 Windows 行为，不修改总体设计版本与修订记录，也不关闭开放问题39。当前实现没有 macOS FSEvents 代码，macOS freshness 订阅能力仍为 `none`，查询采用直接读取。

### 本轮待批准

1. 每个 store 建立一个 FSEvents 流，监视 `records/` 与 `attic/`，启用 `kFSEventStreamCreateFlagWatchRoot`，并把根变化、丢失标记及覆盖身份无法确认统一视为订阅失效。
2. 将 FSEvents 变化作为后台索引维护提示；回调不读写 store。它不改变 freshness 订阅状态，不发布可供查询使用的 FSEvents 检查点，握手后端仍为 `none`。
3. 定义订阅信号取走、回调并发、维护失败回注和同次握手失效传播，避免事件欠账丢失或对外状态滞后一轮。
4. 真实 macOS 根目录移动/替换验收及回退演练完成后，才允许合入该维护提示实现；本轮不包含启用索引快路径的批准。

本轮明确不批准：用 FlushSync 计数为零证明新鲜、以 FSEvents 报告 `backend="fsevents"`、通过 stat 等价性替代通知覆盖证明，或放宽“首次查询不得返回旧值”的要求。

## 1. 问题与安全边界

索引是记录文件的可丢弃副本。只有 freshness 流程能够证明索引反映当前记录内容时，查询才可使用索引；无法证明时必须直接读取记录文件。直接读取较慢，但其正确性不依赖索引是否新鲜。

macOS 当前没有可用于 freshness 的变更订阅，因此查询始终直读。接入 FSEvents 后，本轮仅让 sidecar 更及时地维护后台索引，不改变上述查询判据。FSEvents 刷新可以触发或协助收敛维护，但不能单独证明此前所有写入通知均已到达。尤其是等长、恢复 mtime 的内容改写，stat 也无法弥补通知延迟。

因此需区分两个问题：

| 问题 | 本轮答案 |
|---|---|
| 是否有变化提示可用于安排后台维护？ | 有，FSEvents；发生覆盖不确定时停止订阅 |
| 能否据此让查询使用索引？ | 不能；继续 `backend="none"` 并直读 |

## 2. 术语

| 词语 | 含义 |
|---|---|
| FSEvents | macOS 目录变化通知服务。系统可能合并变化，通知用于提示检查/维护，不是完整逐文件操作清单。 |
| sidecar | `mem serve` 启动的后台进程，负责维护索引并经本地 socket 回答状态查询。 |
| freshness 订阅 | freshness 流程用来证明检查点以来变化连续覆盖且已消化的订阅。本轮 FSEvents 不注册为此类订阅。 |
| 维护提示 | 促使 sidecar 后台更新索引的信号；缺失或延迟不会使查询信任索引，因为查询仍直读。 |
| 根身份 | 被监视目录及其路径祖先当前指向的目录对象。路径名相同不代表目录对象未被移走或替换。 |

## 3. 实施方案

### 3.1 监视范围、根身份与启动顺序

每个 store 建立一个 FSEvents 流，同时监视 `records/` 与 `attic/`。两个目录都影响索引维护；任一根路径不能监视或身份无法核验，整体订阅不得报告为有效维护提示。FSEvents 不监视 `index/`，避免索引写入触发自身维护。

流创建必须启用 `kFSEventStreamCreateFlagWatchRoot`。该标志请求监视根路径及祖先路径变化通知；收到 `RootChanged` 后立即不可逆地使该订阅失效，并停止将其信号用于维护。`MustScanSubDirs`、`UserDropped`、`KernelDropped`、流停止、回调线程异常和刷新/读取错误同样使订阅失效。失效后本进程生命周期内不重建；sidecar 重启后重新建立。

WatchRoot 是通知机制，不是本方案的查询同步证明。建立流时还须记录 `records/`、`attic/` 的文件系统身份（至少设备号与文件标识），在启动后及每次维护开始和结束时复核；不能读取身份或身份改变即失效。对 store 祖先改名、卷卸载/重新挂载及根路径暂时不存在的情形，任一复核失败均视为覆盖不确定。复核是检测根对象替换的额外护栏，不使 FSEvents 成为 freshness 后端。

启动步骤：

1. 确保两个目录存在，并读取 store、`records/`、`attic/` 的根身份。
2. 创建启用 WatchRoot 的流，安排回调队列并启动；启动失败则无维护提示订阅。
3. 启动成功后进行一次完整索引物化。期间任何变化均只标记维护待办。
4. 完成物化后刷新并检查根身份；若观察到普通变化则按维护循环再做一次物化。沿用现有最多四轮收敛上限，但该上限只约束后台维护，不表示 freshness 已证明。
5. 后台维护完成后，索引可供诊断或后续维护使用；握手仍返回 `backend="none"`、`undigested` 按 none 语义处理，查询保持直读。

Apple API 文档描述流需先安排到运行队列或 RunLoop 再启动；WatchRoot 标志用于请求根路径变化通知。即便刷新同步返回，也不据此宣称此前所有修改均已送达。

### 3.2 运行时维护提示与信号账务

回调只更新线程安全的待办状态，不读写 store、不扫描文件、不执行索引物化。普通变化将待办置为有信号；事件标志提示覆盖缺口或根变化时，原子地进入失效状态，后续信号不得把失效状态清回正常。

信号处理采用不丢账的合并语义：

1. 维护循环以原子交换方式取走当前待办代次；取走只转移责任，不表示已处理。
2. 取走后到维护结束前新到的回调写入下一代待办，不能被本轮清零覆盖。
3. 仅在索引维护成功且结束时根身份复核通过后，才确认本代待办完成。
4. 维护失败、四轮未收敛、刷新失败或根身份复核失败时，将本代欠账回注；若已失效则直接保留失效状态，不再声称维护提示连续。
5. 下一次握手/维护轮必须仍可观察到未完成待办或失效，不得因一次失败而报告干净状态。

这些计数仅供维护调度，不是 freshness 的 `undigested` 证明，不得传入允许索引快路径的判定函数。

### 3.3 失效与降级

以下情形使维护提示订阅在本进程生命周期内失效：

- 收到 `RootChanged`、`MustScanSubDirs`、`UserDropped` 或 `KernelDropped`；
- 任一被监视根、store 祖先或卷身份复核失败或变化；
- 流停止、回调队列退出、创建/启动/刷新失败，或平台句柄报告不可恢复错误；
- 事件信号状态无法安全读取或维护欠账无法回注。

失效时立即停止并释放流，将维护订阅置为不可用。查询端始终使用 `backend="none"` 和直接读取。允许 sidecar 继续提供其他服务；是否停止后台索引维护由现有维护器错误处理决定，但不得把失效后的索引状态对查询宣称为新鲜。sidecar 重启才重新尝试建立维护提示。

### 3.4 Sidecar 接线和握手

- 在 `crates/mem-core/src/platform/macos.rs` 封装流创建、WatchRoot 标志、根身份读取、事件标志解析、停止和释放；不向 sidecar 暴露原始 FFI。
- 在 `crates/mem-core/src/sidecar.rs` 将其作为维护提示句柄接线，和 freshness 订阅抽象分开；不得让 `backend()` 将其映射为 `fsevents`。
- `Hello.backend` 保持 `none`，`Hello.undigested` 保持 none 后端语义。配置中的受支持后端不得写入 `fsevents`，不得改变客户端快路径判定。
- 同次握手须传播本次 freshness 检查或维护过程中发现的失效，不能先用旧订阅值生成 Hello、下一轮才清理。虽本轮后端始终 none，该传播仍需覆盖维护状态与配置，避免状态滞后及后续接线错误。
- 维护失败回注与下一次握手观察到欠账的测试作为接线验收；注入接口仅服务维护提示测试，不构成 freshness 订阅。

FSEvents 属 CoreServices 系统 API。编码前核对 Rust 绑定 crate 的维护状态、许可证、Rust 版本和 ABI 覆盖；没有满足要求的绑定时，先审查最小平台封装。仅 macOS 目标链接 CoreServices，其他目标不引入链接依赖。

### 3.5 与 freshness 规则的关系

现有 freshness 规则要求查询只在“stat 检查点一致且订阅覆盖连续、没有未消化变化”时使用索引。本方案不改变该规则，也不声称 FSEvents 满足其中的覆盖证明条件。

FSEvents 刷新返回且维护待办为空，只表示维护调度当前没有已观察到的普通事件；由于存在通知晚到的已记录限制，它不能推出此前所有已完成写入都已回调。因此不能返回 `Some(0)` 给 `consult_with_hello`，不能据此发布可供查询使用的收敛检查点，也不能将握手后端改为 `fsevents`。后台索引维护不影响查询正确性。

未来若要启用 macOS 索引快路径，需另行提出决策，至少说明：独立同步保证的权威来源和适用边界；等长保 mtime 改写且通知被可控延迟时首次查询仍返回新内容的测试；根路径覆盖的真实 API 接线证据；以及失败、恢复和回退语义。固定等待、重复刷新、cookie 或有限压力测试均不单独满足该条件。

## 4. 状态变化

```text
未建立维护提示
  ├─ 创建/启动成功且根身份可核验 → 维护提示正常
  └─ 创建/启动/身份核验失败 → 无维护提示；查询直读

维护提示正常
  ├─ 普通事件 → 记录待办 → 后台维护 → 成功确认本代 / 失败回注
  └─ 根变化/通知缺口/线程或流失效 → 释放流 → 无维护提示

所有状态下的查询
  └─ freshness backend=none → 直接读取记录文件

sidecar 重启
  └─ 重新核验身份并建立维护提示；查询仍直读
```

## 6. 方案取舍

| 选项 | 结果 | 破坏时的表现 | 可逆性 / 依据 | 结论 |
|---|---|---|---|---|
| 维持现状：macOS 不接 FSEvents | 查询直读；没有后台通知维护 | 查询正确但始终扫描记录，索引维护不能及时响应 | 完全可逆；当前行为已由代码确认 | 作为安全基线 |
| 接入 FSEvents，仅作维护提示 | 后台可响应目录变化；查询仍直读 | 通知晚到会让后台索引短暂落后，但不会返回旧答案；根身份不确定则停止提示 | 可逆，不改持久格式；API 接线和真实卷行为尚待验证 | **本轮推荐批准** |
| 用 FlushSync 零计数开放查询快路径 | 可尝试提高查询速度 | 已记录的通知晚到场景可使等长保 mtime 改写返回旧索引 | 现有证据不能支持其同步保证 | 不选；违反现行首次读取正确性要求 |
| 用定时全量扫描替代通知并开放快路径 | 周期性更新索引 | 扫描间隔内可能返回旧结果，除非查询继续直读 | 可撤销，但不解决查询同步 | 排除 |

## 7. 验收设计

### 自动化测试

1. 普通变化产生维护待办；维护成功后确认对应代次，查询 freshness 后端仍为 `none`。
2. 等长、恢复 mtime 的内容改写完成后，注入“通知延迟至刷新返回之后”；首次查询必须直读并返回新内容，不能进入 indexed 路径。
3. 维护取走信号后并发回调写入下一代待办，确认本轮完成不会清掉新信号。
4. 注入维护失败、刷新失败和四轮不收敛；确认欠账回注，下一次握手/维护仍观察到待办，不报告干净状态。
5. 注入 `RootChanged`、三个缺口标志、流停止及回调线程退出；确认维护提示失效且不可在当前进程重建，Hello freshness backend 保持 `none`。
6. 注入根身份不匹配、身份读取失败；确认流失效，且维护检查点不被作为查询 freshness 证明。
7. 流创建/启动失败或两个根任一无法监视时整体无维护提示；回调不做文件扫描或索引写入；`index/` 写入不触发自身维护。
8. 验证失效在同次握手中传播，不出现旧订阅后端或旧配置值；共享 sidecar、freshness、快路径与 Windows 测试保持原状。

自动化注入只能验证状态机与信号账务，不能证明 macOS API 在真实文件系统上的根路径通知行为，也不能构成索引快路径同步保证。

### macOS 外部验收

1. 记录 macOS 版本、文件系统及本地/网络/可移动存储类型；验证启动建立 WatchRoot 流并能维护 `records/`、`attic/` 变化，握手始终为 `none` 且查询直读。
2. 分别移动 `records/` 和 `attic/`，在原路径重建与旧树 stat 完全相同的新目录；确认 RootChanged 或根身份复核使维护提示失效。
3. 改名 store 祖先目录，验证身份复核/WatchRoot 结果使订阅失效；覆盖卷卸载再挂载情形，身份不能确认时失效。
4. 对 `records/`、`attic/` 分别测试新增、原子替换、删除、重命名；测试维护期间并发写入及维护失败回注。
5. 在不支持或无法持续监听的环境验证降级；不要求网络卷必须支持 FSEvents。
6. 按§8步骤5执行回退演练；步骤4只需完成本节外部验收1–5项。两者证据齐备后，才可把本轮实现标记完成。

真实 API 验收不得用手工注入 RootChanged 标志替代。当前环境若非 macOS，所有上述项目列为外部验收项，不得标为完成。

## 8. 实施顺序、门禁与回退

按以下顺序实施；本机可执行测试是开发验证，真实 macOS 行为是外部验收，不作为开发开工门禁。

1. **维护状态与信号账务测试**：写普通事件、并发回调、失败回注、失效和同次握手传播测试。验收证据：自动化测试覆盖第7节1、3–6项。
2. **平台 FSEvents 封装**：实现 WatchRoot 创建参数、根身份采集/复核、事件标志映射和释放。验收证据：封装测试及 macOS 编译通过；测试不能替代第7节真实 API 验收。
3. **Sidecar 维护提示接线**：接入维护器但与 freshness 订阅隔离；默认关闭接线，提供仅用于验收的构建开关；确认 `backend=none`、查询直读。验收证据：第7节自动化测试1、2、7、8项。
4. **真实 macOS 外部验收**：在构建开关打开的验收构建中执行第7节 macOS 外部验收1–5项，记录环境和结果；未完成前不得声称 FSEvents 行为验收通过，也不得默认启用。
5. **回退演练**：对应第7节 macOS 外部验收第6项。在默认启用前关闭验收构建开关并运行现有 store，确认禁用版本仍将 freshness backend 视作 `none`、查询直读且不要求迁移；卸载流后进程可正常退出。留存命令、环境、查询路径和结果。
6. **默认启用维护提示**：仅在步骤4的外部验收1–5证据和步骤5的外部验收6回退演练证据齐备后，方可默认启用本轮维护提示。该启用不批准索引快路径；未来开放快路径需独立决策及验收。

回退方式是禁用维护提示接线、移除 macOS 平台句柄并恢复无订阅路径。无需数据迁移：索引与检查点仍为可重建的派生物；查询本来就直读。回退不得要求旧版识别新的持久格式，因为本方案不新增持久状态。

## 9. 作者自曝：最可能被推翻的三处

1. **FSEvents 仅作维护提示，快路径继续关闭。** 可能被推翻的证据：有适用于受支持系统范围的独立查询同步保证，并通过可控延迟、等长保 mtime 改写的首次查询验收；单次或多次压力测试通过不足以推翻。
2. **WatchRoot 加根身份复核作为维护覆盖护栏。** 可能被推翻的证据：真实 macOS 验收表明某受支持环境中的 WatchRoot 和所选身份接口不能可靠识别根替换/祖先移动；届时须改变维护提示范围或继续禁用该卷上的订阅。
3. **失效后保持无维护提示直到重启。** 可能被推翻的证据：存在经验证的重扫与重新接续协议，能证明恢复过程无覆盖空窗；届时另行设计运行时恢复，不在本轮隐式加入。

## 10. 证据与未验证项

- **由当前代码确认：** macOS freshness 订阅未实现，`fs_name_for` 返回 `None`；sidecar 目前只接入 Windows RDC；freshness 在订阅为 `None` 时不开放索引快路径。
- **评审报告的一手依据：** Watchman 官方文档记录 macOS FSEvents 通知可能晚于 cookie 通知和同步刷新返回；本轮没有在当前机器复现该现象，也不把它表述为 Apple 新规范。
- **Apple API 文档：** 提供 FSEvents 创建、启动、同步刷新、WatchRoot 和事件标志说明。这些 API 说明不消除前述上游观察，刷新零计数故不作为查询同步保证。
- **尚待验证：** 绑定选择、CoreServices 链接、根身份接口与跨版本行为、真实移动/替换/祖先改名通知、支持卷类型、可重复的延迟通知测试注入。
