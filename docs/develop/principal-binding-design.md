# 写路径归属绑定——技术方案（principal 产品级强制）

- 版本：v0.6（终审通过待批准；v0.5 终审无阻断，一项非阻断措辞照改）

- 修订：v0.4 响应 r3 阻断 **B5/B6**。**B5（创建先完成分支仍悬空）**：删除侧对称闭环（决策⑦）——记录的 `envelope.principal` 纳入删除依赖集合：默认**阻止**删除，`force` 越过时**显式告警**（与既有引用删除语义同构）；依赖复核置于被删 principal 的**记录锁内**（现状依赖计算在锁外、锁在其后，同类窗口必须锁内复核）。至此两分支均闭环：删除先完成 → add 锁内复核拒绝（r2）；创建先完成 → delete 锁内复核阻止/告警（本轮）。裁决：活跃台账的身份引用**不**阻止删除——两阶段校验已使台账无法写出悬空归属（后续创建被预检拒绝，错误给出路），阻止无收益。**B6（锁内拒绝无法全店逐字节一致）**：净零对象重新界定为**真相层**（决策⑥ 修订）——锁内复核拒绝承诺"真相层净零"（records/、attic/、事件日志、`.gitattributes`、台账等真相载体不变）；**运行时锁文件显式豁免**于逐字节断言：其存在与内容无真相语义，既有锁协议本就允许锁文件存续、每次获锁重写持有者时间戳。v0.3 的"自建锁文件随释放清理"机制**废止**——现有锁协议 Drop 不删锁文件，释放时删除需与跨进程等待者、陈旧锁判定兼容的安全清理协议且有互斥裂口风险，不做。验收改真相层快照断言，并补"principal 锁文件预先存在"的并发反例。**B5 并发验收补双分支**：删除先完成 → add 拒绝；add 先完成 → delete 阻止或 force 显式告警，不得无声悬空；另补串行删除回归。
- 修订：v0.3 响应复审追加项 **B4**（并发删除穿透锁外校验，悬空归属仍可产生）。修复 = **两阶段协议**（决策⑥）：第一阶段锁外预检（确定性失败在此拒绝，全程零写盘）+ 第二阶段锁内复核（新记录锁之后、任何写盘之前，按全库统一锁规范获取归属 principal 的记录锁，锁内重确认仍在 `records/`；与 principal 删除在该锁上串行，悬空归属在受管并发下结构性排除）。锁序显式声明：新记录锁 → principal 记录锁 → 序列锁，单向获取无死锁环。**零写盘承诺按路径分层**（显式裁决，非静默缩小）：锁外拒绝 = 全程零写盘；锁内复核拒绝 = 终态净零（自建锁文件随释放清理，无记录无事件，`.gitattributes` 未写，前后快照一致）。验收补可控暂停并发交错测试与死锁守护（§4.1/§4.2）。非阻断措辞照改：§2.5 删除与"合法可读无告警"矛盾的治理表述。
- 修订：v0.2 响应 `docs/review/principal-binding-design-review.md`（2026-11-19）。**B1**："仅 principal 类型合法"收窄为"**仅 principal 类型可在受管创建时省略归属**"——收窄落在接口约束层，信封物理格式与公开规范零变更；外部直写与存量记录的空归属仍按原规范合法可读、无告警（§2.5），验收补 read/verify/fix 三面（§4.2）。**B2**：归属解析与拒绝的位置规定到创建操作最前段（`.gitattributes` 写前核验与锁文件创建之前），"磁盘零变化"强断言显式含 `.gitattributes` 与锁文件，验收改店级文件树前后一致并必测"有 .git 缺 .gitattributes"反例（§2.1/§4.1）。**B3**：显式与台账两种来源统一走**创建当次**存在性校验，建台账时的校验不替代；补"建台账→删身份→继承创建"反例与"恢复后成功"验收（§2.1/§4.1）。非阻断两项照改：F5"零新增读取"表述修正（§1.2）；决策⑤"调用方零破坏"改为"签名零变化"（§3）。

## 0. 评审层

### 0.1 待批准清单（本轮批什么）

1. **决策①** 写路径归属规则：显式参数 > 会话台账 > 响亮拒绝；
2. **决策②** 规则落位：单源在核心库（CLI 与 MCP 同源），不在前端各自实现；
3. **决策③** 显式与台账不一致时：显式胜出 + 告警，不拒绝；
4. **决策④** 豁免边界：仅 `principal` 类型创建豁免强制；受管创建的省略口子从"任何类型都可省略"收窄为"仅 principal 类型可省略"（不动物理格式合法域）；
5. 两前端签名不变：MCP `mem_add` 的 principal 保持可选（schema 不动）、CLI `--principal` 保持可选；
6. **B1 路线**：收窄落在受管创建层，信封物理格式与公开规范零变更；外部直写与存量记录的空归属按原规范合法可读（§2.5）；
7. **决策⑥（B4/B6）**：归属校验两阶段协议（锁外预检 + principal 记录锁内复核，与删除串行）；净零承诺界定为真相层——锁外拒绝全店逐字节一致，锁内复核拒绝真相载体零变化、运行时锁文件显式豁免（§2.1）；
8. **决策⑦（B5/B7）**：删除侧对称闭环——记录归属字段纳入删除依赖集合（默认阻止、`force` 显式告警），依赖复核置于被删 principal 记录锁内；force 后悬空由 verify 归属完整性审计承接（执行层统一扫描引用镜像与归属两字段域，信封字段零变更）；活跃台账的身份引用不阻止删除（§2.1 删除侧对称闭环）；
9. 验收测试面（§4.2，含 B2 零写盘反例、B3 串行悬空反例、B4/B5 双分支可控暂停并发反例、删除侧回归、verify 归属断链三组回归与死锁守护）；
10. 评审通过后收编主设计文档：在主档新增一条编号决策承载本方案（主档决策编号顺延），并把开放问题36/30 标注部分收口（见 §7）——对主档的改动本身单独批。

### 0.2 明确不批什么（不在清单上的内容不构成已批准）

- 产品身份的注册托管**全流程**（谁有权创建身份记录、要不要审批）——本方案只覆盖"注册不需要额外流程"这一小片，托管另议；
- 视图（声明式查询模板）的表达力边界问题；
- `adapters/*/AGENTS.md` 宿主模板的具体文案（每宿主一行教学，文案各产品自定）；
- 实施排期与任务拆分（评审通过后另出执行计划）。

### 0.3 自曝三处（作者认为最可能被推翻的点）

1. **破坏面定性**：本方案判定"机制自身没有任何非豁免的建记录路径，拒绝规则不会误伤机制写入"。依据：核心库创建记录只有一个操作（下钻：`ops::add`），全仓检索它的生产调用点恰好 3 处——自举建首条身份 ×1、命令行创建 ×1、MCP 创建 ×1；机制自身的其他路径（回填、修复、合并、删除/恢复）都不新建记录。**会推翻它的证据**：存在未检索到的机制写入路径调用了该创建操作，或未来新增机制写入路径时未意识到豁免规则——后者靠 §4.2 的机制路径回归测试兜底。
2. **MCP 客户端体验倒退**：未建台账就直接 mem_add 的既有 agent 工作流会从"静默成功但无归属"变为"响亮失败"。判断这是收益还是倒退取决于立场：对没发布的产品这是早期纠偏（错误信息给出三条出路），对已深度依赖免签直写的宿主这是破坏。**会推翻它的证据**：存在真实宿主的工作流是"先 add 后 session start"且无法改造——目前无此宿主（产品未发布；MCP 握手时发给客户端的教学串，现状就在教"先建台账"）。
3. **归属与会话耦合**：有人会主张归属应独立于会话存在（add 不带 session 也能有归属）。本方案的回答：无来源的身份就是无身份，拒绝比猜好；独立路径其实已存在（CLI `--principal` 显式参数，批处理脚本逐条显式声明即可）。**会推翻它的证据**：出现"无法预知归属、又不能建会话"的合法工作流。

## 1. 范围与现状

### 1.1 背景与术语（先读这一节，后文不依赖任何外部文档）

本产品的记忆库是跨 Agent 共享的单店：多个宿主产品（CODEX、ZCode 等）读写同一个目录。每条记录的信封（记录头部的机制字段区）有一个归属字段 `principal`，指向一条"执行体身份"记录；台账（会话登记）在建立时必须显式声明身份。用户的问题：CODEX 想让自己的记忆都归属自己的域——**缺省写路径目前做不到**，因为归属参数可省略，省略后记录落入"无归属"状态，没有机制兜底。

本文反复使用的术语，在此一次性讲清：

| 术语 | 一句话解释 |
|---|---|
| 单店 | 所有产品共用同一个记忆库目录；跨产品共享是本产品的设计立场，不是要修的缺陷 |
| 信封 | 每条记录文件头部的机制字段区（id、类型、版本、归属……），机制所有，写入者不手填 |
| 归属（principal） | 信封上指向"身份记录"的单值字段——这条记忆归谁负责 |
| 身份记录 | 库内一条 principal 类型的记录，代表一个执行体（如 codex、zcode、shared） |
| 台账（会话） | 一次工作会话的登记：建立时必填"哪个身份、什么视图、干什么任务"；写路径顺带在台账留痕 |
| 前端 | 调用记忆库的两个入口：命令行（CLI）与 MCP 协议；规则住核心库，入口只传参 |
| 写上下文 | 写操作随身携带的一包引用（库、类型集、台账 id）——署名与台账留痕都从它取 |
| 解析链 | 本文裁决的归属取值顺序：显式参数 → 台账身份 → 响亮拒绝 |
| 响亮拒绝 | 立即失败并给出明确原因与出路；绝不静默成功或静默放行（本仓库对参数错误的既有处置形态） |
| 豁免 | 不走解析链强制的类型：仅身份类型本身（身份不能要求先有身份） |
| 自举 | 空库初始化（mem init）时创建第一条身份记录——此刻库里无任何身份可归属 |
| slug | 记录的短名（按类型声明充当唯一键）；身份记录的短名如 codex、shared，传参时短名与记录 ID 均可 |
| 破坏面 | 本次改动迫使修改的既有代码与测试清单（见 §1.2 F9、§4.2） |

### 1.3 现状的缺口（一句话）

身份声明点其实已经存在且强制（F6），但**写路径不消费它**（F1/F2/F3）——同一个产品里"先建台账、再写记忆"的标准流程，写出来的记忆依然无归属。宿主适配层今天教了"先建台账"，机制层却没有兑现"建了台账就有归属"。

## 2. 方案

### 2.1 归属解析链（核心规则，一条）

创建记录时，归属按以下顺序取第一个可用者：

```
1. 显式参数（CLI --principal / MCP principal）；
2. 会话台账——调用携带台账 id、且台账存在并可读时，用台账登记的身份；
   台账缺失或损坏视为无台账（身份不可从残缺现场猜出，直接落入第 3 步）；
3. 响亮拒绝——错误信息给出三条出路：显式传归属 / 先建会话台账 / principal 类型本身豁免。
```

**两阶段校验（评审 B4：锁外预检 + 锁内复核，两种来源一视同仁）**：解析链产出归属 ID 后——无论来自显式参数还是台账——归属校验分两阶段执行：

- **第一阶段，锁外预检**：按当前全库状态扫描，确认归属指向 `records/` 中现存的 principal 类型记录。确定性的失败（无归属、归属指向不存在或已隔离进隔离区的身份）在此响亮拒绝——此路径全程零写盘。**建台账时的校验不能替代本预检**：台账可长期存活，身份可在期间被删除；
- **第二阶段，锁内复核**：预检通过后，按既有创建锁序获取新记录锁，随后、在任何写盘（含 `.gitattributes` 写前核验与记录文件）之前，按全库统一锁规范获取归属 principal 的记录锁，锁内重新确认其仍在 `records/`。复核失败 → 释放自持锁 → 响亮拒绝，错误注明"创建期间身份已被删除"（锁文件的处置见下方净零承诺的界定，决策⑥）。

两阶段缺一不可：只有第一阶段，"预检通过后、创建完成前另一进程删除身份"的并发交错会写出悬空归属（评审 B4 反例）；只有第二阶段，无归属这类确定性错误要拿到锁才能发现，零写盘承诺破产。

**锁序（在全库统一锁序内声明新增点）**：本方案新增的锁获取点有两处——创建侧的归属 principal 记录锁（新记录锁之后、事件序列锁之前）与删除侧的依赖锁内复核（在被删 principal 的记录锁内，见下）。全路径单向获取（新记录锁 → principal 记录锁 → 序列锁），无反向边；并发创建争同一 principal 锁时一方等待，无环；既有其他写路径不获取 principal 锁，不产生新环。

**删除侧对称闭环（评审 B5；决策⑦）**：创建与删除在 principal 锁上串行后，胜负两分支必须都闭环，缺一不可：

- **删除先完成** → add 锁内复核发现身份已不在 `records/` → 响亮拒绝（前一轮已修复）；
- **创建先完成** → 带归属的新记录已存在，此时 delete 该身份：现状的删除依赖集合只看记录的引用边、**不看归属字段**，且依赖计算发生在取得 principal 锁之前——会无声移走身份、留下悬空归属。修复：归属字段纳入删除依赖集合（默认**阻止**，`force` 显式告警——与既有引用删除语义完全同构），且依赖复核置于 principal 记录锁内。锁内复核是必须的：只把归属塞进锁外预检，仍有"删除预检通过 → add 创建归属记录 → 删除再取锁"的同类窗口。`force` 越过后的悬空归属，由 **verify 的归属完整性审计**报告（本方案新增的审计面，见 §5——现状断链审计只扫引用镜像、不读归属字段，若不补审计则 force 后的显式可发现性没有实现路径，评审 B7）。

两分支闭环后，受管并发下悬空归属被双向结构性排除：任何一侧后到，都会在对端持有的锁上等待，并在锁内看到对方的最新结果。

豁免：`principal` 类型的创建不适用此链（自举与注册的合法通道，见决策④）。

**执行位置**：第一阶段位于创建操作的最前段——可写性只读检查之后、`.gitattributes` 写前核验与任何锁文件创建之前；第二阶段在新记录锁内、写前核验之前。合法写入时既有的写前核验与同批提交纪律原样保留（顺序在其后，不删除）。

失败形态沿用本仓库已裁决过的同类处置：此前发现创建时载荷缺省会被静默清空内容，裁决为必须响亮拒绝（禁止静默缺省）。归属沿用同一形态——解析链走到底仍无归属时，返回通用参数错误并附明确文字与出路，不新造错误类别、不静默放行。**强断言（按拒绝路径分层，显式裁决见决策⑥）**：

- **锁外预检拒绝：全店逐字节一致**——此路径未获取任何锁，"磁盘"指全店文件树含运行时锁文件：有 `.git` 而缺 `.gitattributes` 的店是确定可达的反例（写前核验若先于预检执行，拒绝路径会留下这个新文件）；
- **锁内复核拒绝：真相层净零**——records/、attic/、事件日志、`.gitattributes`、会话台账等**真相载体**零变化，前后快照逐字节一致；**运行时锁文件显式豁免**于该断言：锁文件的存在与内容（含每次获锁重写的持有者时间戳）无真相语义，既有锁协议本就允许锁文件在记录消失后继续存续。豁免依据与裁决过程见决策⑥——v0.3 曾承诺"自建锁文件随释放清理"，经核验与现有锁协议不符（Drop 不删锁文件；释放时删除需兼容跨进程等待者的安全清理协议且有互斥裂口风险），废止。

**承诺边界**：悬空归属防御覆盖**受管并发**（经接口的创建与删除）；绕过接口的外部直写删除不在承诺内——它是机制外的合法路径，其可见由坏写入识别机制承接（与全库其他完整性承诺同一边界）。验证点见 §4.1。

### 2.2 规则落位：核心库单源

解析链实现在核心库的创建操作内（写上下文已随身携带台账 id 与库引用，读台账无新依赖）。CLI 与 MCP 各自只做一件事：把调用参数原样传入。理由与先例：关键词检索功能曾因命令行与 MCP 各写一套匹配逻辑、命中结果不一致被评审打回，收口为"执行逻辑单源在核心库、前端只传参"后评审通过；归属是写路径的核心不变量，更没有理由例外。

前端只改两处描述性内容：
- CLI `--principal` 的帮助文本：补"缺省时从 --session 台账继承；两者皆无则拒绝"；
- MCP 协议 instructions（握手时发给客户端的教学串）：补一句"写前先建台账，归属自动继承"。

工具 schema 与 CLI 参数签名**零改动**（决策见 §3 决策①⑤）。

### 2.3 显式与台账不一致：显式胜出 + 中性告警

调用同时给了显式归属和台账、且两者不同时：用显式的，并在响应的告警数组里追加一条提示（创建操作的响应本就带告警数组——机制对可容忍偏差不拒绝、只随响应附说明，宽松分档校验用的是同一通道）。不拒绝——机制层的威胁模型历来是"防错报、不防伪装"：显式声明就是显式声明，机制不审查动机。

告警文案必须是**中性事实陈述**（如"显式 principal 与台账 principal 不同"），不得写成警示语气——因为显式传一个非台账身份是**合法常态操作**：跨归属共享内容就是靠它写入的（完整写法见 §2.4）。若文案暗示"可能出错"，常态操作会制造告警疲劳，告警反而失去信号价值。

### 2.4 跨归属内容的写入姿势（评审问答）

评审中会被问到的场景：Agent 要创建**跨归属**的内容（不是只属于自己产品的记忆），怎么传？答案分三层——归属、关联、可见是三个不同的维度，由三个不同的机制承载，不要合并到归属一个字段上：

| 维度 | 承载者 | 跨域写法 |
|---|---|---|
| 归属（谁写的/谁负责） | 信封归属字段，**单值**（一条记录一个主，数据模型层面不存在多归属） | 归作者（台账继承）；确需共同拥有的内容（如约定）显式传共享身份 |
| 关联（和谁相关） | 信封类型化引用 + 主题挂接（主题本身是库内的一条条记录，不是写死在机制里的枚举） | 跨域引用对方的记录 id、挂双方共用的主题 |
| 可见（谁能看到） | 视图（声明式查询模板） | 视图不限归属维度即可跨域可见——归属从来不是可见性边界 |

共享身份的注册：建一条短名（slug，身份的唯一短标识）形如 `shared` 的身份记录（走决策④的豁免通道，无需归属），之后任何产品的会话显式传 `principal=shared` 写共享内容（传短名或记录 ID 均可，现有解析两者都认）——显式优先级（决策③）就是这条路的机制支撑，触发的告警是中性事实陈述（§2.3），属预期行为。

#### 具体调用形态（两前端现存语法，本方案不改签名）

**场景 A：归作者（最常见）。** 先建台账、后写入、不传归属——归属自动继承台账身份。以 CODEX 会话为例：

MCP（`tools/call` 的 `arguments`；第二步不传 `principal`）：

```json
{"name": "mem_session_start", "arguments": {"principal": "codex"}}
→ {"session": "<台账id>", ...}   // 响应还含 status/watermark 等字段

{"name": "mem_add", "arguments": {"type": "memory", "payload": {"title": "..."}, "session": "<台账id>"}}
→ {"id": "...", "warnings": []}   // 信封归属 = codex 的记录 id
```

CLI（`add` 的类型是位置参数）：

```bash
mem session start --principal codex          # → 输出 "session": "<台账id>"
mem add memory --payload '{"title":"..."}' --session <台账id>
```

**场景 B：写跨归属共享内容。** 一次性注册共享身份（豁免通道，无需归属），之后显式传它：

```bash
mem add principal --payload '{"slug":"shared","label":"共享域"}'   # 一次性注册
```

MCP（带台账 + 显式归属 → 显式胜出，`warnings` 含中性提示）：`{"name": "mem_add", "arguments": {"type": "memory", "payload": {"title": "..."}, "principal": "shared", "session": "<台账id>"}}`

CLI：`mem add memory --payload '{"title":"..."}' --principal shared --session <台账id>`

不带 `--session` / `session` 也可：显式归属是唯一来源，无告警。告警出现在创建响应的 `warnings` 数组（两前端字段同名）。

**场景 C：无显式归属且无台账。** 响亮拒绝，错误信息给出三条出路：显式传归属 / 先建台账 / 身份类型本身豁免（§2.1）。

明确排除：把同一条内容复制两份分别归属两方——违反单一副本（同一逻辑身份一份实体，跨机器迁移等于复制目录，库内不做份）。多归属（把归属字段扩成数组）也不做：归属是"谁负责"，多主让责任指向模糊，且改信封格式牵动唯一性校验、视图过滤、事件日志全链——收益不抵。

### 2.5 空归属的合法域：受管创建收紧，格式规范不动（B1 契约）

本方案收窄的是**受管创建**的接口约束，不是信封字段的物理合法域——两者分属不同层，混为一谈是 v0.1 的阻断项 B1：

- **物理格式层（公开规范管，零变更）**：信封归属字段的取值形态保持现状——字符串或空均可，非空必须指向现存 principal。公开信封格式规范（存储格式的单一事实源）零变更，解析器零变更；
- **受管创建层（本方案管）**：经创建操作写入时，省略归属仅 principal 类型可用；其余类型省略即拒绝（§2.1）；
- **外部直写与存量记录**：直接放入店内的非 principal 空归属记录，按原规范**合法、可读、无告警**，校验不报坏，修复不动它——与现行行为完全一致，零新行为；这类记录合法但未归属，按归属过滤检索时自然不命中。受管更新不携带归属参数，这类记录无法经接口补归属——接受这一现状（生产无存量）。

信封注释同步改写为如实描述："空 = 未归属；受管创建仅 principal 类型可省略归属；外部写入的未归属记录按格式规范合法可读。"

### 2.6 宿主适配层落点（回答"要补齐什么"）

**一行教学，零新配置**。各宿主产品的 AGENTS.md/Skill 加一句："会话建立用你产品的身份（如 codex），之后所有写入自动归属"。机制层负责强制（没台账就拒绝），教学层负责选身份——这正是"宿主薄适配"的既有分工（每个宿主只加一层薄壳：教学与配置，机制规则一律住核心库），不新增任何配置项、环境变量或启动参数。

## 3. 决策条目（六要素）

### 决策① 写路径归属规则：显式 > 台账 > 响亮拒绝

- **① 背景**：当前创建记录时归属可整体省略，省略即无归属（终身的，创建后补不了）。跨产品共享单店里，无归属记忆无法按产品域过滤，也不知是谁写的。
- **② 选项**：
  - (a) 维持现状：归属可省略，无归属合法；
  - (b) 显式 > 台账 > 拒绝（本方案）；
  - (c) 服务端启动时绑定产品身份（给服务进程加身份参数）；
  - (d) 纯宿主教学：只靠文档教 agent 每次显式传。
- **③ 后果**（破坏了会怎么表现）：
  - (a) 无归属记忆持续累积；按产品域检索要靠调用方自觉，漏一次就污染；等数据攒多再清理等于给存量做迁移，代价更大；
  - (b) 未声明身份的写入立即失败——对忘建台账的 agent 是一次响亮纠偏（错误信息指出路）；批处理脚本需逐条显式声明，比免签多一个参数；
  - (c) 身份出现第三个声明源（台账、显式参数、启动绑定），必须再裁决"谁优先、冲突算谁的"，且服务进程为多产品共享时绑不住单一身份——把已经解决的问题再复杂化一遍；
  - (d) 教学可被遗忘，漏传静默成功——保证建立在每次调用都读过文档的前提上，无机制兜底。
- **④ 可逆性**：(b) 若选错，回退 = 恢复"缺省放行"，一行改动；已产生的归属记录不受影响（它们只会更完整，不会因回退损坏）。(a)(d) 事后补强需做存量无归属数据的迁移（逐条定归属，人审），代价远高于现在拒绝。
- **⑤ 依据强度**：F1–F8 已代码核验；"无归属是终身的"由 F8 支撑；"拒绝不会误伤机制写入"由 F7 支撑（全仓仅 3 处生产调用点）。
- **⑥ 推荐 + 默认**：推荐 (b)。人不决定时默认走 (b)——它是唯一同时满足"身份不可推断"（身份必须来自显式声明或显式建立的台账）与"单一事实源"（声明点唯一）两条既有立法方向的选项。

### 决策② 规则落位：核心库单源，前端零逻辑

- **① 背景**：解析链若在 CLI 与 MCP 各写一遍，两套实现随时间漂移——本仓库的关键词检索功能就发生过：同一匹配语义两处实现，评审发现命中结果不一致，最终收口为单源。
- **② 选项**：(a) 核心库单源（本方案）；(b) 前端各自解析后传入。
- **③ 后果**：(a) 两前端行为由同一份代码保证一致，测试在核心层一处覆盖；(b) 每加一个前端（未来的 sidecar 直调等）就要重实现一次规则，漏一个就出现绕过归属的通道。
- **④ 可逆性**：(a)→(b) 迁移是把核心逻辑上提到前端，机械但无收益；(b)→(a) 迁移需要先补核心层测试面。先 (a) 后悔成本低。
- **⑤ 依据强度**：单源教训已在本仓库发生并被裁决过一次（检索执行器），有实施后全绿证据；写上下文已含台账引用（F5），核心层实现无新依赖。
- **⑥ 推荐 + 默认**：推荐 (a)。人不决定时默认 (a)。

### 决策③ 显式与台账不一致：显式胜出 + 告警，不拒绝

- **① 背景**：解析链的两种来源可能同时存在且取值不同。不一致不一定是错误——跨归属共享内容就靠显式传一个非台账身份写入（写入姿势见 §2.4），因此告警只做中性事实陈述，不做警示语气。
- **② 选项**：(a) 显式胜出 + 告警（本方案）；(b) 拒绝（强制一致）；(c) 台账胜出。
- **③ 后果**：(a) 记录归属与调用者意图一致；不一致在响应告警中可见，人评审时能发现；极端情况下 agent 可以故意传错身份且成功——但机制层从不承诺防伪装，这是既有威胁模型的边界；(b) 出现新的一类失败："显式声明因与台账冲突被拒"——显式声明本是最高优先级的意图表达，被拒挫败感最强，且审查动机超出机制职责；(c) 显式参数静默失效，调用者以为传了就是传了，实际归属被覆盖——比 (a) 更隐蔽。
- **④ 可逆性**：(a)→(b) 收紧是一行守卫；(a)→(c) 反转优先级同样一行。均低代价。
- **⑤ 依据强度**：威胁模型边界（防错报不防伪装）是已裁决的设计立场；创建响应的告警数组是既有通道（宽松分档校验在用），实现成本一行。
- **⑥ 推荐 + 默认**：推荐 (a)。人不决定时默认 (a)。

### 决策④ 豁免边界：仅 principal 类型；受管创建的省略口子收窄

- **① 背景**：身份记录（principal 类型，即"身份本身"）的创建不能要求"归属到某个身份"——先有身份才有归属；空库初始化创建第一条身份时（自举），库里既无身份也无台账。现状的无归属口子比需要的宽：任何类型省略都放行。
- **② 选项**：(a) 仅 principal 类型豁免，其余类型一律走解析链（本方案）；(b) 维持全类型可省略；(c) 豁免收紧到"仅库内无任何 principal 记录时"（真·首条才豁免）。
- **③ 后果**：(a) 受管创建的无归属从"任何类型可达"收窄为"身份类型专属"（外部直写不受此限，其记录语义见 §2.5）；注册第二个身份（如 CODEX 的身份记录）走同一条豁免路，无需特殊时点判定；(b) 等于不修；(c) 需要机制每次创建时扫描全库判"是否首条"，成本高且脆弱——并发注册时两个创建互相看见与否会翻转判定，且身份记录被删进隔离区（本库删除 = 移入隔离区而非消失）后统计口径随之翻覆；收益为零，因为后续注册的身份记录本来就该无归属。
- **④ 可逆性**：收窄后若发现某类型合法地需要无归属，再放宽该类型——按类型放宽是局部改动。
- **⑤ 依据强度**：F4（现状注释本就把无归属与自举绑定）；F7（自举调用点类型恰为 principal，豁免自然覆盖）。
- **⑥ 推荐 + 默认**：推荐 (a)。人不决定时默认 (a)。

### 决策⑤ 两前端签名不变

- **① 背景**：MCP 工具 schema 与 CLI 参数若把归属升为必填，会强迫每次调用重复传——与"台账继承"语义冲突，且破坏既有调用方。
- **② 选项**：(a) 签名不变，归属保持可选、语义由解析链承载（本方案）；(b) schema 升必填。
- **③ 后果**：(a) **签名零变化**——既有调用的参数写法全部有效；但行为契约收紧：无显式归属且无台账的既有调用从"静默成功但无归属"变为拒绝（§0.3 自曝第 2 条如实承认该破坏）。"必填"的语义由核心层拒绝兜住（不传且无台账 = 拒绝），等效于条件必填；(b) 每次调用都带身份，台账继承形同虚设；既有调用方全部破坏。
- **④ 可逆性**：日后升必填随时可做（加 required 是加严，兼容性单向）。
- **⑤ 依据强度**：现状的 MCP schema 中归属本就可选（§1.2 F1 已核验）；台账继承语义由决策①承载。
- **⑥ 推荐 + 默认**：推荐 (a)。人不决定时默认 (a)。

### 决策⑥ 归属校验两阶段协议；净零承诺界定为真相层（运行时锁文件豁免）

- **① 背景**：两阶段协议（r2 B4 修复）引入锁内复核后，复核失败的路径必然曾持有锁文件；而锁协议的实况（r3 核验）是：锁释放**不删除**锁文件，且每次成功获锁都会把含时间戳的持有者信息**覆盖重写**进锁文件——即使锁文件预先存在（如并发删除刚持有过），内容也已改变。因此"锁内拒绝后全店文件逐字节一致"按字面执行，要么测试必败，要么诱导实现去删锁文件——而删除锁文件会制造互斥裂口（等待者仍持旧文件句柄，另一进程经新路径创建新文件，出现两个锁实体）。
- **② 选项**：
  - (a) 两阶段协议 + 净零界定为**真相层**：锁内拒绝承诺真相载体（记录、隔离区、事件日志、写前核验文件、台账）零变化；运行时锁文件的存在与内容显式豁免于逐字节断言（本方案）；
  - (b) 仅锁外校验，防御承诺降级为"尽力而为"；
  - (c) 坚持全店逐字节一致（含锁文件）：给出与跨进程等待者、陈旧锁判定兼容的完整锁清理/内容恢复协议。
- **③ 后果**（破坏了会怎么表现）：
  - (a) 锁内拒绝路径的断言是"真相层前后一致 + 指定锁文件豁免"——断言可执行、不诱导危险实现；代价是"逐字节一致"的字面范围缩小到真相层，锁文件时间戳变化不在断言内；
  - (b) 并发交错下悬空归属照旧产生，归属可信承诺降级为概率性保证；
  - (c) 需要证明锁清理在"等待者持旧句柄"场景下不产生两个锁实体——这是跨进程文件锁协议的深水区，为一条拒绝路径的断言字面性付出全局协议复杂度与风险。
- **④ 可逆性**：(a)→(c) 是收紧断言范围，随时可做（补锁文件协议后把豁免收回来）；(a)→(b) 是移除复核步，机械。
- **⑤ 依据强度**：锁文件无真相语义有协议依据——既有协议允许记录消失后锁文件继续存在，锁文件本就是协调原语而非数据；持有者重写与不删锁文件均经 r3 源码核验；两阶段的互斥复核形态沿用 r2 论证（锁序单向，新增获取点可枚举：创建侧 principal 锁与删除侧锁内复核，共两处，均在全库锁序的单向链上）。
- **⑥ 推荐 + 默认**：推荐 (a)。人不决定时默认 (a)。

### 决策⑦ 删除侧归属依赖处置：纳入依赖集合、锁内复核；活跃台账引用不阻止删除

- **① 背景**：r3 B5——创建先完成后，删除流程照常执行：依赖集合只遍历记录的引用边、**不检查归属字段**，且依赖计算发生在取得被删 principal 记录锁之前。结果：身份被无声移入隔离区，新建记录的归属悬空。两阶段校验只堵住了"删除先完成"一侧。
- **② 选项**：
  - (a) 记录的归属字段纳入删除依赖集合（默认阻止，`force` 显式告警），依赖复核置于被删 principal 的记录锁内；活跃台账的身份引用不纳入依赖（本方案）；
  - (b) 归属纳入依赖但只做锁外预检（不锁内复核）；
  - (c) 除记录归属外，活跃台账的身份引用也阻止删除；
  - (d) 不改删除，靠事后校验发现悬空再修复。
- **③ 后果**（破坏了会怎么表现）：
  - (a) 两分支闭环：创建后删除会被告知"有 N 条记录归属此身份"并阻止；`force` 越过时显式告警并留断链注记——与既有引用删除语义完全同构，删除者的越权是显式选择。断链注记的承接 = **verify 新增归属完整性审计**（对非空归属字段检查目标是否仍为现存身份记录；指向隔离区或缺失时按既有断链注记形态报告三要素：来源记录、目标身份、修复入口——修复入口按缺位形态分写：目标在隔离区 → "恢复身份记录"；目标缺失（外部删除）→ "如实报告缺失，给出可用的历史/备份恢复指引"）。审计在执行层统一扫描引用镜像与归属两个字段域，**不把归属隐式复制进引用集合**（守住信封字段与公开格式零变更）。agenda 不在本方案新增扫描范围。锁内复核堵住"删除预检 → add 创建 → 删除取锁"的同类窗口。代价：锁内复核与归属审计均需扫描记录归属字段，成本随库规模线性（与既有直读扫描同阶，性能归档既有性能基线问题）；活跃台账在身份被删后继续存活，其后续写入会被创建预检拒绝，错误信息给出路（换身份或重建身份）——台账持着已删身份无法再写，属可接受的行为闭环；
  - (b) "删除预检通过 → add 创建归属 → 删除取锁执行"窗口照旧穿透，无声悬空仍在；
  - (c) 阻止无收益：两阶段校验已保证台账写不出悬空归属，身份删除后活跃台账只是"不能再写"，没有数据损坏；阻止反而锁死身份清理路径；
  - (d) 悬空在事后才被发现，违背"受管并发下结构性排除"的承诺定位。
- **④ 可逆性**：台账引用日后纳入是加严（阻止集变大），随时可做；反向（移除阻止）会让既有删除决策失效，代价高。先窄后宽安全。
- **⑤ 依据强度**：依赖集合只看引用边、依赖计算在锁外，均经 r3 源码核验；`force` 告警与断链注记的承接形态是既有删除语义（已被引用删除使用）。
- **⑥ 推荐 + 默认**：推荐 (a)。人不决定时默认 (a)。

| 悬空归属被双向排除（受管并发下） | 两阶段协议 + 删除侧对称闭环：创建侧 principal 锁内复核；删除侧依赖锁内复核（归属字段纳入依赖集合，决策⑦）——互斥由锁语义保证，不依赖时序（§2.1） | 反例×3：串行——建台账 X → 删除 X → 继承创建响亮拒绝且真相层净零，恢复 X 后创建成功（r1 B3）；并发·删除先完成——add 预检后可控暂停 → 删除 X → 恢复 add → 拒绝且真相层净零（r2 B4）；并发·创建先完成——add 创建完成后 delete X → **默认阻止** / `force` 显式告警，不得无声悬空（r3 B5）；另验证两分支多轮交错在超时内完成（无死锁） |

| 显式与台账不一致时显式胜出且告警可见 | 解析链第 1 步优先 + 告警数组追加 | 核心层测试：台账 X + 显式 Y → 归属 = Y 且告警含不一致提示 |

### 4.2 验收测试面（修复缺陷先写复现测试的纪律适用）

1. **核心层**（mem-core 测试）——十组：继承、拒绝、显式胜出+告警、豁免、悬空归属串行反例、悬空归属并发反例（双分支）、删除侧归属依赖回归、verify 归属断链审计、外部空归属语义、死锁守护；
   - 拒绝断言按路径分层（决策⑥）：锁外拒绝 = **全店逐字节一致**（未触任何锁文件；必测"有 `.git` 缺 `.gitattributes`"反例——拒绝后该文件未被创建）；锁内复核拒绝 = **真相层净零**（真相载体前后快照一致；运行时锁文件豁免——用"principal 锁文件预先存在"反例验证：持有者时间戳被并发重写不影响断言）；
   - 悬空串行反例：建台账 X → 删除身份 X → 继承创建响亮拒绝且真相层净零；恢复 X → 创建成功；
   - 悬空并发反例（可控暂停，双分支）：删除先完成——add 预检后暂停 → 删 X → 恢复 add → 拒绝且真相层净零；创建先完成——add 创建完成后 delete X → 默认阻止 / `force` 显式告警，不得无声悬空；
   - 删除侧回归：创建归属 X 的记录 → 删 X 默认阻止 → `force` 后删除成功且告警含归属悬空、verify 报断链注记；
   - verify 归属断链审计三组回归（评审 B7）：force 删除身份后 verify 报告断链且含三要素（来源记录、目标身份、修复入口）→ 恢复身份记录后复跑 verify 告警消失 → 空归属记录与正常归属基线 verify 不误报；
   - 死锁守护：合法创建与并发删除多轮交错在超时内完成（新增锁序单向，无死锁环）；
   - 外部空归属语义：手工放入非 principal 空归属记录 → 读取正常、校验不报坏、修复不动它；principal 空归属仍合法（自举回归）；
2. **MCP 端到端**（mem-mcp 测试）：建台账 → 创建（不带归属）→ 继承成功；无台账的创建 → 响亮拒绝且错误信息含三条出路，并在前置反例店（缺 `.gitattributes`）断言无文件变化；
3. **CLI 端到端**（mem 测试）：`--principal` 显式；`--session` 继承；两者皆无 → 拒绝——三态与 MCP 逐字对齐，拒绝用例同样断言前置反例下无文件变化。

破坏面修复（机械改动）：§1.2 F9 所列测试中走核心创建且归属缺省的调用，逐一补显式归属或补台账上下文——修复本身即验收面 1 的负面样本来源。

## 6. 排除方案一览

| 排除项 | 一句话理由 |
|---|---|
| 服务端启动绑定（serve 加身份参数） | 身份第三声明源，优先级与冲突问题自找复杂化；多产品共享进程时绑不住（决策①选项 c） |
| 严格模式（拒绝显式与台账不一致） | 审查动机超出机制职责，威胁模型历来防错报不防伪装（决策③选项 b） |
| 解析链放前端各自实现 | 两套实现必然漂移，本仓库已为此付出过一轮评审代价（决策②选项 b） |
| 豁免收紧到"仅真·首条" | 每次创建扫全库判首条，成本高、并发下判定脆弱，收益为零（决策④选项 c） |
| schema 升必填 | 台账继承形同虚设，既有调用方全破坏（决策⑤选项 b） |
| 存量无归属数据迁移 | 无生产数据；产品未发布，无归属记录仅存在于测试夹具——为不存在的数据设计迁移是想多了 |
| 归属参数改类型化枚举（编译期强制） | 与运行时拒绝等价但迫使全部构造点改写（含 73 处测试），防错收益不抵机械成本 |
| 收窄信封物理格式合法域（修订公开规范 + 定义外部/存量迁移路径） | 收窄受管创建即可达成目标；改格式层要牵动公开规范、解析器、外部直写治理与存量语义，无对应收益（B1 契约，§2.5） |
| 锁内复核改为再次无锁扫描（不加锁重读一遍） | 无锁扫描与并发删除之间仍有窗口，只是缩小不是排除——全称防御要求互斥，不是概率（评审 B4） |
| 删除侧只做锁外归属预检（不锁内复核） | "删除预检通过 → add 创建归属 → 删除取锁执行"窗口照旧穿透，无声悬空仍在（评审 B5） |
| 锁内复核拒绝时删除自建锁文件以保全店逐字节断言 | 现有锁协议 Drop 不删锁文件；释放时删除在"等待者持旧句柄"场景下可产生两个锁实体（互斥裂口）——锁文件豁免于断言，协议不动（评审 B6，决策⑥） |
| 活跃台账的身份引用纳入删除阻止集 | 两阶段校验已使台账写不出悬空归属（身份删除后其后续写入被创建预检拒绝，出路明确），阻止无收益还锁死身份清理路径（决策⑦选项 c） |
| 把归属隐式复制进引用集合以复用既有断链审计 | 改信封字段集合，违反"信封字段与公开格式零变更"承诺；改为审计执行层统一扫描两个字段域，格式零变更（评审 B7） |
